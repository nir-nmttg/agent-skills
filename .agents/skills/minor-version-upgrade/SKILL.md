# Ruby・Node・Pythonをまとめて更新する

Ruby・Node（JavaScript／TypeScript）・Pythonのランタイムと依存ライブラリについて、互換性を保つマイナー・パッチ更新を一つのまとまりとして進める。新しい版の導入前に供給網を確認し、更新後のテストと対象に応じた実操作まで行う。マイナー番号でも互換性は保証されず、監査が成功しても攻撃がないとは断定できない。

Python 3.9 以降の標準ライブラリで動く [実行ゲート](references/gate.md) を必須にする。最終採用候補の導入・更新は、根拠付きの固定7項目と機械検査を通った計画を `scripts/supply-chain.py run` から一度だけ実行する。調査用 scratch での解決と固定した更新前グラフの基準環境再現は [準備手順](references/isolation.md#4-準備段階と対応できない工程) に従い、対象へ反映しない。`check` 後の任意コマンドや skip・force で代用しない。

## 対象と検証計画を決める

1. 対象の指示、未コミット差分、README、CI、manifest・ビルド定義・存在する lockfile、環境の版指定、コンテナ設定を静的に読む。[管理系統の見分け方と注意点](references/ecosystems.md) から該当する節を選び、Ruby・Node・Pythonのランタイムと採用中の依存管理ツールの版・管理方法を調べる。Bundler、npm／pnpm／Yarn、uv／pip／Poetry等のうち実際に使うものを確認し、管理方式を勝手に切り替えない。未知のラッパー・ビルド定義・プラグインは、版の確認のためにもいきなり実行しない。
2. 範囲指定がなければ、現在のプロジェクトにある3言語のランタイムと直接・間接依存を対象にする。混在する構成は系統ごとに一覧化し、dev・build・optional 依存、workspace、CI のみの依存も含める。未探索の系統・OS・アーキテクチャを記録する。他言語の構成は影響・依存境界を記録し、更新対象へ広げない。グローバル環境・OS 全体・管理ツール本体は依頼された場合だけ扱う。
3. このスキルの実体から `bash scripts/new-run.sh <project-slug>` を実行し、出力先を `RUN` とする。`report.md` に対象、元の差分、候補表、取得日時と根拠 URL、実行結果、保留理由を随時記録し、`plan.json`・証拠・ゲート状態もここに保存する。候補編集前に [保存・反映契約](references/isolation.md#6-検証した差分を保存して対象へ反映する)に従い、全適用予定パスの元の有無・hash・実行 bit を親側に記録する。対象・候補用コピーから分離し、隔離 executor へ `RUN` 全体を渡さない。スクリプトへのパスは対象プロジェクトの作業場所ではなくスキルから解決する。秘密値や実データを保存しない。
4. 変更前後に実行する既存テスト・型チェック・lint・ビルドを CI から選び、Web・CLI・ライブラリ・ネイティブアプリなど対象の利用形態に合う操作と期待結果を対応づける。下記の隔離準備後に基準結果を取り、既存失敗と実行不能を新しい失敗と区別する。Web は必要なら変更前の画面も記録する。

## 更新候補を絞る

- 最新情報は実行時に公式レジストリ、リリースノート、セキュリティ告知、サポート方針で確認する。`latest` タグだけで選ばず、互換性・サポート期間・既存の制約を満たす安定版を選び、導入する正確な版を固定する。範囲指定を変える場合も既存の pin 方針を守る。
- Ruby・CPython本体は同一 `X.Y` の patch、Node本体は同一 major の minor・patch を一括候補にする。Rubyのブランチ変更、Pythonのfeature release、Nodeのmajor更新は `$major-version-upgrade` へ回す。ライブラリは各製品の公式方針で分類し、SemVerの `1.x` 以降は同一major内の互換更新を候補とする。`0.x` のminor増加・非互換変更・分類不明な版は一括に入れない。PEP 440等をSemVerの互換性保証と解釈しない。
- prerelease、撤回・非推奨・既知の悪性版、対象環境でサポートされない版を除く。候補版と全実配布物（wheel・image 等）の最も新しい公開日時から **7日以上** が必須で、日時不明・未来の日時・7日未満はゲートが停止する。より厳しい組織方針は追加で守る。緊急修正でも短縮しない。これは検知を待つための下限で、安全の証明ではない。
- 現在の互換系列の保守が終了していれば、その場で系列を越えず移行が必要と報告する。同梱ツール、peer／plugin／ビルド依存、native ABI、要求するRuby・Node・Pythonの版、対象プラットフォームの組合せも確認する。
- 候補表は「管理系統・種類・名前・現在の解決版 → 候補の正確な版・公開日・公式方針による分類理由・状態」を持たせる。直接依存だけでなく、解決時に変わる全間接依存・ビルド依存にも同じ確認を適用する。個別扱いの版変更を一括更新に紛れ込ませず、互換性を満たす既存系列の別候補に固定するか個別移行へ回す。
- ABI 別 wheel 等の同版配布物への切替は実際の `source` 変更として版上昇と分け、差分・hash・公開日・出所・監査・互換性を全件確認する。同版・同じ取得元の metadata だけの変更は認めず、互換性不明なら個別移行へ回す。

## 隔離環境を準備する

image が供給するランタイムの変更は、[計画の `runtime_image`](references/gate.md) に image 参照と ID を記録し、実行設定へ結びつける。正確な実版は準備時と最終 worker 内で照合する。native 拡張には対象版の headers・compiler・build tool を含む image を選び、固定したソースから再ビルドして実際にロード・テストする。

[隔離環境の準備](references/isolation.md) に従い、対象のランタイム・管理ツール・OS に合う公認 image を調査して digest を固定し、同梱の `scripts/docker-sandbox.py prepare` で既存 Docker 上の設定と executor を自動生成する。同梱コード・生成設定・worker と probe の結果をレビューする。条件を満たす既存のコンテナ・VM・OS sandbox も利用できる。Web・DB 等を含む検証は `init` 前に全工程を完遂できる既存 executor を選び、用意できなければ検証・適用を保留する。準備成功だけで供給網レビューを `pass` にしない。

Docker 本体の導入・daemon 起動、`sudo`・root 実行・socket の権限変更などのホスト設定変更はこの準備で行わない。信頼済みの同梱処理が既存 Docker へ接続するための [Codex の実行承認](references/isolation.md#docker-接続と-codex-の実行承認) は利用できる。通常実行の接続拒否だけで保留せず、正規の承認手続きで切り分ける。承認不可・未導入・未起動・通信・image のツール不足などで準備できなければ、確認結果と再開条件を報告する。既存 executor のパスを一律に尋ねず、静的調査と差分案を続ける。

## 導入前の供給網を確認する

1. [供給網と実行・動作検証](references/verification.md) と [実行ゲート](references/gate.md) を読み、公開元、配布物、脆弱性、コード実行箇所、隔離条件を確認する。使う管理系統について [更新方法の注意点](references/ecosystems.md) も読む。下記の一括処理にも、この確認を省略しない。
2. 静的に読める manifest・ビルド定義・lockfile と公式メタデータから仮候補を作る。準備・レビューした隔離で、秘密を除いた最小コピーと専用 cache を使う。基準用は現在のランタイムと固定した更新前グラフを再現して照合・テストし、候補解決用とは worker・入力・出力を分ける。公認元からの固定した取得物と、条件を満たす [監査専用の照会](references/isolation.md#5-対象コードを実行しない監査照会) は、対象コードを実行しない取得用プロセスで揃える。依存解決やメタデータ取得でもビルド定義・backend・hook・plugin を実行し得るため、コード評価がある操作には `init` 前から隔離を適用する。同梱 executor は外部通信を許可しない。コード評価と通信の両方が必要、またはコード評価を排除できるか不明なら、送信先を限定できる既存隔離を確認し、なければその工程を保留する。
3. 更新前後の全依存 inventory と候補グラフを固定し、版・取得元・integrity/checksum・git ref・追加削除・install/build script の変更を全件一覧化する。全変更版の取得物・公開日時と、更新後の全ライブラリ・ビルド依存の監査 JSON を揃え、実際の配布物差分を読む。ランタイムだけの変更でも既存依存を監査する。導入に必要な manifest・設定・移行用の静的な変更も候補コピーで準備する。`schema_version: 2` の `RUN/plan.json` に、準備・レビューした隔離 executor の実体・設定・argv 配列を固定する。自動準備時は `sandbox/execution.json` を `plan.execution` へ統合し、worker・include・補助 script 等の候補外ファイル入力を `execution.inputs` に列挙する。入力先はゲートの token で指定し、全入力の hash と、ファイルでない image 等の immutable digest を確認する。
4. 脆弱性と悪性パッケージの告知、配布元の連続性、署名・provenance、疑わしいコード、監査 DB の鮮度と隔離境界を複数の根拠で確認する。監査ゼロ件、署名、provenance、利用者数のいずれも単独の採用根拠にしない。署名が未提供なら独立した代替根拠と限界を記録する。証拠不足・不審・互換性不明の候補は保留し、機械検査不能を自動で `pass` にしない。
5. 保留対象を除外するときは、依存関係を再解決して計画・inventory・監査・差分を作り直す。保留版が間接依存に残るならその導入元も保留する。既存の危険な版に戻すだけでは解消扱いにしない。独立した範囲だけを進める場合も、その全件を新しい計画で確認し直す。
6. `init` でゲートを初期化する。起動は [実行ゲート](references/gate.md) の信頼済みPython実体・絶対パスのゲート・`-I -S` を必須とする。`coverage`・`sources`・`artifacts`・`advisories`・`authenticity`・`isolation`・`compatibility` の7項目はすべて `unknown` から始め、非空の実際の証拠と説明を付けて `review` する。証拠の SHA256・時刻・計画 fingerprint を結びつける。`check` は全項目の有効な `pass` と機械検査が揃うまで停止する。証拠・監査は24時間で期限切れとなり、監査のエラー・skip・非対応・finding・coverage 不足も停止の根拠になる。既存の証拠変更・期限切れ・既存 `pass` の別証拠への置換や `fail` からの復活を同じ `RUN` の再承認に使わず、新しい実行記録で全レビューをやり直す。

## 採用した候補をまとめて反映する

- `"$UPGRADE_PYTHON" -I -S "$UPGRADE_GATE" run --run "$RUN"` で、事前確認を終えた一つの計画だけを反映する。ゲートは承認済み入力を読み取り専用 snapshot にコピー・照合し、直前の時刻で証拠・監査も再検査する。executor は token を解決した snapshot を受け取り、隔離内の scratch へコピーして導入・テストする。元の候補を実行せず、出力先は別の `RUN/execution-output` だけとする。レビュー済みの argv 配列を `shell=False` で一度だけ起動し、`RUN` 全体を渡さない。executor 内の処理は管理系統と依存順に分かれてよいが、各 minor ごとに承認や全テストを挟まない。Ruby・Node・Pythonの連携、native extension／addonのABI、生成コードの互換条件を保ち、採用表にない更新を加えない。
- 確認した配布物と固定した全依存グラフで再現可能に導入し、実行時の未確認な再取得・再解決を許さない。管理ツールの版を固定し、既存 lockfile を削除して作り直さない。lockfile がない系統は、既存方式で正確な全解決版・取得元・digest・必要なビルド依存を記録して再照合する。再現できる固定方法がなければ保留する。native build や必要な script は、内容と取得バイナリまでレビューして計画した隔離内で許可する。
- 候補で準備した環境指定、manifest・ビルド定義・lockfile 相当、必要な CI・コンテナ設定を同期する。ホストの既定環境切替、`sudo`・root 実行、グローバル更新を代替策にしない。最終 worker 内で下記の検証を完了し、[保存・反映契約](references/isolation.md#6-検証した差分を保存して対象へ反映する)に従って全差分・実行 bit・削除と証拠を保存する。結果を読み、元の全適用予定パスの初期状態を再照合してから許可差分だけを反映する。キャッシュ・依存ディレクトリ・秘密ファイルを持ち込まない。
- 導入後の実バージョン・依存グラフ・checksum を、同じ worker 内で候補表と照合する。新たな依存・別版や入力の変更があれば停止し、新しい実行記録で計画と全レビューをやり直す。同じ計画の再実行やゲート外の導入で修正しない。適用に付随するコード修正は互換性の維持に必要な最小範囲とし、新機能や設計変更を混ぜない。

## 最終 worker 内で検証し、結果を確認する

1. `init` 前に、最終 worker が導入 → 実版・全依存グラフ・digest の照合 → 計画したテスト・型チェック・lint・ビルドと必須チェック → 対象別の実操作 → 許可差分と証拠の保存を一度の `run` 内で完了するよう組む。`set -eu` で始め、必須処理の失敗を終了コードへ伝える。重大なセキュリティ修正は再現可能な回帰テストでも確認する。
2. チェック成功後、CLI・ライブラリ等は同じ worker 内で `references/verification.md` の正常系・異常系を実行する。Web・DB・ネイティブ操作は、事前に選んだ既存 executor が検査済み環境を維持して必要な実操作まで完了する。Web は組み込みブラウザで正常系・入力エラー・保存後の再表示を確認する。全工程を完了できない候補は未検証とし、適用しない。
3. 同梱 executor の scratch と導入済み環境は worker 終了時に消える。`run` 後は保存した検証結果・差分を確認し、その環境で後続コマンドを動かせると扱わない。追加検証・失敗修正・原因調査のための分割・部分除外には、新しい実行記録・計画で全レビューと導入・検証をやり直す。残す更新の組合せで検証を完了し、未検証の差分を対象に残さない。
4. `git diff --check` と最終差分を確認する。テストの削除・失敗の無視・監査や checksum の無効化・強制オプションで通さない。ユーザーの既存変更を戻さず、自分のサーバーなど一時プロセスは終了する。

## 結果を報告する

日本語で、採用した更新と保留一覧、供給網の根拠と限界、ゲートの7項目・機械検査・`run` の結果、検証コマンドと結果、実操作の入力・期待／実際の結果・証拠、Web の場合は URL と画面操作、残る問題と元に戻す方法、`report.md` のパスを簡潔に伝える。記録は実行ごとに分ける。

Web の影響がない対象は理由と対象別の実行検証を記録し「ブラウザ検証は対象外」とする。組み込みブラウザが使えない場合、必要な Web 検証は「未実施」とし、外部ブラウザや E2E 成功で置き換えない。隔離不足やネットワーク制限などで進めない場合も、未実施の工程と安全に再開する条件を示す。供給網確認・テスト・必要な実操作が揃うまで検証完了としない。疑わしい兆候がなかった範囲に限り「確認した範囲では疑わしい兆候を検出しなかった」と述べ、検出した兆候は根拠と停止・保留を明示する。コミット・push・PR・公開は別途依頼があるときに行う。

ゲートは同じ UID の利用者による意図的な偽造や直接コマンドの迂回を防ぐ OS 境界ではなく、成功しても供給網の無害を保証しない。根拠・隔離・検証の不足を隠さず残す。
