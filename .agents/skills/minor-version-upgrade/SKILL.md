# Ruby・Node・Pythonをまとめて更新する

Ruby・Node（JavaScript／TypeScript）・Pythonのランタイムと依存を、互換性を保つ範囲で一つのまとまりとして更新する。

静的確認を通った更新差分を反映して完了する。Docker・導入環境・テスト・ブラウザ操作を利用できないことだけでは保留しない。静的確認済みと動作確認済みを区別し、未実施の検証を成功扱いにしない。

組織・対象プロジェクトの必須条件も守る。

## 対象と更新候補を調べる

1. 対象の指示、未コミット差分、README、CI、manifest・ビルド定義・既存 lockfile、環境の版指定を静的に読む。採用中の Ruby/Bundler、npm/pnpm/Yarn、uv/pip/Poetry 等を [管理系統の見分け方](references/ecosystems.md) で確認し、管理方式を勝手に変えない。未知のラッパーやプロジェクトコードを版確認のために実行しない。
2. 範囲指定がなければ現在のプロジェクトにある3言語のランタイムと全依存を一覧化する。他言語は影響と依存境界を記録し、グローバル環境・OS・管理ツール本体は依頼範囲だけ扱う。
3. Ruby・CPython 本体は同一 `X.Y` の patch、Node 本体は同一 major 内の互換更新を候補にする。Ruby/Python の系列変更、Node の major、ライブラリの major・`0.x` minor・非互換・分類不明の変更は `$major-version-upgrade` へ回す。製品の公式方針を優先し、PEP 440 等を SemVer の互換保証と解釈しない。
4. スキル実体から `bash scripts/new-run.sh <project-slug>` を実行し、`RUN/report.md` に元の差分、候補一覧、根拠 URL と取得日時、結果を記録する。候補編集前に [保存・反映契約](references/isolation.md#6-検証した差分を保存して対象へ反映する) の全許可パスと初期状態を記録する。秘密・実データは保存しない。

## 静的に確認する

1. 実行時の公式レジストリ、リリースノート、移行ガイド、サポート方針、セキュリティ告知から、正確な安定版と取得元を確認する。`latest` だけで選ばず、撤回・非推奨・既知の悪性版、対象環境で非対応の版を除く。候補版と新たに採用する全実配布物（wheel・image 等）の最新の公式公開日時から7日以上を必須とする。最新安定版が7日未満なら、7日以上経過した適切な安定版を選び、適切な版がなければ当該対象を保留して再開可能日を報告する。日時不明・未来も保留し、不明な再開日は推測しない。同版の新規配布物を古い版の初回公開日で代用せず、緊急修正でも待機を短縮しない。
2. 更新前後の全依存 inventory を照合する。直接・間接・dev・build・optional・workspace・CI の依存を含め、全変更版の配布物・取得元・hash・追加削除・install/build script、peer/plugin・ランタイム要求・native ABI を確認する。[供給網の確認](references/verification.md) と [管理系統ごとの注意点](references/ecosystems.md) に従い、配布物は実行せず検査する。ランタイム更新でも残る既存依存の脆弱性確認を省略しない。
3. ゲートの初期化前に、manifest・既存 lockfile 相当・ランタイム指定・必要な CI 設定と移行ソースを候補コピーで完成させる。既存の管理方式と pin 方針を保ち、lockfile を推測で作らない。その後 `schema_version: 2` の `RUN/plan.json` を作り、候補コピー・全依存 inventory・取得物・根拠を固定する。モード指定は不要で、`execution` は指定しない。過去の実行付き計画や承認を流用しない。起動には [実行ゲート](references/gate.md) の信頼済み Python 実体・絶対パスのゲート・`-I -S` を使う。
4. `init` の後、`coverage`・`sources`・`artifacts`・`advisories`・`authenticity`・`compatibility` の6項目を、非空の実際の根拠と説明を付けて `review` し、`check` を通す。静的確認のために `isolation` を `pass` にしない。監査 JSON がある場合はエラー・finding・coverage 不足を無視せず、JSON のない場合の公式告知による全依存確認はゲートの条件に従う。署名等の未提供は独立した代替根拠と限界を記録し、不明を確認済みと偽らない。
5. 取得元・hash の不一致、採用を妨げる既知の脆弱性・悪性告知、明確な非互換、未解決の依存制約や必須移行の漏れは修正するか、その対象を保留する。根拠・候補・計画の変更、失敗や期限切れはゲートに従って新しい `RUN` に分ける。

同版の ABI 別 wheel 等への切替は、実際の `source` と hash の変更を記録して確認する。同版・同じ取得元の metadata だけの変更は更新候補にせず、互換性不明なら個別移行へ回す。保留対象を除外するときは、残る組合せを解決・確認し直し、未確認の版を間接依存に残さない。

## 更新差分を反映する

- 事前準備した manifest・lockfile 相当・ランタイム指定・設定・移行ソースが静的ゲートに固定した内容と一致することを確認する。初期化後に差分を追加・修正するなら、既存の承認を使わず新しい `RUN` で静的確認をやり直す。lockfile を削除して全再解決したり、正しさを確認できない固定記録を捏造したりしない。
- lockfile 生成・依存解決・code mod・ビルド定義等がコードを評価する場合は、[隔離条件](references/isolation.md) を適用する。静的確認の成功はホストで対象・依存コードを動かす許可ではない。必要な実行環境を用意できず正しい更新差分を作れない対象は保留し、独立して反映できる対象を進める。
- `"$UPGRADE_PYTHON" -I -S "$UPGRADE_GATE" run --run "$RUN"` を実行する。ゲートの `run` はコードを起動せず、確認した候補の反映用 snapshot と静的結果を保存する。これは依存のインストールやテストの成功を意味しない。
- 保存した結果を読み、[保存・反映契約](references/isolation.md#6-検証した差分を保存して対象へ反映する) に従う。全反映予定パスの元の有無・hash・実行 bit を再照合し、ユーザー変更との競合がなければ許可した追加・変更・削除・rename だけを反映する。保存時の mode を流用せず、適用後の hash・実行 bit・削除を照合する。秘密・依存ディレクトリ・cache は持ち込まない。
- `git diff --check` と最終差分、manifest/lockfile/版指定の整合を確認する。静的条件を満たす正しい更新差分を反映したら、更新は完了とする。テストや実操作の未実施だけを理由に未完へ戻さない。

## 可能な場合に追加検証する

- CI と既存手順から、変更に関係するテスト・型チェック・lint・ビルド・対象別の実操作を選ぶ。静的 `run` 後の承認済み snapshot と固定配布物から、別の検証用 `RUN` に準備したレビュー済み executor で実行する。境界・worker・設定を事前確認し、[実行ゲート](references/gate.md)・[隔離手順](references/isolation.md) に従う。静的計画へ `execution` を追加しない。
- 利用できないチェックは対象と理由を記録する。既存失敗、環境の不足、更新による新しい失敗を区別する。更新由来の失敗は修正する。反映後にソースだけを直す場合も、[再確認手順](references/isolation.md#反映後に修正が必要になった場合)で当該更新分だけを安全に取り下げ、実際の更新前グラフから修正済み候補を新しい `RUN` で6項目の静的確認にかける。解消できない対象は自分の反映分だけ安全に取り下げて保留し、ユーザー変更や独立した完了済み更新を戻さない。その対象に依存する後続の更新も見直す。テストを削除したり、実際の失敗を「未実施」に書き換えたりしない。
- ランタイムの系列変更・native 拡張は、実版・対象 ABI・再ビルド・ロードを実測した範囲だけ動作確認済みとする。Web は組み込みブラウザ、その他は利用形態に合う操作を選ぶ。必要な導入は検証コンテナ内に留め、依存をホストへ持ち出さない。検証結果にソース・lockfile の修正があれば、上記の再確認手順に従い、元の静的承認を再利用しない。
- 本番データの変換や実サービスへの書込みは別途依頼がある場合だけ行う。

## 結果を報告する

日本語で、採用した版と差分、静的ゲートの結果と根拠、保留対象と理由、追加検証の成功・失敗・未実施と理由、残る制約、元に戻す方法、`report.md` のパスを簡潔に伝える。完了時は「更新を反映済み・静的確認済み・実行テスト未実施」などと明示し、「動作確認済み」「全検証成功」と混同しない。疑わしい兆候を確認しなかった範囲と未確認の範囲を示し、供給網の無害を保証しない。自分の一時プロセスは終了する。コミット・push・PR・公開は別途依頼があるときに行う。
