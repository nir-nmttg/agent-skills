# プロジェクトの設計に合わせてリファクタリングする

プロジェクト自身の設計思想・責務分担・依存関係に実装を揃える。修正件数や見た目の統一を目標にせず、根拠のある逸脱がなければ変更しなくてよい。

## 探索して設計の根拠をつかむ

- リポジトリの指示と作業中の変更を確認する。対象が指定されていればその範囲と関連する呼び出し元・依存先を調べ、指定がなければプロジェクト全体の構成と主要な処理経路を入口に探索する。生成物・依存パッケージ・外部から取り込んだコードは直接の修正対象にしない。
- README、設計文書、ADR、CONTRIBUTING、モジュール構成、公開 API、設定、代表的な実装とテストを照合する。必要に応じて関連する履歴を確認し、責務の境界、依存の向き、データの流れ、エラーや副作用の扱い、拡張方法を読み取る。特定のアーキテクチャや自分の好みを持ち込まない。
- 明文化された方針と、複数の実装から推定した慣習を区別し、判断に使うファイルやコード箇所を押さえる。多い書き方をそれだけで正解にせず、古い文書、移行途中の実装、意図的な例外も見分ける。文書と実装が矛盾し、どちらが現在の方針か判断できない箇所は保留する。

## 逸脱と修正範囲を決める

- 候補ごとに「設計の根拠」「逸脱している実装」「具体的な問題」「既存の設計へ合わせる方法」を説明できるようにする。たとえば責務の漏れ、依存方向の逆転、共通の仕組みを迂回する実装、同じ業務ルールの分散を調べる。局所的な命名や形式の違いだけを設計違反と決めつけない。
- 正当な例外や未採用の将来構想を、現在の設計への違反として直さない。設計を実装に合わせて書き換えることで逸脱を解消したことにしない。設計自体の変更が必要な場合は、リファクタリングと分けて理由と選択肢を報告する。
- 根拠が明確で効果のある修正を、影響範囲を追える単位に分けて進める。探索結果と採用する方針を簡潔に伝え、通常の内部リファクタリングは提案だけで終わらせず実施する。レビューだけの依頼なら指摘と提案に留める。
- 公開 API、永続化形式、業務ルール、外部への副作用などの振る舞いを変える必要があれば、その箇所は保留してユーザーに確認する。設計の判断が不要な独立した修正は進める。対象範囲を黙って広げず、保留や未探索の範囲を明らかにする。

## 振る舞いを保って変更する

- 対象の契約と影響範囲を確認し、変更前に関連する既存のチェックを実行する。既存の失敗と実行不能を記録し、変更による失敗と区別する。重要な振る舞いを守るテストが足りなければ、必要な回帰テストを追加する。
- 既存の抽象化・共通処理・依存の渡し方を活かし、責務や処理を適切な場所へ移す。呼び出し元、依存先、設定、テストまで追って整合させる。一律の共通化や、将来のためだけの層・フレームワークの導入は避ける。
- 戻り値、エラー、処理順序、トランザクション、権限、外部 I/O など、対象に関係する契約を維持する。振る舞いを固定するテストは残し、内部構造に依存するテストは観測する契約を保って更新する。失敗を隠すためにテストや必須チェックを弱めない。
- ユーザーの未コミット変更を上書き・巻き戻しせず、自分の変更と区別して扱う。関連する説明や参照先が変更で古くなる場合は、必要な範囲で更新する。

## 確認と報告

- 変更した処理と影響範囲のテスト、型チェック、lint、ビルドなど適切な既存の検証と、リポジトリで必須のチェックを実行する。差分を読み直し、呼び出し経路や依存関係が設計へ揃ったことと、振る舞いが維持されていることを確かめる。
- 日本語で簡潔に、探索した範囲、採用した設計の根拠、修正箇所と理由、実行コマンドと結果、保留・未探索・未検証の事項を報告する。逸脱が見つからなければ、確認した範囲と変更不要と判断した根拠を伝える。限られた探索でプロジェクト全体に問題がないと断定しない。
