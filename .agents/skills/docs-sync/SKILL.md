# 実装に合わせてドキュメントを整える

現状の実装を正として、読者が現在の使い方と振る舞いを理解できるドキュメントに更新する。情報量や修正件数を目標にせず、必要な情報を見つけやすくする。整合している説明はそのまま残す。

## 対象と根拠を確かめる

- 指定されたファイル・機能・差分の範囲で作業する。指定がなければ README.md を入口に、そこから参照される利用・開発ドキュメントと関連する実装を確認する。無関係な文書まで一律に書き換えない。
- リポジトリの指示と既存の変更を読み、作業中の実装変更も含めて確認する。公開版など対象の版が指定されていれば、その版の実装を基準にする。異なる版の説明を混ぜない。
- 文書の説明を、入口となるコード、コマンド定義、設定・既定値、処理の分岐、CI、関連テストなどと照合する。名称やファイルの存在だけで対応済みと判断せず、利用者から到達できる振る舞いを確かめる。テストやコメントと実装が食い違うときは実装を基準にする。
- 実装を文書に合わせる変更は行わない。不具合らしい挙動も、意図された仕様・推奨手順と断定しない。根拠を確認できない点は推測で補わず、更新できる部分を進めて未確認事項として報告する。
- 設計上の意図、背景、過去の経緯、将来の計画は、現行機能の説明と区別して扱う。コードに見当たらないだけで削除せず、文書の目的と現在の有用性で判断する。

## 必要な情報を選ぶ

読者が導入・利用・開発・運用で何を判断し、実行するための情報かを基準にする。

| 判断 | 基準と対応 |
| --- | --- |
| 残す | 現在も正しい説明、前提、重要な制約、判断に役立つ背景。表現を統一するだけの全面改稿は避ける。 |
| 書き換える | 現状と異なる使い方・設定・既定値・振る舞い。古い記述に訂正を追記するのではなく、その箇所を現在の説明へ置き換える。 |
| 統合する | 同じ情報の重複や、本文と注記に分散した説明。主な説明場所にまとめ、別の文書からは必要に応じて参照する。 |
| 削除する | 廃止された手順、無効な選択肢、読者の判断に役立たない実装の細部。移行や互換性のために必要な情報は適切な場所に残す。 |
| 追加する | 導入・利用に不可欠な手順、設定、制約、失敗時の対処など、欠落すると読者が困る情報。コードの網羅的な解説は追加しない。 |

- README は概要と主要な導線を中心にし、詳細は既存の適切な文書へまとめる。短い説明で足りる内容のために新しい文書を増やさない。
- 元の状態を否定するだけの説明にしない。「以前の説明は誤り」「X はできない」で終わらせず、現在できること、使う手順、条件を具体的に書く。たとえば起動コマンドが変わったら、現在のコマンドと必要な前提を示す。
- 非対応・制限・注意事項は、読者の判断や誤操作の防止に必要なものを残す。代替手段が実装にあるなら添える。不要な否定の列挙も、制約を隠すための削除も避ける。
- 文書の読者、言語、用語、構成を尊重する。変更履歴や移行説明が目的の箇所以外では、作業の経緯や新旧比較を本文に持ち込まない。

## 確認と報告

- 更新した記述を根拠の実装に照らして読み直す。コマンド、引数、パス、設定名、リンクや見出しへの参照を確認し、重複や不要になった注記も整理する。
- 文書用の lint・リンク検査・ビルドなど、対象に適した既存のチェックとリポジトリで必須の確認を行う。安全に実行できるコマンド例は必要に応じて試す。外部への変更を伴う操作を検証目的だけで実行しない。
- 差分を確認し、重要な前提や制約が埋もれていないか、根拠のない断定や依頼外の実装変更がないか確かめる。実行できなかった検証を成功扱いにしない。
- 日本語で簡潔に、更新した文書と主な変更理由、整理・削除した情報の理由、確認結果、残る未確認事項を報告する。変更が不要ならその旨を伝える。
