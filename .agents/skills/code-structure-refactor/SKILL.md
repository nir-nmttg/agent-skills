# 責務分割と共通化でプロジェクトを整える

変更理由が異なる処理を分け、同じ知識やルールの重複を整理して、変更箇所と影響範囲を理解しやすくする。改善候補の列挙で終わらせず、効果を説明できるものを実装・検証する。分割数やコードの削減量を目標にせず、有益な変更がなければ変更しなくてよい。

## 探索して変更の理由をつかむ

- リポジトリの指示と作業中の差分を確認する。対象が指定されていればその範囲と関連する呼び出し元・依存先を調べ、指定がなければ全体構成と主要な処理経路から探索する。生成物・依存パッケージ・外部から取り込んだコードは直接編集しない。
- README、設計文書、モジュール構成、代表的な実装とテストから、責務の境界、依存の向き、データと副作用の流れ、既存の共通処理を把握する。既存設計からの逸脱だけでなく、現在の構造自体に改善余地があるかを見る。特定のアーキテクチャへの移行を前提にしない。
- 大きなファイルや関数、条件分岐、似たコードを探索の入口にし、呼び出し経路と利用側まで読む。長さや見た目だけで問題と決めず、変更理由の混在、同じ修正が複数箇所に必要になる構造、暗黙の依存、理解に必要な往復を確かめる。
- 候補ごとに、根拠となるコード、困る変更の具体例、改善方法、影響範囲を押さえる。実際の利用箇所や変更履歴を必要に応じて調べ、効果とリスクから着手する範囲を選ぶ。未探索の領域まで問題がないと断定しない。

## 責務分割と共通化を判断する

| 対象 | 判断と進め方 |
| --- | --- |
| 責務の混在 | 入出力、業務判断、永続化、表示など変更理由の異なる処理が絡んでいる場合、意味のある境界で分ける。呼び出し側から目的が読み取れ、必要な依存とデータが明示される形にする。 |
| 同じ知識の重複 | 同じ業務ルールや変換・検証が分散し、一緒に変更されるべきものは共通化する。既存の適切な共通処理があれば利用し、利用側に不要な依存を持ち込まない場所へ置く。 |
| 見た目が似た処理 | 意味、境界条件、失敗時の扱い、変更理由が異なるなら別に保つ。共通化のための多数のフラグや例外分岐が必要なら、無理に一つへまとめない。 |
| 拡張しづらい構造 | 現在の利用例や要求で繰り返される変更を局所化する。仮想的な将来の用途だけを理由に、汎用フレームワーク、設定項目、継承階層を増やさない。 |
| 過剰な分割・抽象化 | 一つの処理を理解するための往復や間接参照が増えている場合は統合・単純化も選ぶ。短い関数や共通 helper を作ること自体を成果にしない。 |

- 採用する変更と理由を簡潔に伝えてから、影響範囲を追える単位で進める。内部の構造改善は一律の承認待ちにしない。レビューだけを求められている場合は実装しない。
- 公開 API、永続化形式、業務ルールなどの契約変更が必要になる箇所は、通常のリファクタリングと分けて理由と選択肢を確認する。既存の依頼で許可された範囲を踏まえ、判断に依存しない改善は進める。

## 振る舞いを保って実装する

- 対象の返り値、例外、境界条件、状態変更、外部 I/O を把握し、関連する既存テストを変更前に確認・実行する。既存の失敗と実行不能を記録して変更による失敗と区別する。重要な契約の検証が不足している場合だけ、必要な回帰テストを補う。
- 処理の抽出・移動、依存の整理、利用側の置き換えを小さな単位で行う。呼び出し元、import・export、設定、テスト、関連文書を追い、移動漏れや循環依存を確かめる。不要になったコードは参照を確認して取り除く。
- 処理順序、トランザクション境界、権限、リトライ、キャッシュ、リソースの寿命など、移動や共通化で変わりやすい意味を維持する。副作用や遅延評価を持つ処理を単なる式の重複としてまとめない。
- テストは利用側から観測できる契約を守る。内部構造に依存する確認は契約を維持して更新し、失敗を隠す削除や必須チェックの緩和は行わない。依頼外の仕様修正や全面的な整形、ユーザーの変更の上書き・巻き戻しを混ぜない。

## 検証して結果を報告する

- 変更箇所と共通処理を利用する影響範囲のテスト、型チェック、lint、ビルドなど適切な既存の検証と、リポジトリで必須のチェックを実行する。実行できなかった検証は成功扱いにしない。
- 差分を読み直し、契約が保たれたか、責務や依存が明確になったか、利用側が読みやすくなったかを確認する。重複を減らしても分岐や間接参照が増えただけなら、共通化の範囲を見直す。
- 日本語で簡潔に、探索した範囲、変更箇所と改善理由、共通化しなかった候補とその理由、実行コマンドと結果、保留・未探索・未検証の事項を報告する。変更不要なら、その根拠を伝える。
