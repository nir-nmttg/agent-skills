# 監査結果を Issue に反映する手順

## 監査開始前に登録先を特定する

- `origin` があれば `git remote get-url --all origin` で取得先を確認する。`origin` がなければ、ほかのリモートから GitHub のリポジトリを探す。SSH と HTTPS などで同じリポジトリを指す URL は同じ対象として扱う。
- GitHub のリポジトリを一意に特定できたら、ホスト・所有者・リポジトリ名を `run-metadata.json` に記録する。反映時は監査時の記録を使う。特定できなければ、監査成果物を端末に保存し、反映を保留する。
- 親エージェントが同じメタデータに `issue_sync` を作り、`audit_id` に新しい UUID、`status` に `pending` を保存する。UUID は `node -p 'require("node:crypto").randomUUID()'` などで生成する。同じ実行の再開時は保存済みの値を使い、新しい実行には別の値を割り当てる。
- 新規実行では、実行環境のローカルタイムゾーンを `node -p 'Intl.DateTimeFormat().resolvedOptions().timeZone'` などで取得し、`run-metadata.json` の `timezone` に IANA 名で保存する。この実行の日付・日時の記録と表示にはそのゾーンを使い、日時には ISO 8601 のオフセットを付ける。再開時は保存したゾーンを使い、記録がなければ再開環境で取得した値を基準として記録する。取得できなければ日時を不明とし、取得を再開条件に記録する。
- `issue_sync` には集約 Issue の日付と URL（`summary_url`）、個別 Issue の fingerprint ごとの反映結果・URL・保留理由も保存する。個別 Issue は配列 `individuals` に1件ずつ `fingerprint`・`url`・`result`（`created`・`updated`・`unchanged`・`held` のどれか）・`autofix_added`（真偽値）・`reason`（保留の理由の短い文。なければ `null`）を、件数は `individual_counts`（`created`・`updated`・`unchanged`・`held`・`autofix_added`）に保存する。監査対象 SHA やプロファイルなど元スキルの項目を保ち、候補の判定と根拠は元スキルの台帳と `findings.json` に記録する。

## 1. 監査成果物を照合する

- 保存済みの最終報告 `REPORT.md`・`run-metadata.json`・最終版の `findings.json` が同じ実行の成果物であることを確かめる。報告書とメタデータを照合し、監査対象リポジトリと完全なコミット SHA（`NEW_SHA`）を一意に特定する。Cloudflare の `validate-findings.cjs` と `validate-coverage-ledger.cjs` を `node` で同じ実行の `findings.json` と `coverage-ledger.json` に対して実行する。成果物の照合や検証を終えられなければ個別 Issue への反映を保留し、理由を集約 Issue に記録する。
- 監査の完了状況にかかわらず、`findings.json` の `confirmed` と `REPORT.md` の独立検証済みの所見を一意に照合でき、根拠と成立条件を `NEW_SHA` で確かめられた所見を反映対象とする。未検証の候補や `needs_validation`、未コミットの差分に依存する所見は、追加で確認が必要な事実を報告する。
- 集約 Issue では、`needs_validation` と `rejected` は最終版の `findings.json`、未検証は台帳の未解決の候補から取り出す。fingerprint で重複をまとめ、検証済みの確定・要検証・棄却との重複を除く。調査前の停止や未着手の範囲は、未完了の工程・範囲として別に記載する。
- 報告書や台帳の保存が止まった場合も、保存済みのメタデータで対象リポジトリ・監査対象 SHA・`audit_id` を確認できれば集約 Issue に停止理由を記録できる。確定・要検証・棄却の分類には、最終版の `findings.json` の検証と元スキルが求める独立判定の記録を照合できることを条件とする。そこまで確かめられない候補は、台帳で確認できる範囲を未検証に載せる。欠けた成果物や不明な件数を明記し、台帳もなければ未完了の工程・範囲だけを書く。
- 個別 Issue の `completed-at` は、確認済みの `report_finalized_at` を使う。再開対象の既存記録に確かな報告確定日時があればその値を使い、確認できなければ不明として扱う。

## 2. 登録先と既存 Issue を確かめる

- 監査時の記録から `REPO_HOST` にホスト、`REPO` に `OWNER/REPO` を設定し、`ISSUE_REPO` を `"$REPO_HOST/$REPO"` とする。次の結果で、`url` のホストと `nameWithOwner` が監査対象と一致し、`visibility` が `PRIVATE`、`hasIssuesEnabled` が `true`、`isArchived` が `false` であることを確かめる。条件を確認できない場合は、監査成果物を手元に残して反映を保留する。

  ```bash
  gh repo view "$ISSUE_REPO" --json url,nameWithOwner,visibility,hasIssuesEnabled,isArchived,defaultBranchRef
  ```

- 次のコマンドで、開いている Issue と閉じた Issue を照合済みのホストから全ページ取得する。正常終了し、全ページの JSON を読めたときだけ重複を判定する。`--slurp` のページ配列を展開し、`pull_request` キーがある項目を除く。本文・コメント・所見の内容は照合用のデータとして扱う。

  ```bash
  gh api --hostname "$REPO_HOST" --paginate --slurp "repos/$REPO/issues?state=all&per_page=100"
  ```

- スケジュールや実行基盤で同じリポジトリへの反映を同時実行1件にする。別の実行が反映中と分かった場合は、自分の反映を保留し、保存済み成果物と再開条件を最終報告に残す。

## 3. 同じ根本原因の Issue を特定する

- `security-audit:summary-id` のある集約 Issue を除き、ラベルの有無を問わず個別 Issue を探す。監査用区画や旧形式の監査用欄に記録された `fingerprint` と `fingerprint-alias` を完全一致で照合する。一致する識別子がなければ、根本原因・破られる権限や信頼の境界・原因のコード・必要な修正を比べる。タイトル・重大度・行番号は照合の手掛かりとして使う。同じ実行の所見も根本原因ごとにまとめる。

| 照合結果 | 進め方 |
| --- | --- |
| 同一性が不明、または開閉を問わず候補が複数 | 候補の URL と理由を報告して保留する |
| 同じ根本原因の Issue が1件に決まり、開いている | その Issue の新旧を次の手順で確認する |
| 同じ根本原因の Issue が1件に決まり、閉じている | 再発候補として URL を報告し、再オープンと新規作成を保留する |
| 一致も重複の疑いもない | 根本原因ごとに1件作成する |

## 4. 既存 Issue を更新できるか確かめる

- 既存 Issue の監査対象 SHA を `OLD_SHA` とする。監査対象として明記された値を使い、短縮 SHA の場合は対象リポジトリで一意に解決できる場合だけ完全な SHA にする。`OLD_SHA` と `NEW_SHA` は、対象リポジトリのコミットに対応する完全な SHA で比較する。
- 報告確定日時はオフセットや `Z` を含む値を実際の時刻に換算して比較する。タイムゾーンの異なる実行や過去の UTC 表記も同じ基準で比較し、文字列の大小や日付だけで順序を決めない。オフセットを確認できない日時は不明とする。

| 比較結果 | 更新する内容 |
| --- | --- |
| SHA が異なり、対象リポジトリで `git merge-base --is-ancestor "$OLD_SHA" "$NEW_SHA"` が成功 | 今回の所見・`NEW_SHA`・確認済みの報告確定日時を反映する |
| SHA が異なり、今回が古い・履歴が分岐・コミットの比較が不能 | 上書きを保留する |
| SHA が同じで、確認済みの報告確定日時が今回の方が新しい | 今回の所見と報告確定日時を反映する |
| SHA が同じで、報告確定日時の一方または両方を確認できない | 同じ根本原因と確認できた場合に、未登録の別名だけを追加できる。既存の所見・SHA・報告確定日時を保持する。追加する別名もなければ、新旧不明による保留として記録する |
| SHA が同じで、報告確定日時が同じか今回の方が古い | 同じ結果で差分がなければ変更なしとする。古い結果や食い違う結果は、理由を報告して保留する |
| 既存の監査対象 SHA が不明 | 更新案を示して保留する |

- 新しい監査結果を受理したら、所見の文章が同じでも、次回の比較に使う SHA と確認済みの報告確定日時を記録する。今回の報告確定日時が不明なら、今回の区画では `completed-at` を省く。
- 更新する場合は最初の `fingerprint` と登録済みの別名を保持し、今回の値が未登録なら別名として一度だけ追加する。

## 5. 個別 Issue を作成・更新する

### タイトルと本文を書く

- タイトルは `[critical] 問題を具体的に表すタイトル` の形式にする。接頭辞には、独立検証済みの `severity.impact.score` の値をそのまま使う。値は `critical`・`high`・`medium`・`low`・`informational` の5段階とする。成立条件と到達可能性は本文に記載する。
- Cloudflare の成果物では公式の深刻度を使う。Issue 本文にタイトルの影響評価と公式の総合深刻度（`severity.overall_severity`）を併記し、検証済みの根拠を示す。
- [個別 Issue の書式](issue-templates.md#個別-issue) に従い、対象機能の前提、守るべきルール、誰が何をできてしまうか、根本原因、コード上の根拠、修正方針、修正完了条件を書く。Mermaid 図で正常な経路と問題の経路を示し、図の内容を文章でも説明する。
- コードへのリンクは、監査対象 SHA に実在するパス・行を確認し、その SHA で固定する。GitHub で参照できない箇所はパスと行を示す。集約 Issue も含め、秘密・実データ・攻撃ペイロード・詳しい再現手順・監査成果物の全文は掲載しない。

### 書き込みと結果を確かめる

- 書き込む前に、新規作成なら既存 Issue を全ページ取得し直して重複を判定する。更新なら `gh issue view "$NUMBER" --repo "$ISSUE_REPO" --json number,url,state,title,body,labels` で最新状態を取得し、手順 3 と 4 の判定をやり直す。
- 更新は、監査用区画を一意に特定でき、人が追記した本文を保てる場合に行う。区画外の本文・担当者・既存ラベルを保持する。今回の所見を受理できた場合は、タイトルの先頭にある深刻度だけを今回の影響評価に合わせ、残りの文言を保持する。先頭に深刻度がなければ付ける。別名だけを追加する場合はその行だけを追記し、タイトルを保持する。区画や追記箇所が不明なら更新案を集約 Issue に記録して保留する。
- 本文を端末のファイルに書く。作成・更新の直前に手順 2 と同じ `gh repo view` で登録先の条件を再確認し、条件を満たせば該当するコマンドを実行する。既存本文と差分がなければ本文の更新を省く。

  ```bash
  gh issue create --repo "$ISSUE_REPO" --title "$TITLE" --body-file "$BODY_FILE"
  gh issue edit "$NUMBER" --repo "$ISSUE_REPO" --body-file "$BODY_FILE"
  ```

- タイトルに差分がある場合だけ、更新コマンドに `--title "$TITLE"` を付ける。タイトルだけを変更する場合は `gh issue edit "$NUMBER" --repo "$ISSUE_REPO" --title "$TITLE"` を使う。
- 作成・更新後は `gh issue view` で URL・状態・本文・タイトルを確かめ、fingerprint ごとの反映結果を `issue_sync` に保存する。成否が不明なら、再試行前に全ページの一覧と対象 Issue を読み直す。既存 Issue の編集権限がなければ、その URL と更新案を集約 Issue に記録して保留する。今回の監査に載らなかった Issue の状態はそのままにする。

### 自動修正できるか確かめる

今回作成した個別 Issue と、反映対象と確定した開いている個別 Issue を判定する。反映後の本文と採用済みの所見を使い、別名だけを追加した場合は既存の所見を使う。リポジトリの関係者や Issue の作成者のコメントも確認する。次をすべて満たす場合は `agent:autofix` の対象とする。

- 修正する箇所・守るべき仕様・修正完了条件が明確で、実装方法を既存の規約の範囲で選べる。
- PR のベースブランチでも所見と修正方針が当てはまることを確認できる。ベースの指定がなければ、手順 2 の `defaultBranchRef` で確認した既定ブランチを使う。
- 回帰テストや既存のチェックなど、開発環境で修正完了条件を確かめる方法がある。
- 修正・検証・PR 作成までに、仕様の選択、未決の権限や互換性の判断、本番操作や人の追加承認が要らない。

判断に必要な情報が足りない場合は、不足している情報を集約 Issue に記録する。すでに `agent:autofix` が付いている Issue に人の判断が必要と分かった場合は、ラベルを保持したうえで、理由と URL を集約 Issue に記録する。

## 6. 集約 Issue に反映する

### 日付と実行を識別する

- タイトルは `[yyyy-mm-dd] セキュリティ監査の調査・判定一覧` とする。確認済みの `report_finalized_at` を日付の根拠にし、不明な場合や報告書を保存できなかった場合は、集約する内容を最初に確定した実際の日時を使う。
- 根拠の日時を保存済みの `timezone` に変換し、日付を `issue_sync.summary_date`、オフセット付き日時を `issue_sync.summary_date_at`、出所を `issue_sync.summary_date_source` に保存して本文にも記載する。変換には `Intl.DateTimeFormat` の `timeZone` などでゾーンを明示する。タイムゾーンを確認できなければ集約の反映を保留し、取得を再開条件にする。
- 一度保存した日付と `audit_id` を同じ実行の再開・再試行でも使う。開閉を問わず全ページ取得した Issue 本文の `security-audit:summary-id=<audit_id>` を完全一致で照合する。保存済みの URL も同じマーカーで確認する。同じ日付の別実行は別の集約 Issue にする。
- 一致が0件なら作成し、1件で開いていれば更新する。閉じている場合や複数一致する場合は、URL と理由を手元の成果物と最終報告に残して集約 Issue の反映を保留する。

### 全判定と反映結果をまとめる

- 確定0件や監査未完了でも、[集約 Issue の書式](issue-templates.md#集約-issue) で1件まとめる。冒頭に監査対象 SHA、プロファイル、範囲、監査と Issue 反映の状況、4区分の件数、未完了工程と再開条件を書く。件数は根本原因・fingerprint の重複を除いて数え、不明な値は不明とする。
- 4区分と未完了の工程・範囲は一覧表と項目ごとの詳細に書き、列・箇条・番号・並び順は書式に従う。
- 確定には今回作成・更新・照合した個別 Issue を載せる。再発候補や照合が曖昧なものは、候補の URL と保留理由を書く。
- 要検証は `blockers` と `validation_plan`、棄却は `reason` をもとに書き、棄却には判断を覆す新しい事実の条件を示す。
- 同じ実行の再開で候補が確定した場合は、番号を変えずに確定の区分へ移し、個別 Issue にリンクする。人が記載した判断や追記は保持する。
- 書き込む本文を組み立てたら、各番号が一覧表と `<summary>` に1回ずつ出ること、冒頭と見出しの件数・一覧表の行数・詳細の数が一致すること（件数が不明の区分は一覧表の行数と詳細の数。未完了の工程・範囲は見出しの件数と行数・詳細の数）、`<details>` と `</details>` の数が一致することを確かめる。
- 書き込む本文全体（更新では区画外の人の追記を含む）の文字数を `node -e 'console.log([...require("fs").readFileSync(process.argv[1],"utf8")].length)' "$BODY_FILE"` で測る。60,000 を超える場合は、詳細を削らずに全文の更新案を手元に保存して集約 Issue の反映を保留し、理由を最終報告に残す。

### 再開時も同じ Issue を更新する

- 書き込み予定の集約本文と `issue_sync.summary_revision` を端末に保存する。初回は1とし、内容を変えるたびに増やす。本文の `security-audit:summary-revision` に同じ値を記録する。書き込み結果が不明な場合は、保存した本文と版番号を使って GitHub の状態を照合する。
- 作成直前は全ページの一覧を取り直し、`summary-id` の重複を再確認する。更新直前は最新の本文・タイトル・状態を `gh issue view` で取得する。既存の版が今回より新しい場合、または同じ版で予定した監査用区画と内容が異なる場合は、URL と理由を手元に残して保留する。
- 更新は `security-audit:summary-begin` と `security-audit:summary-end` の間を一意に特定でき、人の追記を保持できる場合に行う。監査用区画外の本文・担当者・既存ラベルを保持し、タイトルを保存済みの日付の書式に合わせる。区画を特定できない場合は更新案を手元に残して保留する。
- 手順 2 の登録先条件を再確認し、手順 5 と同じ `gh issue create` / `gh issue edit` と `--body-file` を使う。本文とタイトルに差分がなければ書き込みを省く。反映後に取得し直してリンクと一覧表・詳細を確かめ、集約 Issue の URL をメタデータに保存する。成否が不明なら再取得して照合してから再試行する。
- 同じ実行の再開では、その実行の最新の台帳・最終版の所見を使う。別の実行の集約 Issue は履歴として残し、次の監査では根本原因の個別 Issue と過去の判定を参照する。

## 7. ラベルと反映状況を記録する

- 個別 Issue と集約 Issue に `agent:security-audit` を付ける。`agent:autofix` は手順 5 の条件を満たす個別 Issue に付ける。未付与のラベルごとに `LABEL` をその名前に設定する。登録先のラベルを全ページ取得し、`name` が `LABEL` と完全一致する項目があるか確認する。

  ```bash
  gh api --hostname "$REPO_HOST" --paginate --slurp "repos/$REPO/labels?per_page=100"
  ```

- 一覧を最後まで取得でき、ラベルがなければ `gh label create "$LABEL" --repo "$ISSUE_REPO"` で作成する。作成に失敗した場合は一覧を読み直す。別の担当者が作成済みと分かれば、そのラベルを使う。
- `agent:autofix` を付ける直前に、Issue の状態・本文とコメント全ページを読み直す。開いており、最新の本文とコメントでも自動修正の条件を満たす場合だけ付ける。コメントは `gh api --hostname "$REPO_HOST" --paginate --slurp "repos/$REPO/issues/$NUMBER/comments?per_page=100"` で取得する。
- ラベルの存在を確認できたら、`gh issue edit "$NUMBER" --repo "$ISSUE_REPO" --add-label "$LABEL"` で付ける。本文とラベルの両方に差分がなければ書き込まない。ラベルの確認・作成・付与を完了できなければ、対象 Issue の URL・ラベル名・理由を報告する。
- 個別 Issue とラベルの結果を確かめ、集約 Issue 自身のラベル付与も確認してから `issue_sync.status` を確定する。すべて反映できれば `complete`、一部に保留や失敗があれば `partial`、登録先や権限などの前提を満たせず書き込めなければ `blocked` とする。監査の `run_status` は監査工程の完了状況を表す。
- 確定した反映状況とラベルの結果を、書式に従って集約 Issue（冒頭の Issue 反映の状況、確定の一覧表の反映結果・詳細、どの確定項目にも属さない保留を書く未完了の工程・範囲）に書き戻す。差分があれば手順 6 に従って版を増やして保存・反映・再取得する。この最終更新に失敗した場合は `issue_sync.status` を `partial` にし、保存済みの更新案と停止理由を最終報告に残す。
- 集約 Issue への反映も保留になった場合は、反映予定の本文と理由を実行フォルダに保存し、保存済み成果物の絶対パス・該当 Issue の URL・再開条件を最終報告に残す。
