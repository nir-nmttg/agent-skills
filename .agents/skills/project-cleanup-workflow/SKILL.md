# 整備スキルを組み合わせてプロジェクト全体を整える

トークンや時間に余裕があるときに、気になっている箇所を個別に挙げなくてもプロジェクト全体を一巡して整える。改善の効果を基準に実装・検証し、変更不要の工程はそのまま終える。変更件数やトークン消費量を目標にしない。

## 共通の探索と準備を行う

- リポジトリの指示、既存の差分、README、設計文書、ディレクトリ・パッケージ構成、実行設定と CI を読み、設計の根拠と検証方法を把握する。範囲指定がなければ、プロジェクト全体の自前のコード・テスト・利用／開発／運用文書を対象にする。生成物・依存パッケージ・外部から取り込んだコードは除外する。
- このスキルの実体からの相対パスで、下表の各 `SKILL.md` を工程に入る前に読む。この呼び出しの中で各スキルの手順を適用し、個別の再呼び出しや追加の承認待ちを挟まない。前提が不明なら [skills-preflight](../skills-preflight/SKILL.md) の読み取り専用の手順で確認する。確認済みの情報は再利用する。
- 各領域の入口、主要経路、設計上の制約、関連テスト、探索済み・未探索の範囲をまとめ、後続の工程へ引き継ぐ。各スキルで全体探索を最初から繰り返さず、変更されたコードと新しく影響する依存先は読み直す。ファイル一覧の取得だけで探索完了とはしない。
- 変更前の関連チェックを実行し、成功・既存の失敗・実行不能を区別する。未コミット変更を保ち、自分の変更と区別して扱う。
- 対象・優先領域・時間やトークンの上限が指定されていれば計画に反映し、検証・修復・報告の余力を残す。指定がなければ全工程を一巡する。残量を推測して作業量を決めず、制約内で終えられない範囲は未完了として明記する。

## 次の順番で整備する

| 順序 | スキル | この工程の役割 |
| --- | --- | --- |
| 1 | [design-alignment-refactor](../design-alignment-refactor/SKILL.md) | 現在の設計方針を根拠に逸脱を修正し、後続が守る責務の境界や依存方向を明確にする。 |
| 2 | [code-structure-refactor](../code-structure-refactor/SKILL.md) | その方針を保ちながら、責務の混在・重複・過剰な分割を整理する。前工程で解消した候補を別案へ作り直さない。 |
| 3 | [test-suite-refactor](../test-suite-refactor/SKILL.md) | 本体の構造が落ち着いてから、検出力を保ってテストの重複や実装の細部への依存を整理する。前工程の確認に必要なテストは先に削減しない。 |
| 4 | [code-order-refactor](../code-order-refactor/SKILL.md) | 本体・テストの抽出や統合を終えた状態で、ファイル内の宣言を読みやすい順に整える。 |
| 5 | [docs-align-with-code](../docs-align-with-code/SKILL.md) | 最終的な実装に利用・開発・運用の説明と導線を合わせる。設計方針を実装に合わせて書き換え、保留した逸脱を解消した扱いにしない。 |

- 順序と採用理由を簡潔に伝えてから進める。各工程に共通の対象範囲を引き継ぎ、直近の差分だけで探索を終えない。各スキルの判断基準を使い、効果のある候補を順に実装・検証する。
- 構造変更に必要なテスト・文書・参照先の更新は、その変更と一緒に行う。後の専用工程は、プロジェクト全体の残る改善を扱う。
- 工程ごとに変更と影響範囲の検証結果を確かめる。同じ状態・条件で成功済みの検証結果は共有し、影響するコードや設定が変わったら再実行する。
- 判断が必要な契約変更は保留し、独立した改善を進める。新たな検証失敗はまず自分の変更を修復し、解消できなければ該当する自分の変更だけを戻す。失敗した変更に依存する後続作業は保留する。既存失敗と実行不能を、新しい不具合と混同しない。
- 必要なスキルが読めない工程は、手順を推測して代替しない。不足と影響を記録し、独立して実行できる工程は進める。完了・変更不要・保留・未着手を区別する。

## 最終状態を検証して報告する

- 最終状態について、各変更の影響範囲とリポジトリで必須のテスト・型チェック・lint・ビルド・文書検証を確認する。差分を読み、振る舞い、設計の根拠、テストの検出力、宣言順の制約、文書との整合が保たれているかを見る。実行できなかった検証を成功扱いにしない。
- 同じ判断基準で見直し、前工程の改善を後工程で打ち消していないか、既に整った箇所に別案を持ち込んでいないかを確かめる。変更を作るために全工程を繰り返さず、追加対応は見つかった具体的な問題に絞る。
- 日本語で簡潔に、探索範囲、各工程の結果と主な改善理由、実行した検証と結果、保留・未探索・未検証の範囲をまとめる。予算などで中断した場合は再開箇所も示し、全体完了とは報告しない。すべて変更不要でも、確認した範囲と根拠を伝える。
