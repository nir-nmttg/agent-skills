# Codex スキルを使う準備の確認

このリポジトリの `.agents/skills/` を対象に、実際の前提を確認する。Claude 側と同様に、確認だけを行い、インストール・ログイン・リンクの変更は別途依頼された場合に行う。

## 基本環境を確認する

1. このスキルからの相対パス `scripts/check.sh` を `bash` で実行する。対象プロジェクトの作業ディレクトリは変えず、スキルの実際の配置を基準にスクリプトのパスを解決する。
2. 出力にある各スキルの `SKILL.md` と、存在する `agents/openai.yaml` を読む。定義の存在と利用可能を区別し、フォルダ名と `name`、参照する補助ファイル、呼び出し設定、必要なコマンド・外部スキル・認証を確認する。スクリプトはファイルの存在・読み取りとリンクを確認するもので、YAML の構文や個別の依存関係は検証しない。
3. 実際に使うコマンドや認証だけを、存在確認・バージョン表示・ログイン状態の取得など読み取り専用の方法で確かめる。現在の Codex スキルには、Codex CLI・Claude CLI・GitHub CLI とそのログインを一律に要求しない。将来追加されたスキルは、その定義に基づいて確認項目を補う。

## 対象プロジェクトの前提を確認する

- 対象が指定されていればその場所、なければ現在のプロジェクトの指示、README、実行設定、CI から、利用するスキルに必要なランタイム・パッケージ管理・テストや文書検証の手段を確認する。対象が決まっていなければプロジェクト固有の前提は未確認とする。
- `docs-align-with-code` は対象文書と実装の参照、および既存の文書検証手段、`design-alignment-refactor`・`code-structure-refactor`・`code-order-refactor` は対象コードと影響範囲の検証環境、`test-suite-refactor` は対象テスト・実装・テスト実行環境を確認する。コマンドが見つかるだけで、依存パッケージやサービスまで準備済みと判定しない。
- `codebase-cleanup-workflow` は組み合わせる5つの整備スキルの定義を参照でき、各スキルの前提が満たされているか確認する。一部だけ実行可能なら、全体を利用可能とせず条件付きとして不足する工程を示す。
- `minor-version-upgrade`・`major-version-upgrade` は Ruby・Node（JavaScript / TypeScript）・Python のランタイムと依存を対象にする。`.ruby-version`・`Gemfile`・`Gemfile.lock`、Node の版指定・`package.json`・`packageManager`・lockfile、`.python-version`・`pyproject.toml`・`uv.lock`・`poetry.lock`・requirements / constraints など、存在する設定と CI を静的に読み、採用中の Ruby / Bundler、Node / npm・pnpm・Yarn、Python / uv・pip・Poetry などの管理方式・更新対象を一覧化する。必要なのは採用されたツールだけで、すべての導入や別ツールへの変更を求めない。lockfile がない場合も、採用方式で全解決版・取得元・digest を固定・再照合する手段を確認する。
- Rails・Node のフロントエンド・Python worker など3言語の混在を見落とさず、言語間の連携を含む検証手順があるか確認する。その他の言語の構成は影響・依存境界だけ記録し、更新範囲を広げない。Ruby・Python の `X.Y` ブランチ変更や機能リリース、Node の major 更新を個別移行として区別し、Node の同一 major 内の minor / patch、Ruby・Python の同一 `X.Y` 内の patch、各ライブラリの互換性は公式方針と実際の変更から確認できることを前提にする。ライブラリの `0.x` の minor 増加や非互換変更を番号だけで一括更新に含めない。グローバル環境は依頼範囲に含まれるものだけを対象にする。
- 更新スキルのランタイム・依存管理の存在・バージョンは、未確認のプロジェクトコードやラッパーを動かさない読み取り専用の方法で確かめる。公式レジストリ・配布元・リリース情報・セキュリティ情報へアクセスできるか、採用中の各系統の既存のテスト・型チェック・lint・ビルドと実行検証の手順・依存サービスがあるかを確認する。認証済み設定の秘密値やトークンは表示しない。
- 両更新スキルの `references/isolation.md` と `scripts/docker-sandbox.py` を読み、利用可能なローカル Docker CLI・daemon/context、公認の digest 固定 image と必要な toolchain を確認する。同梱処理で設定・executor を自動生成し probe できる前提があるかを、読み取り専用で調べる。条件を満たす既存のコンテナ・VM・OS sandbox も選べる。Docker の未導入・未起動・通信・toolchain 不足など、確認できた不足と再開条件を報告し、既存 executor のパスを一律に要求しない。Docker 本体導入・daemon 起動、`sudo`・root 実行・socket の権限変更などのホスト設定変更は自動準備の対象外である。信頼済み CLI の読み取り専用の接続確認には、両更新スキルの `references/isolation.md` に従う Codex の正規の実行承認を利用できる。通常実行での接続拒否だけで未起動や利用不可と断定せず、承認不可・承認後の結果を区別する。事前確認では承認されても `prepare`・probe・worker を起動しない。
- 両更新スキルの `references/gate.md` と `scripts/supply-chain.py`・`archive_inspector.py`・`audit_report.py` を読む。`bash` と、プロジェクト外の信頼済みPython 3.9以降の実体を利用でき、絶対パス・`-I -S` で標準ライブラリだけを使ってゲートを起動できるか確認する。対象のvenv・shim・PYTHONPATH・site由来コードをゲートの起動へ持ち込まない。対象が Ruby / Node だけでもゲート用の Python は必要だが、すべての言語や依存管理ツールの導入を要求しない。取得物・全依存 inventory と npm audit v2 / pip-audit / bundler-audit の対応する JSON を準備でき、監査範囲・DB 鮮度・公式告知を確認できるか調べる。監査は隔離内、または `references/isolation.md` の対象コードを実行しない監査専用プロセスの条件を満たして行い、無加工 JSON・実測時刻と終了コード・ツール版・送信先の根拠を記録できるか確認する。コード評価の有無が不明なら通信を制限する隔離が必要である。エラー・skip・未対応形式・finding・期限切れ・coverage 不足を停止条件として扱えることを確認する。
- ゲートの `coverage`・`sources`・`artifacts`・`advisories`・`authenticity`・`isolation`・`compatibility` が `unknown` から始まり、非空の証拠・SHA256・時刻・計画 fingerprint に結びつく手順を読めるか確認する。証拠・監査の24時間の期限、候補版と各実配布物（image を含む）の最も新しい公開日時から7日以上という下限、日時不明・未来の日時も停止する条件を確認する。署名の信頼・出所・配布物差分・DB 鮮度・OS 隔離は、機械検査で自動承認せず根拠付きの手動レビューが必要である。
- 更新後 inventory の全ライブラリ・ビルド依存を監査でき、ランタイムだけの変更でも既存依存を省略しないことを確認する。更新後がランタイムだけの場合に限り package 監査 JSON を不要とし、公式告知は確認する。pip-audit の全 package 名・版の照合と、npm/bundler の全範囲の手動 coverage レビューを行えるか確認する。
- 更新スキルは `schema_version: 2` の計画で、自動準備・レビューした executor または検証済み既存隔離の実体・設定・token を使う argv と全入力を固定する。自動準備時の `sandbox/execution.json` を `plan.execution` へ統合し、worker 等の候補外入力を `execution.inputs` に列挙でき、image 等を immutable digest に固定できるか確認する。最終 worker が `run` の読み取り専用 snapshot を scratch へコピーし、導入・実版/全グラフ/digest の照合・必須チェック・CLI/consumer 等の実操作・証拠保存まで一度で完了し、失敗を終了コードへ伝えられるか確認する。同梱環境は終了時に消えるため、以後は結果を読み、検証済みの許可差分だけを反映する。追加検証・修正・部分除外は新しい `RUN` と計画で全レビュー・導入・検証をやり直す。元の候補や未固定のホスト入力を実行に使わず、`RUN` 全体を executor に渡さない。証拠変更・期限切れ・既存 `pass` の別証拠への置換や `fail` の復活も同じ `RUN` で再承認しない。ゲート自体は OS 境界ではなく、準備や probe の成功も供給網レビューの自動承認ではない。同じ UID の意図的な偽造や直接コマンドまで禁止するものでもない。
- 調査用 scratch の候補解決、固定した更新前グラフの基準環境再現・テストに、別々の worker・入力・出力を用意できるか確認する。基準用は旧版の出所・digest を固定し、現在の実ランタイム・全グラフを照合してから測り、対象へ反映しない。ランタイム更新で旧版と採用版の image が異なる場合は、別の `RUN` で準備する。コード評価がある操作は `init` 前から同じ隔離条件が必要で、同梱 sandbox の外部通信は禁止する。コード評価と通信の両方が必要な取得には条件を満たす既存隔離を確認する。DB・ブラウザ・ネイティブ操作が必要なら、`init` 前に導入済み環境を実操作完了まで維持して一度の `run` で全工程を完遂できる既存 executor を確認する。なければ該当工程を条件付きとし、検証・適用の保留と再開条件を報告する。
- `references/isolation.md` の保存・反映契約に従い、候補編集前の全適用予定パスの有無・hash・実行 bit を親側に記録でき、元プロジェクトから最後に検証した scratch までの追加・変更・削除・rename を patch または変更 manifest と最終内容へ保存できるか確認する。保存時の `0600` を反映先へ流用せず、適用直前の全件照合・既存権限の保持・適用後の hash/実行 bit/削除の照合を行えるか確認する。
- 更新スキルで Web 画面を持つ対象は、組み込みブラウザ（IAB）のツールが利用でき、ローカル環境へ接続して実操作を検証できる前提があるか確認する。CLI・ライブラリ・ネイティブアプリなどブラウザが適用されない対象は、その理由と対象に合った実行検証の手段を確認する。ブラウザ利用不可を画面検証済みと扱わず、ネットワーク・隔離環境・テストなど必須の前提が不足する場合も条件付きとして、不足する工程と対処を示す。更新本体、`scripts/new-run.sh`、`docker-sandbox.py prepare`、ゲートの `init`・`review`・`check`・`run` は実行せず、ファイルと設定を読んだ範囲を報告する。
- 事前確認のために本体のスキル、テスト一式、ビルド、任意のセットアップスクリプトを実行しない。実行権限、ネットワーク、外部サービスなどで確認できない項目は、未導入・未ログインと断定せず未確認として残す。認証情報や設定ファイルの秘密値は表示しない。
- image 供給のランタイム更新は、`runtime_image`・inventory の取得元・container の実行設定が同じ固定 image を指す手順と、準備時・最終 worker の正確な版の照合方法を確認する。native 拡張が必要なら headers・compiler・build tool を含む image と、固定ソースの再ビルド・ロード検証が可能か確認する。同版の ABI 別配布物でも実際の `source` 変更を記録し、差分・hash・公開日・出所・監査・互換性の全レビューが必要であり、ネイティブアプリの OS 操作とは区別する。事前確認では image 取得・build・更新は実行しない。

## 結果を報告する

- 日本語で、スキルごとの「使える・条件付き・使えない・未確認」、根拠、不足と対処を表で示す。`skills-preflight` 自身は基本チェックが実行できれば使えると判断できる。他のスキルも、必須の前提を確かめた範囲で判断する。
- リンクは他のフォルダから使うための任意項目として扱う。同名の別ファイル・別の場所への有効なリンクは置き換えず、その状態を報告する。リンクの対処には、このリポジトリの `scripts/link-skills.sh --codex` を案内する。worktree ではメインの checkout から実行する必要がある。
- 不足への対処は対象の OS・プロジェクトで採用された方法に合わせて案内する。確認した範囲と未確認の前提を明記し、基本チェックだけで全スキルの実行成功を保証しない。
