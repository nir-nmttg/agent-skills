# Ruby・Node・Pythonを一件ずつ移行する

Ruby・Node（JavaScript／TypeScript）・Pythonのランタイムと依存の非互換更新を、一件ずつ必要な移行とともに進める。

標準は静的確認を通った更新差分を反映して完了する。Docker・導入環境・テスト・ブラウザ操作を利用できないことだけでは保留しない。静的確認済みと動作確認済みを区別し、未実施の検証を成功扱いにしない。

ユーザーが「厳格モード」「全工程検証を必須」「未検証なら反映しない」などと明示した場合だけ [厳格モード](references/strict.md) を使う。通常の更新を勝手に厳格モードへ変更しない。組織・対象プロジェクトの必須条件は守る。

## 対象と一件の境界を決める

1. 対象の指示、未コミット差分、README、CI、manifest・ビルド定義・既存 lockfile、環境の版指定を静的に読む。採用中の Ruby/Bundler、npm/pnpm/Yarn、uv/pip/Poetry 等を [管理系統の見分け方](references/ecosystems.md) で確認し、管理方式を勝手に変えない。未知のラッパーやプロジェクトコードを版確認のために実行しない。
2. 範囲指定がなければ3言語のランタイムと全依存を系統別に一覧化し、依存順・サポート終了・脆弱性・移行コストから順序を決める。他言語は影響と依存境界を記録し、グローバル環境・OS・管理ツール本体は依頼範囲だけ扱う。
3. 通常は一つの直接依存、間接依存の導入元、または一つのランタイムを一件とする。不可分の peer/plugin・ビルド依存・公式に版を揃えるセットは理由と全構成を記録する。無関係な major を混ぜない。Ruby/Python の `X.Y` 系列変更、Node の major、ライブラリの major・`0.x` minor・破壊的変更を公式方針で分類する。
4. 一件ごとに現在 → 目標の正確な版、破壊的変更と利用箇所、必要な API・設定・データ形式の移行、戻し方を記録する。複数 major を飛び越すなら中間版の移行ガイドも読み、公式の段階的移行に従う。移行経路や必須の仕様判断が未解決ならその対象を保留する。
5. 一件ごとにスキル実体から `bash scripts/new-run.sh <project-slug>` を実行する。`RUN/report.md` に元の差分、関連セット、根拠 URL と取得日時、結果を記録し、候補編集前に [保存・反映契約](references/isolation.md#6-検証した差分を保存して対象へ反映する) の全許可パスと初期状態を記録する。秘密・実データは保存しない。

## 一件ずつ静的に確認する

1. 実行時の公式レジストリ、リリースノート、移行ガイド、サポート方針、セキュリティ告知から、正確な安定版と取得元を確認する。`latest` だけで選ばず、撤回・非推奨・既知の悪性版、対象環境で非対応の版を除く。判明した版・配布物の公開日を記録する。標準では公開後7日の待機を必須にせず、厳格モードの条件と混同しない。
2. 更新前後の全依存 inventory を照合する。直接・間接・dev・build・optional・workspace・CI の依存を含め、全変更版の配布物・取得元・hash・追加削除・install/build script、peer/plugin・ランタイム要求・native ABI を確認する。[供給網の確認](references/verification.md) と [管理系統ごとの注意点](references/ecosystems.md) に従い、配布物は実行せず検査する。ランタイム更新でも残る既存依存の脆弱性確認を省略しない。
3. ゲートの初期化前に、manifest・既存 lockfile 相当・ランタイム指定・必要な CI 設定と移行ソースを候補コピーで完成させる。既存の管理方式と pin 方針を保ち、lockfile を推測で作らない。その後 `schema_version: 2` の `RUN/plan.json` に `"verification_mode": "static"` を明示する。候補コピー、全依存 inventory、取得物・根拠を固定し、`execution` は指定しない。既存の厳格用計画を流用しない。起動には [実行ゲート](references/gate.md) の信頼済み Python 実体・絶対パスのゲート・`-I -S` を使う。
4. `init` の後、`coverage`・`sources`・`artifacts`・`advisories`・`authenticity`・`compatibility` の6項目を、非空の実際の根拠と説明を付けて `review` し、`check` を通す。静的確認のために `isolation` を `pass` にしない。監査 JSON がある場合はエラー・finding・coverage 不足を無視せず、JSON のない場合の公式告知による全依存確認はゲートの条件に従う。署名等の未提供は独立した代替根拠と限界を記録し、不明を確認済みと偽らない。
5. 取得元・hash の不一致、採用を妨げる既知の脆弱性・悪性告知、明確な非互換、未解決の依存制約や必須移行の漏れは修正するか、その対象を保留する。根拠・候補・計画の変更、失敗や期限切れはゲートに従って新しい `RUN` に分ける。

同版の ABI 別 wheel 等への切替も、実際の `source` と hash の変更を記録し、一件の移行として互換性・差分・出所を確認する。関連セット以外の変更は最小範囲に絞り、別の独立した major は後の一件に回す。

## 一件の更新差分を反映する

- 事前準備した manifest・lockfile 相当・ランタイム指定・設定・移行ソースが静的ゲートに固定した内容と一致することを確認する。初期化後に差分を追加・修正するなら、既存の承認を使わず新しい `RUN` で静的確認をやり直す。lockfile を削除して全再解決したり、正しさを確認できない固定記録を捏造したりしない。
- lockfile 生成・依存解決・code mod・ビルド定義等がコードを評価する場合は、標準でも [隔離条件](references/isolation.md) を適用する。静的確認の成功はホストで対象・依存コードを動かす許可ではない。必要な実行環境を用意できず正しい更新差分を作れない対象は保留し、独立して反映できる対象を進める。
- `"$UPGRADE_PYTHON" -I -S "$UPGRADE_GATE" run --run "$RUN"` を実行する。静的計画の `run` はコードを起動せず、確認した候補の反映用 snapshot と静的結果を保存する。これは依存のインストールやテストの成功を意味しない。
- 保存した結果を読み、[保存・反映契約](references/isolation.md#6-検証した差分を保存して対象へ反映する) に従う。全反映予定パスの元の有無・hash・実行 bit を再照合し、ユーザー変更との競合がなければ許可した追加・変更・削除・rename だけを反映する。保存時の mode を流用せず、適用後の hash・実行 bit・削除を照合する。秘密・依存ディレクトリ・cache は持ち込まない。
- `git diff --check` と最終差分、manifest/lockfile/版指定の整合を確認する。静的条件を満たす正しい更新差分を反映したら、標準モードの更新は完了とする。テストや実操作の未実施だけを理由に未完へ戻さない。

静的に確認して反映した一件の採用版と全依存グラフを、次の一件の更新前状態にする。新しい一件には新しい `RUN` と計画を使い、完了済みの更新やユーザー変更を戻さない。保留対象に依存する後続候補は保留し、独立した候補を進める。静的確認の完了後、任意の実行検証を利用できないことだけで次の一件を止めない。

## 可能な場合に追加検証する

- CI と既存手順から、変更に関係するテスト・型チェック・lint・ビルド・対象別の実操作を選ぶ。静的 `run` 後の承認済み snapshot と固定配布物から、別の検証用 `RUN` に準備したレビュー済み executor で実行する。境界・worker・設定を事前確認し、[実行ゲート](references/gate.md)・[隔離手順](references/isolation.md) に従う。標準の静的計画へ `execution` を足したり、厳格モードへ自動変更したりしない。
- 利用できないチェックは対象と理由を記録する。既存失敗、環境の不足、更新による新しい失敗を区別する。更新由来の失敗は修正する。反映後にソースだけを直す場合も、[再確認手順](references/isolation.md#反映後に修正が必要になった場合)で当該更新分だけを安全に取り下げ、実際の更新前グラフから修正済み候補を新しい `RUN` で6項目の静的確認にかける。解消できない対象は自分の反映分だけ安全に取り下げて保留し、ユーザー変更や独立した完了済み更新を戻さない。その対象に依存する後続の更新も見直す。テストを削除したり、実際の失敗を「未実施」に書き換えたりしない。
- ランタイムの系列変更・native 拡張は、実版・対象 ABI・再ビルド・ロードを実測した範囲だけ動作確認済みとする。Web は組み込みブラウザ、その他は利用形態に合う操作を選ぶ。必要な導入は検証コンテナ内に留め、依存をホストへ持ち出さない。検証結果にソース・lockfile の修正があれば、上記の再確認手順に従い、元の静的承認を再利用しない。
- 本番データの変換や実サービスへの書込みは別途依頼がある場合だけ行う。

全体の組合せに追加変更があれば、その差分の静的確認と記録を更新する。最後の確認から内容が変わっていなければ同じ検証を繰り返さない。未完の移行ソースを積み上げたまま次へ進めない。

## 結果を報告する

日本語で、採用した版と差分、静的ゲートの結果と根拠、保留対象と理由、追加検証の成功・失敗・未実施と理由、残る制約、元に戻す方法、`report.md` のパスを簡潔に伝える。標準の完了は「更新を反映済み・静的確認済み・実行テスト未実施」などと明示し、「動作確認済み」「全検証成功」と混同しない。疑わしい兆候を確認しなかった範囲と未確認の範囲を示し、供給網の無害を保証しない。自分の一時プロセスは終了する。コミット・push・PR・公開は別途依頼があるときに行う。
