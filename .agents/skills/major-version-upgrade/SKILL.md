# Ruby・Node・Pythonを一件ずつ移行する

Ruby・Node（JavaScript／TypeScript）・Pythonのランタイムと依存ライブラリの移行を、対象の選定 → 供給網確認 → 移行 → テスト → 対象別の実操作の順に一件ずつ完結させる。番号上は minor でも個別移行が必要な更新を含む。監査や動作確認から、攻撃が含まれないと断定することはできない。

Python 3.9 以降の標準ライブラリで動く [実行ゲート](references/gate.md) を一件ごとに必須にする。最終採用候補の導入・更新は、根拠付きの固定7項目と機械検査を通った計画を `scripts/supply-chain.py run` から一度だけ実行する。調査用 scratch での解決と固定した更新前グラフの基準環境再現は [準備手順](references/isolation.md#4-準備段階と対応できない工程) に従い、対象へ反映しない。`check` 後の任意コマンドや skip・force で代用しない。

## 対象と現在の状態を調べる

1. 対象の指示、未コミット差分、README、CI、manifest・ビルド定義・存在する lockfile、環境の版指定を静的に読む。[管理系統の見分け方と注意点](references/ecosystems.md) から該当する節を選び、Ruby・Node・Pythonのランタイムと採用中の依存管理ツールの版・管理方法を調べる。Bundler、npm／pnpm／Yarn、uv／pip／Poetry等のうち実際に使うものを確認し、管理方式を勝手に切り替えない。未知のラッパー・ビルド定義・プラグインは、版の確認のためにもいきなり実行しない。
2. 3言語の指定したランタイム・パッケージを対象にする。範囲指定がなければ混在する構成を系統ごとに一覧化し、依存順とサポート終了・脆弱性・移行コストから優先順位を決める。直接・間接・dev・build・optional 依存、workspace、CI のみの依存も探索し、未探索の系統・OS・アーキテクチャを記録する。他言語は影響・依存境界だけを記録し、更新対象へ広げない。グローバル・OS 全体・管理ツール本体は依頼された範囲だけ扱う。
3. このスキルの実体から、一件ごとに `bash scripts/new-run.sh <project-slug>` を実行し、出力先をその一件の `RUN` とする。`report.md` に候補一覧、実行順、元の差分、取得日時と根拠 URL、結果、保留と再開条件を記録し、`plan.json`・証拠・ゲート状態もここに保存する。候補編集前に [保存・反映契約](references/isolation.md#6-検証した差分を保存して対象へ反映する)に従い、全適用予定パスの元の有無・hash・実行 bit を親側に記録する。対象・候補用コピーから分離し、隔離 executor へ `RUN` 全体を渡さない。全体の報告から各一件の記録を参照する。スクリプトへのパスはスキルから解決し、秘密値・実データを保存しない。
4. CI のテスト・型チェック・lint・ビルドを選び、下記の隔離準備後に基準結果を取る。Web・CLI・ライブラリ・ネイティブアプリなど利用形態に合う操作と期待結果を変更点に対応づける。Web は必要なら変更前の画面も記録する。既存失敗と実行不能を新しい不具合と区別する。

## 一件の境界と移行先を決める

- 通常は一つの直接依存、間接依存の導入元、または一つのRuby・Node・Pythonランタイムを一件とする。その更新に不可欠な peer／plugin／ビルド依存・公式に版を揃える関連パッケージ・同梱ツールは、不可分なセットである理由と全構成を記録して同じ一件に含める。無関係の major や minor を混ぜない。
- Rubyの `X.Y` ブランチ変更、CPythonのfeature release、Nodeのmajor更新を個別に扱う。ライブラリは公式方針に従い、major増加・`0.x` のminor増加・破壊的なminor／patchも対象にする。RubyやPythonの版、PEP 440の表記を一律にSemVerと解釈しない。
- 最新情報は実行時の公式レジストリ、移行ガイド、リリースノート、セキュリティ告知、サポート方針で確認する。単に `latest` を選ばず、対象 OS・アーキテクチャ、Ruby・Node・Pythonの版、フレームワーク、native extension／addon、peer／ビルド依存を満たす正確な安定版を固定する。
- 複数 major を飛び越す場合は、中間版の移行ガイドも読み、公式推奨の段階的更新が必要なら一段ずつ検証する。次の major が既に EOL なら無条件にそこを採用せず、サポートされる版への公式な経路を検討する。経路不明なら保留する。
- 候補版と全実配布物（wheel・image 等）の最も新しい公開日時から **7日以上** が必須で、日時不明・未来の日時・7日未満はゲートが停止する。より厳しい組織方針は追加で守り、緊急修正でも短縮しない。日数は安全の証明ではない。prerelease・撤回・非推奨・既知の悪性版は通常の候補にしない。
- 一件ごとに、現在 → 目標の正確な版、関連セット、破壊的変更と呼び出し箇所、必要な設定・データ形式の移行、テスト、対象別の実操作、戻し方を記録してから進める。既存の依頼で範囲が明確なローカル移行は追加確認を挟まず進める。要件やデータ契約の判断が必要な部分は具体的な案まで用意し、独立した調査・検証を続ける。
- ABI 別 wheel 等の同版配布物への切替も、実際の `source` 変更として版上昇と分けて記録し、差分・hash・公開日・出所・監査・互換性を全件確認する。同版を安全や互換性の根拠にせず、一件の移行境界と互換性を精査する。

## 隔離環境を準備する

image が供給するランタイムの変更は、[計画の `runtime_image`](references/gate.md) に image 参照と ID を記録し、実行設定へ結びつける。正確な実版は準備時と最終 worker 内で照合する。native 拡張には対象版の headers・compiler・build tool を含む image を選び、固定したソースから再ビルドして実際にロード・テストする。

[隔離環境の準備](references/isolation.md) に従い、対象のランタイム・管理ツール・OS に合う公認 image を調査して digest を固定し、同梱の `scripts/docker-sandbox.py prepare` で既存 Docker 上の設定と executor を自動生成する。同梱コード・生成設定・worker と probe の結果をレビューする。条件を満たす既存のコンテナ・VM・OS sandbox も利用できる。Web・DB 等を含む検証は `init` 前に全工程を完遂できる既存 executor を選び、用意できなければ検証・適用を保留する。準備成功だけで供給網レビューを `pass` にしない。

Docker 本体の導入・daemon 起動、`sudo`・root 実行・socket の権限変更などのホスト設定変更はこの準備で行わない。信頼済みの同梱処理が既存 Docker へ接続するための [Codex の実行承認](references/isolation.md#docker-接続と-codex-の実行承認) は利用できる。通常実行の接続拒否だけで保留せず、正規の承認手続きで切り分ける。承認不可・未導入・未起動・通信・image のツール不足などで準備できなければ、確認結果と再開条件を報告する。既存 executor のパスを一律に尋ねず、静的調査と差分案を続ける。

## 一件ずつ次の工程を完了する

### 1. 供給網と全依存差分を確認する

- [供給網と実行・動作検証](references/verification.md)・[実行ゲート](references/gate.md) と、使う管理系統の [更新方法の注意点](references/ecosystems.md) を読む。レジストリ・配布物・脆弱性・実行箇所を確認する。マイナー更新と同じ証拠水準を保つ。
- manifest・ビルド定義・lockfile の静的確認と公式メタデータから仮候補を作る。準備・レビューした隔離で、秘密を除いた最小コピーと専用 cache を使う。基準用は現在のランタイムと固定した更新前グラフを再現して照合・テストし、候補解決用とは worker・入力・出力を分ける。公認元からの固定した取得物と、条件を満たす [監査専用の照会](references/isolation.md#5-対象コードを実行しない監査照会) は、対象コードを実行しない取得用プロセスで揃える。解決・メタデータ取得だけでもビルド定義・backend・hook・plugin を実行し得るため、コード評価がある操作には `init` 前から隔離を適用する。同梱 executor は外部通信を許可しない。コード評価と通信の両方が必要、またはコード評価を排除できるか不明なら、送信先を限定できる既存隔離を確認し、なければその工程を保留する。
- 更新前後の全依存 inventory と、全変更版の取得物・正確な版・公開日時・取得元・integrity/checksum・git ref・追加削除・install/build script、更新後の全ライブラリ・ビルド依存の監査 JSON を揃え、配布物差分を確認する。ランタイムだけの変更でも既存依存を監査する。関連セット以外の変更は必要性を説明できる最小範囲に絞り、別の独立した major は固定するか後の一件に回す。
- 公開元の連続性、署名・provenance、既知の脆弱性・悪性告知、疑わしいコード、監査 DB の鮮度と隔離境界を複数の根拠で確認する。監査ゼロ件、署名、provenance、利用者数だけで採用しない。署名が未提供なら独立した代替根拠と限界を記録する。不審・証拠不足ならこの一件を導入せず保留し、機械検査不能を自動で `pass` にしない。
- manifest・設定・移行ソースの静的な変更を候補コピーで準備する。`schema_version: 2` の `RUN/plan.json` に、準備・レビューした隔離 executor の実体・設定・argv 配列を固定する。自動準備時は `sandbox/execution.json` を `plan.execution` へ統合し、worker・include・補助 script 等の候補外ファイル入力を `execution.inputs` に列挙する。入力先はゲートの token で指定し、全入力の hash と、ファイルでない image 等の immutable digest を確認する。`init` で初期化し、`coverage`・`sources`・`artifacts`・`advisories`・`authenticity`・`isolation`・`compatibility` の7項目をすべて `unknown` から始める。実際の非空の証拠と説明を付けて `review` し、証拠の SHA256・時刻・計画 fingerprint を結びつける。
- `check` は全項目の有効な `pass` と機械検査が揃うまで停止する。証拠・監査は24時間で期限切れとなり、監査のエラー・skip・非対応・finding・coverage 不足も停止の根拠になる。候補・入力の変更、既存の証拠変更・期限切れ・既存 `pass` の別証拠への置換や `fail` からの復活は同じ `RUN` の再承認に使わず、別の実行記録で計画・全レビューをやり直す。

### 2. 固定した版へ移行する

- `"$UPGRADE_PYTHON" -I -S "$UPGRADE_GATE" run --run "$RUN"` で、この一件の計画だけを導入する。ゲートは承認済み入力を読み取り専用 snapshot にコピー・照合し、直前の時刻で証拠・監査も再検査する。executor は token を解決した snapshot を受け取り、隔離内の scratch へコピーして導入・テストする。元の候補を実行せず、出力先は別の `RUN/execution-output` だけとする。レビュー済みの argv 配列を `shell=False` で一度だけ起動し、`RUN` 全体を渡さない。確認済みの配布物と固定した全依存グラフで再現可能に導入し、実行時の未確認な再取得・再解決を許さない。既存 lockfile がない系統は、採用中の方式で正確な全解決版・取得元・digest・ビルド依存を記録して再照合する。固定方法を確認できなければ保留する。必要な script・native build・取得バイナリまでレビューして計画した隔離内で使い、lockfile 削除による全再解決や強制オプションに頼らない。
- 候補で準備した manifest・ビルド定義・lockfile 相当、環境の版指定、CI・コンテナ設定と、公式移行ガイドで必要な API・設定の修正を最終 worker の検証対象に含める。テストを消して通したり、無関係なリファクタリングや新機能を混ぜたりしない。ホストの既定環境や OS・グローバル環境を勝手に変えない。
- 移行補助ツール・code mod・生成器も配布物・実行範囲・入力を計画前に確認し、同じ `run` が起動するレビュー済み executor 内で使い、生成された全差分を読む。移行ガイドにあるという理由だけで自動取得・即実行しない。追加の導入や更新が必要なら別のレビュー済み計画の `run` を経由する。
- データ移行はダミーデータのローカル環境で試す。本番データの変換、不可逆なマイグレーション、実サービスへの書込みはこのスキルの呼び出しだけで実行しない。必要なら具体的な手順・復元案を作り、ローカルで検証できる範囲まで進める。
- 実際の版・依存グラフ・checksum と採用表を、同じ worker 内で照合する。再解決で未確認の版・間接依存が増えたら停止し、別の実行記録で計画と全レビューをやり直す。同じ計画の再実行やゲート外の導入で修正しない。対象への反映は下記の検証結果確認後とし、依存ディレクトリ・キャッシュ・秘密ファイルを持ち込まない。

### 3. 最終 worker 内で検証し、結果を確認する

- `init` 前に、最終 worker が導入 → 実版・全依存グラフ・digest の照合 → この一件のテスト・型チェック・lint・ビルドと必須チェック → 対象別の実操作 → 許可差分と証拠の保存を一度の `run` 内で完了するよう組む。`set -eu` で始め、必須処理の失敗を終了コードへ伝える。重要な API・認証・シリアライズ・時刻処理等の境界を既存テストで覆えなければ、振る舞いを確認する回帰テストも候補へ含める。
- チェック成功後、CLI・ライブラリ等は同じ worker 内で `references/verification.md` の正常系・異常系を実行する。Web・DB・ネイティブ操作は、事前に選んだ既存 executor が検査済み環境を維持して必要な実操作まで完了する。Web は組み込みブラウザで正常系・入力エラー・保存と再表示・必要な認証や権限制御を確認する。全工程を完了できなければ、この一件を適用しない。
- 同梱 executor の scratch と導入済み環境は worker 終了時に消える。[保存・反映契約](references/isolation.md#6-検証した差分を保存して対象へ反映する)に従い、候補で事前準備した分を含む元プロジェクトからの全差分・実行 bit・削除と証拠を保存する。`run` 後は成果物を読み、元の全適用予定パスの初期状態を再照合してから許可差分だけを対象へ反映する。追加検証・失敗修正には、新しい実行記録・計画で全レビューと導入・検証をやり直す。解消できなければこの一件を保留し、ユーザーの既存変更や先に完了した更新を戻さない。危険な元の版が残る場合は未解消の危険も記録する。
- Web の影響がない対象はブラウザ適用外の理由と対象別の実行検証を記録する。組み込みブラウザ利用不可は「未実施」とし、外部ブラウザや E2E 成功で代用したことにしない。必要な実操作が未実施の一件は完了扱いにしない。

### 4. 一件の結果を確定して次へ進む

- `git diff --check`、最終差分、残る脆弱性、採用版、ゲートの7項目・機械検査・`run` の結果、テストと対象別の実操作の証拠を確認する。供給網確認・テスト・必要な実操作が完了した一件だけを「検証済み」と記録して反映し、その採用版・全依存グラフを次の一件の更新前状態にする。次の一件には新しい `RUN` と計画を用い、実行済み状態やレビューを流用しない。変更単位は分けるが、依頼なしにコミットしない。
- 未完の変更を積み上げて次へ進めない。失敗・保留の一件は、自分の適用分を戻してから独立した次の候補を進める。その一件に依存する後続候補は保留する。隔離など全候補に共通する前提が不足していれば、残りは静的調査・計画までに留める。ブラウザなど一部対象だけの前提が不足する場合は、その対象と依存関係のない実行可能な候補を進める。

## 最終状態と残る作業を報告する

全候補の処理後は組合せで影響が生じる箇所を見直し、最後の検証から状態が変わっていなければ結果を再利用する。新たな変更や懸念で追加検証が必要なら、新しい `RUN` と計画で全レビュー・導入・検証をやり直す。自分が起動した一時プロセスは終了する。

日本語で、一件ごとの更新版・移行理由・関連セット・結果、供給網の根拠と限界、ゲートの7項目・機械検査・`run` の結果、検証コマンド、実操作の入力・期待／実際の結果・証拠、Web の場合は URL と画面操作、保留／未着手と次の再開条件、元に戻す方法、各 `report.md` のパスを簡潔に伝える。疑わしい兆候がなかった範囲に限り「確認した範囲では疑わしい兆候を検出しなかった」と述べ、検出した兆候は根拠と停止・保留を明示する。攻撃の不存在を保証しない。隔離やネットワークなどで実行できなければ未実施の工程を示す。コミット・push・PR・公開は別途依頼があるときに行う。

ゲートは同じ UID の利用者による意図的な偽造や直接コマンドの迂回を防ぐ OS 境界ではなく、成功しても供給網の無害を保証しない。根拠・隔離・検証の不足を隠さず残す。
