# ランタイムと依存ライブラリを一件ずつ移行する

メジャー更新を、対象の選定 → 供給網確認 → 移行 → テスト → 画面の実操作の順に一件ずつ完結させる。番号上は minor でも互換性を壊す更新を含む。監査や動作確認から、攻撃が含まれないと断定することはできない。

## 対象と現在の状態を調べる

1. 対象の指示、未コミット差分、README、CI、manifest・lockfile、ランタイム・パッケージ管理ツールの指定を読む。Node、Ruby などの実バージョンと管理方法を調べる。Gemfile・hook・plugin などを調査のためにいきなり実行しない。
2. 指定したパッケージ・ランタイムを対象にする。範囲指定がなければプロジェクト内の候補を一覧化し、依存順とサポート終了・脆弱性・移行コストから優先順位を決める。直接・間接・dev・build・optional 依存、workspace、CI のみの依存も探索し、未探索の lockfile・OS・アーキテクチャを記録する。グローバル・OS 全体・管理ツール本体は依頼された範囲だけ扱う。
3. このスキルの実体から `bash scripts/new-run.sh <project-slug>` を実行し、出力先の `report.md` に候補一覧、実行順、元の差分、取得日時と根拠 URL、結果、保留と再開条件を記録する。スクリプトへのパスはスキルから解決し、秘密値・実データを保存しない。
4. 既存の信頼済み環境で、後述の隔離条件のもと、CI のテスト・型チェック・lint・ビルドの基準結果を取る。画面・操作・期待結果を変更点に対応づけ、必要なら変更前の画面も記録する。既存失敗と実行不能を新しい不具合と区別する。

## 一件の境界と移行先を決める

- 通常は一つの直接依存、間接依存の導入元、または一つのランタイムを一件とする。その更新に不可欠な peer 依存・公式に版を揃える関連パッケージ・同梱ツールは、不可分なセットである理由と全構成を記録して同じ一件に含める。無関係の major や minor を混ぜない。
- SemVer の major 増加に加え、`0.x` の minor 増加、Ruby の `3.3 → 3.4` のように互換性変更を許すブランチ更新、公式に破壊的変更を含む minor・patch もここで扱う。非 SemVer は公式の互換性方針で判断する。
- 最新情報は実行時の公式レジストリ、移行ガイド、リリースノート、セキュリティ告知、サポート方針で確認する。単に `latest` を選ばず、対象 OS・アーキテクチャ、ランタイム、フレームワーク、native extension、peer 依存を満たす正確な安定版を固定する。
- 複数 major を飛び越す場合は、中間版の移行ガイドも読み、公式推奨の段階的更新が必要なら一段ずつ検証する。次の major が既に EOL なら無条件にそこを採用せず、サポートされる版への公式な経路を検討する。経路不明なら保留する。
- 原則として公開から **7日以上** 経過した版を選ぶ。組織の方針を優先し、緊急の脆弱性修正で短縮する場合は根拠と追加確認を記録する。日数は安全の証明ではない。prerelease・撤回・非推奨・既知の悪性版は通常の候補にしない。
- 一件ごとに、現在 → 目標の正確な版、関連セット、破壊的変更と呼び出し箇所、必要な設定・データ形式の移行、テスト、画面操作、戻し方を記録してから進める。既存の依頼で範囲が明確なローカル移行は追加確認を挟まず進める。要件やデータ契約の判断が必要な部分は具体的な案まで用意し、独立した調査・検証を続ける。

## 一件ずつ次の工程を完了する

### 1. 供給網と全依存差分を確認する

- [供給網と実行・画面検証](references/verification.md) と、使う管理系統の [更新方法の注意点](references/ecosystems.md) を読む。レジストリ・配布物・脆弱性・実行箇所を確認する。マイナー更新と同じ証拠水準を保つ。
- manifest・lockfile の静的確認と公式メタデータから仮候補を作り、対象から分離した候補用コピーで解決する。lockfile のみの操作でも対象コードを実行する場合があるため、Gemfile・hook・plugin を先に読み、必要な隔離を解決時から適用する。
- 解決された全直接・間接依存の版・取得元・integrity/checksum・git ref・追加削除・install/build script と配布物差分を一覧化して確認する。公開日の条件も全変更版に適用する。関連セット以外の変更は必要性を説明できる最小範囲に絞り、別の独立した major は固定するか後の一件に回す。
- 公開元の連続性、改ざん検証、既知の脆弱性・悪性告知、疑わしいコードを複数の根拠で確認する。監査ゼロ件、署名、provenance、利用者数だけで採用しない。署名がない場合は代替根拠と限界を記録する。不審・証拠不足なら、この一件を導入せず保留する。

### 2. 固定した版へ移行する

- 取得とコード実行を分け、確認済みの配布物と lockfile で再現可能な導入を行う。必要な install script・native build・取得バイナリまで確認して、隔離内で必要なものだけ実行する。lockfile 削除による全再解決や `--force` に頼らない。
- manifest・lockfile、プロジェクトのランタイム指定、CI・コンテナ設定を同期し、公式移行ガイドで必要な API・設定の修正だけを行う。テストを消して通したり、無関係なリファクタリングや新機能を混ぜたりしない。ホストの既定ランタイムや OS・グローバル環境を勝手に変えない。
- データ移行はダミーデータのローカル環境で試す。本番データの変換、不可逆なマイグレーション、実サービスへの書込みはこのスキルの呼び出しだけで実行しない。必要なら具体的な手順・復元案を作り、ローカルで検証できる範囲まで進める。
- 実際の版・依存グラフ・checksum と採用表を照合する。再解決で未確認の版・間接依存が増えたら、実行前に戻ってレビューする。隔離用コピーから対象へ反映する場合は、許可したソース・設定差分だけを移し、依存ディレクトリ・キャッシュ・秘密ファイルを持ち込まない。

### 3. テストと組み込みブラウザで確かめる

- この一件の状態で、計画したテスト・型チェック・lint・ビルド、必須の全チェックを実行する。重要な API・認証・シリアライズ・時刻処理など破壊的変更の境界を既存テストで覆えなければ、振る舞いを確認する回帰テストを追加する。
- チェック成功後、隔離したローカルアプリを組み込みブラウザで開き、`references/verification.md` の手順で実操作する。変更箇所の正常系・入力エラー、保存と再表示、必要な認証・権限制御、関連する主要経路をダミーデータで確認する。スクリーンショットだけで完了にしない。
- 新しい失敗は自分の移行差分を修正して再検証する。解消できなければこの一件の自分の変更だけを戻し、直前の検証済み状態を確認する。ユーザーの既存変更や先に完了した更新を戻さない。危険な元の版に戻った場合は未解消の危険も記録する。
- 画面のない CLI などは適用外の理由と代替の実行確認を記録する。組み込みブラウザ利用不可は「未実施」とし、外部ブラウザや E2E 成功で代用したことにしない。必要な画面検証が未実施の一件は完了扱いにしない。

### 4. 一件の結果を確定して次へ進む

- `git diff --check`、最終差分、残る脆弱性、採用版、テストと画面の証拠を確認する。供給網確認・テスト・必要な画面検証が完了した一件だけを「検証済み」と記録し、その状態を次の基準にする。変更単位は分けるが、依頼なしにコミットしない。
- 未完の変更を積み上げて次へ進めない。失敗・保留の一件は、自分の適用分を戻してから独立した次の候補を進める。その一件に依存する後続候補は保留する。隔離やブラウザなど共通の前提が不足していれば、残りは静的調査・計画までに留める。

## 最終状態と残る作業を報告する

全候補の処理後は組合せで影響が生じる箇所を見直し、最後の検証から状態が変わっていなければ結果を再利用する。新たな変更や懸念がある検証だけを追加実行する。自分が起動した一時プロセスは終了する。

日本語で、一件ごとの更新版・移行理由・関連セット・結果、供給網の根拠と限界、検証コマンド、画面の URL・操作・期待／実際の結果・証拠、保留／未着手と次の再開条件、元に戻す方法、`report.md` のパスを簡潔に伝える。疑わしい兆候がなかった範囲に限り「確認した範囲では疑わしい兆候を検出しなかった」と述べ、検出した兆候は根拠と停止・保留を明示する。攻撃の不存在を保証しない。隔離やネットワークなどで実行できなければ未実施の工程を示す。コミット・push・PR・公開は別途依頼があるときに行う。
