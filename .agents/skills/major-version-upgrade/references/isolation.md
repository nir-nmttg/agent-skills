# 隔離環境を自動準備する

既存 executor のパスを尋ねる前に、同梱の `scripts/docker-sandbox.py prepare` で準備する。利用可能なローカル Docker 上で、digest を固定した image、読み取り専用入力、容量制限付き作業領域、通信・権限・資源の制限を持つ設定と executor を生成し、probe する。必要な条件を満たす既存のコンテナ・VM・OS sandbox があれば、その実体・設定をレビューして利用してもよい。

Docker 本体のインストール、daemon の起動、`sudo`・root 実行、socket の所有者・権限やユーザーの所属グループなどのホスト設定変更は行わない。自動準備と probe の成功は、供給網の安全性やゲートの `isolation` を自動承認する証明ではない。

## Docker 接続と Codex の実行承認

Codex のコマンド実行制限と、対象・依存コードを動かすコンテナの隔離は別の境界である。ホスト側の信頼済み同梱 helper・ゲート・生成 executor が既存 Docker を制御するため、環境が提供する正規の実行承認を利用できる。承認後も対象・依存コードは制限付きコンテナ内だけで動かす。

- 通常実行で Docker socket への接続が `permission denied` になったら、CLI 実体・既存のローカル endpoint と socket を確認し、対象コードを動かさない接続確認（`docker version` 等）を正規の承認手続きで再試行する。実行ツールに `sandbox_permissions: require_escalated` 相当がある場合はそれを使い、接続先と目的を示す。要求しただけでは承認済みと扱わず、上位の実行ポリシーと承認結果に従う。
- Docker 制御はホストへ広く作用できるため、同梱コード・生成設定・呼び出し引数・固定 image・入力範囲をレビューし、必要な具体的な呼び出しだけを承認対象にする。任意の Docker 操作・Python 実行・プロジェクト内 wrapper をまとめて許可するルールや、Codex 全体の制限解除を求めない。
- この扱いは接続確認に加え、`prepare` と probe、基準用・候補解決用 executor、最終 `supply-chain.py run` からの executor 起動、専用コンテナの後始末に適用する。最終導入は引き続き全レビューを通したゲートからだけ行う。既に開始・失敗した準備や `run` は承認取得を理由に再利用せず、新しい `RUN` と必要な全レビューでやり直す。
- 承認は worker の追加権限、外部通信、ホストの HOME・秘密・Docker socket の公開、対象・依存コードのホストでの代行実行を許可しない。読み取り専用入力・出力分離・実行ユーザー・資源上限と probe を維持する。
- 正規の承認機構を利用できない、ポリシーで禁止・拒否された、または承認後も OS 側で接続を拒否された場合は保留する。拒否を別の実行経路で迂回せず、どの段階で拒否されたかと未実施の工程を記録する。通常実行のエラーだけで Docker の未起動や OS の権限設定不足と断定しない。

## 1. image と worker を準備する

1. 対象の指示・CI・manifest・lockfile・版指定を静的に読み、必要な OS・アーキテクチャ・ランタイム・管理ツール・native build の条件を決める。基準テストには現在版、更新後には採用版の条件を満たす環境が必要であり、異なる OS の結果で代用しない。
2. 公式の配布情報から条件に合う公認 image を調べ、公開元・版・toolchain・対象 platform と `repository@sha256:<64桁の実測値>` を確認する。準備用に `/bin/sh`・`cp`・`chmod`・`mkdir`・`env`・`tar`・`cat` も必要である。可変 tag を実行設定に使わず、実行時の未確認なツール自動取得も許さない。単一 image で複数言語・必要なツールを揃えられなければ、依存境界に従う分割や検証済みの既存環境を検討し、不足を記録する。対象の Dockerfile を無条件に build しない。
3. 同梱の `scripts/docker-sandbox.py` を読み、利用する Docker CLI・ローカル context と制限を確認する。スキルからのパスは実体を基準に解決し、プロジェクトの wrapper を準備処理へ持ち込まない。
4. `RUN/sandbox/worker.sh` に、その工程用のレビュー済み `/bin/sh` スクリプトを作る。`set -eu` で始め、必須処理の失敗を終了コードへ伝える。`if`・`&&`・pipeline 等の例外を確認し、`... | tee` 等で失敗を隠さない。実際に使う管理方式の固定・オフライン導入、照合・検証、結果の保存を記述し、未確認の hook・ツール取得・外部サービスへの接続を含めない。基準用・候補解決用・最終採用用で worker と入力・出力を分け、最終計画は `init` 前に固定する。

ランタイム更新で基準用と採用用の image が異なる場合は、基準用に別の `RUN` を作って現在版 image を準備し、最終採用用の新しい `RUN` で採用版 image を準備する。`prepare` は既存設定を上書きしない。基準用の実測結果と旧版グラフ・環境の記録を、最終 `RUN` の証拠へ保存して対応づける。

## 2. 設定と executor を自動生成する

image でランタイムを切り替える場合は、実測した正確な版と image 参照を inventory に記録し、候補の `runtime_image` を [実行ゲート](gate.md) の形式で宣言する。`execution.config` の `image`・`image_id` と結びつけ、使わないランタイム archive を用意して代用しない。image の識別だけでは中の実版を証明しないため、準備時の観測と最終 worker の実版照合を証拠へ残す。

native 拡張は、対象ランタイムの headers・compiler・linker・build tool を事前に含む image でビルドする。旧 ABI の `.so` や依存ディレクトリを候補へ移さず、ソース・生成器・必要な全入力を固定し、対象環境で再ビルド・ロード・実操作まで確かめる。同じライブラリ版の再ビルドはランタイム移行に含められる。ABI 別 wheel 等で同版の取得物が変わる場合は、実際の配布物を区別する正確な `source` と hash を inventory・候補へ反映する。版上昇とは分けて扱い、新旧配布物の差分・公開日・出所・監査・互換性をすべて確認する。同版を安全の根拠にせず、互換性不明なら個別移行へ回す。minor では同版・同じ取得元の metadata だけの変更を拒否し、major では一件の移行境界と互換性を精査する。worker 内で compiler や SDK を取得せず、不足する場合は image の選定をやり直す。native 拡張のビルド・ロードと、ネイティブアプリの OS 上の画面操作は別の検証である。

`UPGRADE_PYTHON` はプロジェクト外の信頼済み Python 3.9 以降の実体、`UPGRADE_SANDBOX` はこのスキル実体の `scripts/docker-sandbox.py` の絶対パス、`UPGRADE_IMAGE` は前項で確認した実際の digest 付き参照とする。`RUN` は `scripts/new-run.sh` が作った実行記録先を使う。

```bash
"$UPGRADE_PYTHON" -I -S "$UPGRADE_SANDBOX" prepare \
  --run "$RUN" --image "$UPGRADE_IMAGE" --worker sandbox/worker.sh
```

必要なら `--docker <Docker CLI実体の絶対パス>`、`--context <既存のローカルcontext名>` を指定する。通常は利用可能な既存 CLI とローカル daemon/context を検出する。選んだ image がなければ digest 付きで取得し、固定した制限で probe する。image 取得時に対象プロジェクトや worker は実行しない。

生成物を読む。

| 保存先 | 用途 |
| --- | --- |
| `RUN/sandbox/config.json` | 固定 image・Docker 接続先・制限など、実際の実行設定 |
| `RUN/sandbox/executor` | ゲートが起動する実行プログラムの実体 |
| `RUN/sandbox/execution.json` | `plan.json` の `execution` に統合する設定 |
| `RUN/evidence/isolation-setup.json` | 準備と probe の結果。手動レビューの根拠の一部として使う |

準備の成功後も、image・同梱コード・生成 executor/config・worker・実際の境界と probe の範囲をレビューする。`config` に元の `RUN`・`PROJECT`・`CANDIDATE` の生パスを埋め込まない。既存の設定や証拠を変えて承認を再利用せず、変更・失敗・期限切れは [実行ゲート](gate.md) に従って新しい実行記録で扱う。

## 3. worker と入力・出力の契約

- executor は受け取った候補を読み取り専用で公開し、隔離内の `/scratch/project` へコピーしてから worker を動かす。worker は `CANDIDATE=/scratch/project`、`OUTPUT=/scratch/output` を使い、ホストのパスを組み立てない。
- 追加の `--input` は指定順に `/inputs/0`、`/inputs/1`、…へ読み取り専用で渡る。配布物は `--input` の値を `{artifact:RUN内の相対パス}`、補助ファイルは `{input:RUN内の相対パス}` として `execution.argv` に追加する。後者は `execution.inputs` にも列挙する。worker 自身も生成設定どおり `inputs` に含める。ツールが拡張子・元の basename を要求する場合は worker で `/scratch` 配下の所定名（`.tgz` 等）へコピーして使い、ホストの元パスを組み立てない。
- 候補は `.git`・秘密・実データを除いた最小コピーとし、ホストの HOME・認証設定・SSH agent・Docker socket を渡さない。環境変数は executor の許可リストだけを使う。
- `/scratch` などの書き込み領域は容量を制限し、外部通信・追加権限を許可しない。scratch 内の依存コマンド・native code は実行可能にする。tmpfs の使用量もメモリ上限に含まれるため、必要な資源が足りるか確認する。worker は `/bin/sh -eu` で起動され、保存すべき差分・監査結果・検証証拠を `$OUTPUT` へ書き、終了コードで成否を返す。標準出力・標準エラーは `worker.log`、終了コードは `exit-code` に記録されるため、この2名を成果物へ使わない。ホストへの書き戻しは executor が検査した出力だけとし、依存ディレクトリ・cache・秘密を成果物へ混ぜない。
- 最終導入では `sandbox/execution.json` を `plan.execution` に統合し、必要な全配布物・追加ファイルと token を列挙する。ゲートが作る読み取り専用 snapshot と専用出力だけを使い、`RUN` 全体を渡さない。最終採用候補の導入・更新は全レビューを通した `supply-chain.py run` から一度だけ行う。
- 最終 worker は導入、実版・全依存グラフ・digest の照合、テスト・型チェック・lint・ビルド、CLI/consumer 等の正常系・異常系、[許可差分と証拠の保存](#6-検証した差分を保存して対象へ反映する)まで一回で完了する。終了時にコンテナと scratch は削除され、導入済み環境は残らない。`run` 後は出力を読み、同節の事前状態照合を通った検証済み差分だけを対象へ反映する。追加検証・修正・部分除外は新しい `RUN` と計画で全レビュー・導入・検証をやり直し、同じ計画の再実行やホストでの依存再現を使わない。

## 4. 準備段階と対応できない工程

調査用 scratch の依存解決・必要な展開と、固定した更新前グラフの基準環境再現・テストは、`init` 前でも準備・レビューした executor と同じ隔離条件で行える。基準用は旧版の正確な配布物・出所・digest を固定してオフライン導入し、実ランタイム・全依存グラフを更新前状態と照合してから測る。候補解決用には仮候補を渡し、基準結果と混同しない。基準用・候補解決用・最終採用用の worker・入力・専用出力を分ける。未固定の元プロジェクトや `RUN` 全体を公開せず、準備中の依存環境を対象へ反映したり、最終採用の承認済み更新と扱ったりしない。

準備段階の呼び出しは次の形を使う。`PREP_RUN` はその工程の image を準備した実行記録先、`PREP_INPUT` は秘密を除いて固定した入力コピー、`PREP_OUTPUT` は空で所有者だけがアクセスできる専用出力先とする。`PREP_WORKER` は基準用または候補解決用のレビュー済み worker の実体を指定する。配布物・補助ファイルは必要なものだけ `--input <固定したファイルの実体>` で追加する。最終導入時の呼び出しはこの形で代行せず、ゲートの token を使う。

```bash
"$PREP_RUN/sandbox/executor" execute \
  --config "$PREP_RUN/sandbox/config.json" --candidate "$PREP_INPUT" \
  --worker "$PREP_WORKER" --output "$PREP_OUTPUT"
```

公認元から正確な版と digest の取得物を揃える処理と、下記条件を満たす監査専用の照会は、対象コードを実行しない取得用プロセスで行う。同梱 executor の外部通信禁止を解除しない。依存解決・監査などにコード評価と通信の両方が必要、またはコード評価を排除できるか不明なら、秘密を渡さず送信先を限定できる既存の取得専用隔離を確認する。なければその工程を保留する。

同梱 sandbox はオフライン処理向けで、ホストへのポート公開、DB との連携、組み込みブラウザやネイティブ OS の実操作を自動準備しない。必要な場合は `init` 前に、[隔離条件](verification.md#4-隔離を確認してから導入テスト起動する) を満たし、導入済み環境を必要な実操作まで維持して一度の `run` で全工程を完遂できる既存 executor を選ぶ。用意できなければ必要な検証を未実施とし、適用を保留する。途中でホストへ依存環境を持ち出したり、ゲート外で再導入したりしない。

失敗時は「Docker CLI が未導入」「daemon に接続できない」「image 取得先への通信不可」「必要な toolchain/platform がない」「probe が失敗」など、実際に確認できた不足・未確認の区別と再開条件を報告する。Docker の有無だけで実行可能と判定せず、上記の正規の接続承認も切り分け、静的調査と差分案を続ける。worker の権限拡大、対象・依存コードのホストでの代行、通信制限の解除で回避しない。

## 5. 対象コードを実行しない監査照会

監査専用の照会は、次の条件をすべて確認できる場合に、対象コードを実行しない取得用プロセスとして行える。ホストで対象・依存コードを代行実行する例外ではない。

- プロジェクト外の信頼済み audit ツールとランタイムの実体・版を使う。環境変数は空から必要な名前と安全な値だけを許可し、使い捨ての HOME・cache・データ専用作業場を用意する。
- 入力は秘密を除いた manifest・lockfile・正確な全依存 inventory だけとする。元プロジェクトで起動せず、プロジェクトやユーザーの設定、plugin・hook・local wrapper を読み込まない。
- 対象・依存のコードを評価せず、再解決・導入・修復を行わない。使用版の公式仕様と入力・起動経路を確認し、抑止フラグの名前だけで成立と判断しない。
- 送信先と送信内容を確認し、private 名や認証情報を無断送信しない。依存の種類や送信制約のため全範囲を監査できない場合は、未確認の範囲を隠さず保留する。
- 実際のツールが出した JSON を無加工で保存し、実測の時刻・終了コード、ツール版、送信先・送信内容と実行条件の根拠を記録する。更新後 inventory の全ライブラリ・ビルド依存を対象にし、ランタイムだけを変更する場合も既存依存を省略しない。coverage・24時間の期限・finding 等の停止条件は [実行ゲート](gate.md) と同じで、結果を加工して `pass` にしない。

公開依存だけの npm プロジェクトなら、上記のデータ専用作業場で、空の user/global npm 設定・許可した環境・使い捨て HOME/cache と、信頼済みの既存 npm を使い、`npm audit --json --package-lock-only --ignore-scripts --registry=https://registry.npmjs.org/` のように照会する。`--userconfig`・`--globalconfig` で空ファイルを明示し、対象版の仕様で設定・拡張・hook が読み込まれないことと、全依存の coverage を確認する。npm v11 の `ignore-scripts` は `.npm-extension` も無効化するが、他の版へ推測で適用しない。元プロジェクト内では実行しない。

[npm audit の公式仕様](https://docs.npmjs.com/cli/v11/commands/npm-audit/) では、通常の audit は依存情報の registry 照会であり、`audit fix` は `npm install` の処理を含む。監査専用プロセスでは `fix` を使わない。コード評価が起きる、再解決が必要、または上記条件を確認できない場合は、通信を制限する隔離が必要であり、準備できなければ保留する。

## 6. 検証した差分を保存して対象へ反映する

1. 候補の事前編集前に、親側で許可するソースの範囲と反映予定の全パスを宣言し、範囲内の全ファイル・ディレクトリと、元の bytes または SHA256・権限（実行 bit を含む）を完全な基準 manifest として `RUN` に記録する。追加予定の不存在もこの初期一覧で確認する。秘密・依存・cache 等の除外パスは許可範囲へ含めない。必要な基準情報だけを `execution.inputs` に固定して worker へ渡す。事前にパスを決められない生成処理は調査で対象を特定し、初期記録の許可範囲外や未宣言の反映パスが必要なら新しい `RUN` で計画し直す。`plan.files` 外のソースもこの契約で保護する。
2. 最終 worker は、元プロジェクトから最後に検証した scratch までの追加・変更・削除・rename（削除＋追加でもよい）を、変更前後の有無・SHA256・必要な実行 bit を伴うレビュー可能な patch、または変更 manifest と最終内容として保存する。候補で事前準備した差分も含め、scratch 内だけの差分に限定しない。最後のテスト・実操作後に保存対象のソースを変えず、変更が必要なら新しい `RUN` で再検証する。
3. `run` 成功後、検証証拠と全差分の内容・実行 bit・削除を読み、宣言済みパス、変更前の状態と親側の初期記録、変更後の hash と保存内容を照合する。出力の保存 mode `0600` や入力 snapshot の読み取り専用 mode を、元の権限や反映先の指定として扱わない。ソースのコピーだけでは実行 bit・削除・rename を復元できず、反映可能な成果物にはしない。symlink・特殊ファイル・危険なパス、未宣言パス、依存ディレクトリ・cache・秘密を対象へ持ち込まない。
4. 反映直前に、全適用予定パスの現在の有無・bytes/hash・実行 bit と親側の初期記録を照合し、親ディレクトリを含む symlink や特殊な参照も拒否する。一件でも不一致なら全件の適用を開始せず、worker 実行中のユーザー変更も保持して新しい `RUN` で調整する。ゲートの実行前検査だけでこの照合を代用しない。
5. 照合を通した全差分だけを既存のファイル編集・patch 手順で反映する。明示的な変更以外の既存権限を保ち、保存時の `0600` を流用せず、レビューした実行 bit と削除・追加を反映する。適用中に競合・失敗を検出したら適用済み・未適用を記録して停止し、ユーザー変更を巻き込む一括 rollback をしない。最後に全パスの更新後 hash・実行 bit・削除済み状態を成果物と照合し、検証した最終内容と一致するまで反映完了と扱わない。
