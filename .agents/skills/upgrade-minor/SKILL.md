# ランタイムと依存ライブラリをまとめて更新する

プロジェクトのマイナー・パッチ更新を一つのまとまりとして進める。新しい版の導入前に供給網を確認し、更新後のテストと画面の実操作まで行う。マイナー番号でも互換性は保証されず、監査が成功しても攻撃がないとは断定できない。

## 対象と検証計画を決める

1. 対象の指示、未コミット差分、README、CI、manifest・lockfile、ランタイムの指定、コンテナ設定を読む。Node、Ruby、使用中のパッケージ管理ツールの実際の版と管理方法を調べる。未知の設定・プラグイン・Gemfile などを、調査のためにいきなり実行しない。
2. 範囲指定がなければ、現在のプロジェクトで使用するランタイムと直接・間接依存を対象にする。dev・build・optional 依存、workspace、CI でだけ使う依存も含め、未探索の lockfile・OS・アーキテクチャを記録する。グローバルパッケージ・OS 全体・ランタイム管理ツール本体は、依頼された場合だけ扱う。
3. このスキルの実体から `bash scripts/new-run.sh <project-slug>` を実行する。出力先の `report.md` に対象、元の差分、候補表、取得日時と根拠 URL、実行結果、保留理由を随時記録する。スクリプトへのパスは対象プロジェクトの作業場所ではなくスキルから解決する。秘密値や実データを保存しない。
4. 変更前後に実行する既存テスト・型チェック・lint・ビルドを CI から選び、影響する画面・操作・期待結果と対応づける。現在の信頼済み環境でも、下記の隔離条件で基準結果を取る。既存失敗と実行不能を新しい失敗と区別する。必要なら変更前の画面も記録する。

## 更新候補を絞る

- 最新情報は実行時に公式レジストリ、リリースノート、セキュリティ告知、サポート方針で確認する。`latest` タグだけで選ばず、互換性・サポート期間・既存の制約を満たす安定版を選び、導入する正確な版を固定する。範囲指定を変える場合も既存の pin 方針を守る。
- 通常の SemVer の `1.x` 以降は同一 major 内の minor・patch を候補にする。`0.x` の minor 増加、公式に破壊的変更を含む版、Ruby の `3.3 → 3.4` のような互換性変更を許すブランチ更新は個別移行として保留し、`$upgrade-major` を案内する。パッチでも破壊的変更が判明したら同様に扱う。非 SemVer は公式方針で分類し、不明なら一括更新に入れない。
- prerelease、撤回・非推奨・既知の悪性版、対象環境でサポートされない版を除く。候補は原則として公開から **7日以上** 経過した版とし、組織の方針があればそちらを優先する。これは検知を待つための目安で、安全の証明ではない。緊急の脆弱性修正では、修正告知と代替策・追加確認を示して短縮の判断を記録する。
- 同一 major の保守が終了していれば、その場で major を上げず移行が必要と報告する。ランタイムに同梱される npm などの版、peer 依存、native extension、Node/Ruby の要求範囲も確認する。
- 候補表は「種類・名前・現在の解決版 → 候補の正確な版・公開日・分類理由・状態」を持たせる。直接依存だけでなく、解決時に変わる全間接依存にも同じ確認を適用する。間接依存の major 増加を一括更新に紛れ込ませず、互換性を満たす既存 major 内の別候補に固定するか個別移行へ回す。

## 導入前の供給網を確認する

1. [供給網と実行・画面検証](references/verification.md) を読み、公開元、配布物、脆弱性、コード実行箇所、隔離条件を確認する。使う管理系統について [更新方法の注意点](references/ecosystems.md) も読む。下記の一括処理にも、この確認を省略しない。
2. 静的に読める manifest・lockfile と公式メタデータから仮候補を作る。再解決・取得・展開は対象プロジェクトから分離した候補用コピーで行う。lockfile だけの生成でも Gemfile・hook・plugin を実行し得るため、コマンド実行前に読み、コード評価がある操作には最初から実行隔離を適用する。
3. 候補の全依存グラフを固定し、元のグラフとの差を調べる。版・取得元・integrity/checksum・git ref・追加削除・install/build script の変更を全件一覧化し、配布物差分を読む。公開からの日数も全変更版に適用する。レビュー中に再解決されたら、変わった部分を再確認する。
4. 脆弱性と悪性パッケージの告知、配布元の連続性、改ざん検証、疑わしいコードを複数の根拠で確認する。監査ゼロ件、署名、provenance、利用者数のいずれも単独の採用根拠にしない。証拠不足・不審・互換性不明の候補は保留する。署名が提供されない場合は悪性と断定せず、代わりに確認した根拠と残る限界を記録する。
5. 保留対象を除外するときは、依存関係を再解決して差分を確認し直す。保留版が間接依存に残るならその導入元も保留する。既存の危険な版に戻すだけでは解消扱いにしない。全件を確認できなければ確認済みの独立した範囲だけを進め、残りを未確認として残す。

## 採用した候補をまとめて反映する

- 事前確認を終えたランタイム・ライブラリを一つの更新計画としてまとめて反映する。実際のコマンドは管理ツールと依存順に分かれてよいが、各 minor ごとに承認や全テストを挟まない。ランタイムとライブラリの互換条件を保ち、採用表にない更新を加えない。
- 取得とコード実行を分け、確認した配布物と lockfile で再現可能な導入を行う。パッケージ管理ツールの版を固定し、既存 lockfile を削除して作り直さない。native build や必要な install script は、内容と取得するバイナリまで確認したものだけ隔離内で許可する。
- プロジェクトが管理しているランタイム指定、manifest・lockfile、必要な CI・コンテナ設定を同期する。ホストの既定ランタイム切替、権限昇格、グローバル更新を代替策にしない。アプリを確認した隔離用コピーで更新した場合は、許可した設定・ソース差分だけを対象に反映し、キャッシュ・依存ディレクトリ・秘密ファイルを持ち込まない。
- 導入後の実バージョン・依存グラフ・checksum を候補表と照合する。新たな推移依存や別の版が入っていれば、実行する前に再レビューする。適用に付随するコード修正は互換性の維持に必要な最小範囲とし、新機能や設計変更を混ぜない。

## テストと組み込みブラウザで確かめる

1. 固定した新環境で、計画したテスト・型チェック・lint・ビルドと、リポジトリ必須のチェックを実行する。重大なセキュリティ修正は再現可能な回帰テストでも確認する。更新対象の変更点で新しい懸念が出た場合だけ検証を追加する。
2. チェック成功後、隔離したローカルアプリを組み込みブラウザで開き、`references/verification.md` の手順で実際に操作する。画面の表示だけで完了にせず、更新の影響を受ける正常系・入力エラー・保存後の再表示などを確認する。
3. 新しい失敗は更新との差分で切り分ける。一括更新の原因を調べるための一時的な分割はよいが、原因の確定後は残す更新の組合せで再検証する。解消できなければ問題を起こした自分の変更だけを戻し、残した組合せを再検証する。未検証の成果を成功として残さない。
4. `git diff --check` と最終差分を確認する。テストの削除・失敗の無視・監査や checksum の無効化・強制オプションで通さない。ユーザーの既存変更を戻さず、自分のサーバーなど一時プロセスは終了する。

## 結果を報告する

日本語で、採用した更新と保留一覧、供給網の根拠と限界、検証コマンドと結果、画面の URL・操作・期待／実際の結果・証拠、残る問題と元に戻す方法、`report.md` のパスを簡潔に伝える。記録は実行ごとに分ける。

画面のない CLI などは理由と代替の実行確認を記録し「画面検証は対象外」とする。組み込みブラウザが使えない場合、画面検証は「未実施」とし、外部ブラウザや E2E 成功で置き換えない。隔離不足やネットワーク制限などで進めない場合も、未実施の工程と安全に再開する条件を示す。供給網確認・テスト・必要な画面検証が揃うまで検証完了としない。疑わしい兆候がなかった範囲に限り「確認した範囲では疑わしい兆候を検出しなかった」と述べ、検出した兆候は根拠と停止・保留を明示する。コミット・push・PR・公開は別途依頼があるときに行う。
