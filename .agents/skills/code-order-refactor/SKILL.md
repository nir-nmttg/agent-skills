# ファイル内の宣言を読みやすい順番に整える

プロジェクト全体を定期的に見直し、入口から詳細へ処理を追いやすくする。同一ファイル・同一スコープ内の配置を対象にし、関連する宣言の間を往復する負担を減らせる変更を実装・検証する。既に読みやすい箇所は保ち、変更件数を成果にしない。

## プロジェクトを探索する

- リポジトリの指示と作業中の差分を確認する。範囲の指定がなければ `rg --files` などでプロジェクト全体の自前のソースを把握し、ディレクトリ・言語・役割ごとに探索する。指定があればその範囲を扱い、生成物・依存パッケージ・外部から取り込んだコードは除外する。
- README、lint・formatter 設定、代表的な実装と関連テストから、宣言順の規約、フレームワークの約束、入口と呼び出し関係を読む。モノレポや複数言語ではパッケージごとの慣習を尊重する。
- メソッド・関数・型などを読み、入口が補助処理に埋もれている箇所、関係の強い宣言が離れている箇所、役割の異なる宣言が入り交じる箇所を探す。ファイルの長さや名前だけで変更を決めない。主要ファイルだけを見て全体を確認済みとせず、探索済み・未探索の範囲を把握する。

## 安定した並び方を決める

実行上の制約を最優先し、明文化された規約・既存の lint 設定、周囲で確立した慣習、入口から詳細へ読む流れの順に判断する。設定や慣習が食い違う箇所は、根拠のない統一をせず保留する。

| 観点 | 規約がない場合の目安 |
| --- | --- |
| 全体の読み順 | 初期化・主要な入口・公開操作から、内部の実装詳細へ読める配置にする。言語上、利用前の宣言が必要なら依存先を先に置く。 |
| 関係の強い宣言 | 同じ役割・処理段階のメソッド、overload、getter/setter などをまとめ、まとまりの中も処理を追いやすい順にする。 |
| 補助処理 | 一つの入口だけで使う helper はその処理の近くへ置く。複数の入口で共有する helper は、既存の共通処理群や主要操作の後にまとめる。 |
| 同程度に妥当な順序 | 元の相対順を維持する。再帰・相互参照のあるまとまりは内部順を無理に変えない。 |

- 一律のアルファベット順・可視性順・長さ順を持ち込まない。既存のまとまりが読みやすければ、別の並びも可能という理由だけで動かさない。
- ファイルごとに採用する順序と改善理由を決め、簡潔に伝えてから進める。通常の並べ替えは提案だけで止めず実施する。レビュー・候補の提示だけを求められた場合は編集しない。

## 順序が意味を持つ箇所を守る

関数・メソッドに見えても、宣言時の評価、初期化、登録、名前解決、列挙やレイアウトが順序に依存しないか、言語・フレームワーク・利用側から確認する。

| 対象 | 維持する制約 |
| --- | --- |
| 実行される宣言・文 | import の副作用、変数・field の初期化、static block、クラス本体の実行、エントリーポイントの呼び出しをまたぐ移動で評価順や利用時点を変えない。 |
| 定義時の評価・登録 | decorator・attribute、デフォルト引数、計算されたメンバー名、ルートやプラグインの登録などは、評価時点・登録順・参照先を確認する。 |
| 宣言順が契約になるもの | field の位置に依存する構築・シリアライズ、Enum の値、メンバーの列挙、メモリレイアウト、同名宣言の上書き・優先順位、テストや hook の登録順を保つ。 |
| スコープ・構文上の境界 | overload 群、可視性の区間、条件付きコンパイル、macro・pragma、宣言前参照の制約を守る。区間や条件をまたいで移動しない。 |

安全と判断する根拠がない候補はその場に残し、理由を報告する。並べ替えのために初期化を遅延させる、宣言形式や登録方法を変えるなどの回避策は加えない。独立して整理できる箇所は進める。

## 宣言をまとまりごとに移動する

- 宣言と、その doc comment・decorator・attribute・注釈・付随するコメントを一緒に移す。セクション見出し、lint 抑制、formatter の有効範囲を確認し、別の宣言へ誤って適用しない。
- 名前・署名・可視性・本文を保ち、まとまりの移動と必要最小限の空行・区切りの調整に絞る。関数内の実行文の並べ替え、ファイル分割、抽出・共通化、改名、不要コード削除、全面的な整形は混ぜない。
- ファイルや関連する宣言群ごとに差分を確認できる単位で進める。正規表現だけで宣言境界を決めて一括置換しない。既存の並べ替えツールを使う場合も、その言語構文とコメントを扱え、採用した方針に合うことを確認する。
- ユーザーの未コミット変更を上書き・巻き戻ししない。移動対象と重なる場合は元の編集内容を保ち、区別できない箇所は保留する。

## 検証して定期実行に備える

- 変更前に関連する既存テストやチェックを確認し、必要な範囲を実行して既存の失敗・実行不能を記録する。変更後は影響範囲のテスト、型チェック、lint、ビルドなど適切な既存の検証と、リポジトリで必須のチェックを実行する。配置だけを固定するテストは増やさない。
- `git diff --color-moved` などで移動と内容変更を区別し、宣言の欠落・重複、本文やコメントの意図しない変更、順序依存の破壊がないか読む。検証の失敗を隠すために期待値・スナップショット・必須チェックを変えない。変更による問題が解消できなければ、自分の該当する移動だけを戻す。
- 変更後も同じ判断基準で見直し、追加の並べ替えが不要であることを確認する。並べ替えツールを使った場合は同じ設定で再実行し、差分が増えないことを確かめる。同じコードと規約なら、定期実行でも同じ配置を保つ。
- 日本語で簡潔に、探索範囲、採用した並び方と根拠、変更したファイルと改善理由、順序依存などで見送った箇所、実行コマンドと結果、未探索・未検証の範囲を報告する。有益な変更がなければ変更せず、その根拠を伝える。
