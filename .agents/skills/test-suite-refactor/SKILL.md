# 本質的なテストを残す

目的は、守るべき振る舞いの検出力を保ち、テストの保守負担・実行時間・不安定さを減らすこと。削減件数やカバレッジの数値を目標にしない。有用なテストしかなければ、削除しなくてよい。

## 対象と現状を確かめる

- 指定された差分・ファイル・機能の範囲で作業する。範囲がなければ作業中の差分に関係するテストから始め、リポジトリ全体に無条件で広げない。
- リポジトリの指示、仕様、対象コード、テスト、実行設定と CI を読む。各テストについて「どんな現実的な不具合が起きたときに失敗するか」を説明できるようにする。現在の実装だけを仕様の根拠にしない。
- 対象テストを変更前に実行し、成功・既存の失敗・実行不能を区別する。実行できなくても読める範囲の整理は進められるが、検出力を確認できない削除は見送る。
- レビューだけの依頼なら提案に留める。整理・削減・書き換えの依頼なら、根拠がある変更を実施する。

## 残す・統合する・書き換える・削除する

判断の中心は **検出する不具合と、それを確かめる観測点**。見た目が似ていることや、同じ行を通ることだけで重複と決めない。

| 判断 | 基準と対応 |
| --- | --- |
| 残す | 公開された振る舞い、業務ルール、境界値、異常系、状態遷移、権限・データ整合性、過去の不具合を守る。小さな純粋関数でも重要な境界を守っていれば残す。 |
| 統合する | 同じ条件・振る舞い・観測点で同じ不具合を検出する重複は、最も明確で安定したものへ寄せる。入力ごとに意味がある場合はパラメータ化し、ケース名と個別の失敗理由を維持する。 |
| 書き換える | private メソッド、内部の呼び出し順や回数、実装を再計算した期待値、モックが返した値だけを確認するテストは、公開 API・返り値・保存状態・利用者に見える結果を確かめる形へ変える。 |
| 削除する | 具体的な不具合を検出しない自明なアサーション、外部ライブラリ自体の仕様確認、他のテストが同じ契約と不具合を十分に守る重複、廃止が確認できた仕様のテスト。代わりに何が守るか、または守る必要がない根拠を示せるものに限る。 |

- モック・スナップショット・単体テスト・E2E という形式だけで価値を決めない。認可境界、シリアライズ、実際の接続や配線は統合テストでしか検出できない場合がある。テスト層を移すときは、失われる検出対象を確認する。
- 呼び出し回数が契約のこともある。二重課金の防止、リトライ上限、通知の重複防止などは回数の確認を残す。
- 大きなスナップショットは、利用者にとって重要な部分の明示的な確認へ置き換えられるか検討する。シリアライズ形式や出力全体が契約なら全体の確認に意味がある。
- 遅い・不安定・失敗しているだけでは削除しない。時間・乱数・外部 I/O の制御や、適切なテスト層への移動で安定させる。既知の不具合を隠すための削除や skip はしない。
- 仕様上の意味が不明なテストは残し、不明点を報告する。削除の承認を一律に求めず、仕様の判断が必要な箇所だけ確認する。

## 検出力を保ちながら変更する

- 削除・統合する前に、残すテストや置き換えるテストを特定する。同じ入力条件、境界、異常系、副作用を守るか確認し、代替が必要なら先に整える。
- 期待値は仕様や独立した具体例から決める。実装と同じロジックで期待値を作らず、名前・入力・アサーションから守る契約が読み取れる形にする。
- 不要になった fixture・mock・helper は参照を確かめて整理する。テスト削減のために本体の仕様、公開 API、CI の必須チェック、カバレッジ閾値を変更しない。
- 書き換えたテストが重要な不具合を捉える根拠が必要なら、既存の再現ケースや局所的な変異で確認する。たとえば境界条件を反転したり、必要な保存・通知を省いたときに失敗するかを見る。変異は隔離した一時コピーで行うか、戻し漏れが起きない方法を選び、ユーザーの変更を巻き戻さない。全面的な mutation testing の導入は前提にしない。

## 確認と報告

- 変更したテストと、その helper・fixture を共有する影響範囲を実行する。リポジトリで必須のチェックも行う。同じ条件での不要な再実行は避ける。
- 通ったことだけを根拠に検出力が同じとは判断しない。差分を読み直し、重要な失敗条件が消えていないか確かめる。カバレッジは抜けを探す補助に使う。
- 日本語で簡潔に、削除・統合・書き換えた対象と理由、残した重要な振る舞い、実行コマンドと結果、未検証・保留事項を報告する。件数や時間を示す場合は実測し、パラメータ化によるテスト宣言数の減少と実行ケース数の減少を区別する。
