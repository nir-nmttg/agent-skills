# Sol と Opus による設計レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が考えた設計を、Sol（Codex CLI の GPT-6.1 Sol）と Opus（`opus-reviewer`）に**同じ依頼で**レビューさせ、その指摘を Claude が吟味する。同じ観点を別のモデルで見て、単一モデルの見落としを補う。どちらも要件と設計から読み解くので、実装者の不安に注意が偏らない。プロンプトの組み立てと Codex の呼び出しはスクリプトに任せ、Claude は「要件と設計書をまとめる」「指摘を判断する」だけを行う。結果は `artifacts/design-cross-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Claude が設計や実装計画をまとめ、ユーザーに提示する（または実装を始める）前に、次の基準で判断する。**迷ったら使う。**

**使う**: 作り方の判断を含む設計や実装計画すべて。たとえば次のもの。

- 新しい機能・画面・API・モジュールを作る、新しいライブラリやアーキテクチャ上の仕組みを持ち込む
- 複数の案を比べて 1 つを選ぶ（選ばなかった案との比較を独立に確かめる）
- DB スキーマ、公開 API・インターフェース、設定ファイルの形式、データ移行、認証・権限・課金・個人情報・秘密情報、並行処理、キャッシュ、分散、再試行、データの整合性、後から戻しにくいもの（外部公開、互換性を壊す変更、データの削除・変換）に触れる
- 外部のツール・ライブラリ・プラットフォーム・API の挙動を前提にする（公式の資料や実際の動作で確かめていない前提を含む）
- 既存の設計・規約・命名から外れる
- haiku-implementation で Haiku に任せる前の、分割や指示書の前提を決める

**使わない**（設計の欠陥が起こりえない、次の場合だけ）

- 設計の判断を含まない変更: 原因と直し方が一通りに決まる修正、意味や動作を変えない修正（typo・整形・コメント）
- ユーザーが「レビューは不要」と言っている
- 下の「レビュアーの決め方」で、動かす担当が残らない

**再レビュー**: 要否は、直した分だけで判断する。レビューで重要度「高」の指摘を直したとき、または直す中で指摘の範囲を超えて設計を足したり、新たにリスク領域に触れたりしたときにもう一度使う。レビューには同じ要件と、直した設計書の全体を渡す。担当は下の「レビュアーの決め方」で決め、この会話で片方だけを指定されていれば同じ担当にする。同じ設計への再レビューは 2 回までにし、残る指摘はユーザーに伝える。

**自分の判断で使うときの違い**

- 見つけるのは設計の欠陥（前提の誤り・要件の抜け・壊れやすい構造）。壊れ方は Astra（codex-risk-design-review）が見るので、両方の条件に当たれば両方を使う。
- 設計が codex-risk-design-review の「聞く」条件（データ移行・認可・課金・外部への送信など、壊れると影響が大きく戻しにくいもの）に当たるとき、または当たるか迷うときは、先に codex-risk-design-review の聞き方で Astra を加えるかをユーザーに聞く（そのスキルの「聞かない」に当たるとき、たとえばユーザーが「急ぎ」と言っているときは聞かず、Astra なしで進める）。加えると選ばれたら、codex-risk-design-review の手順で、このスキルと並べて実行する（Astra の設計書・指摘のまとめ方・報告の形式はそちらに従う）。
- 始める前に「提示する前に <動かす担当> に要件と設計だけでレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。
- まだユーザーに見せていない Claude 自身の設計案なので、5. で「採用」とした指摘は設計に反映してから提示してよい。その場合も、5. の表で何を採用し何を変えたかを示す。

## レビュアーの決め方

次の順に決める。

1. **指定**: `--only sol`・`--only opus`、または「Sol だけ」「Codex だけ」「Opus だけ」と言われたら、その担当だけを動かす（レビュー済みでも動かす）。`--only` の値が `sol` / `opus` 以外なら、そのことを伝えて止める。「Opus で設計をレビューして」「Codex にレビューしてもらって」のように名前を挙げただけの依頼は、指定に数えない。
2. **直接の依頼**: `/design-cross-review` やレビューを頼まれたら、レビュー済みでも Sol と Opus を動かす。
3. **自分の判断で使うとき**: Sol と Opus を対象にする。そこから、同じ設計をこの会話ですでにレビューして結果を受け取った担当を除く。残りがなければ動かさない。

## 手順

### 1. 引数を読む

- `--only` は「レビュアーの決め方」に使う（`prepare.sh` には渡さない）。
- ファイルパスがあれば、それをレビュー対象の設計書とする（3. で要件と設計に分けて写す）。
- パスがなければ、この会話で Claude が考えた直近の設計案を対象にする。設計案が会話にないときは、何をレビューするかを尋ねて終わる。
- `--cd <dir>` があれば、4. の `prepare.sh` に渡す。設計が今のフォルダ以外のリポジトリについてのものなら、`--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

設計の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。動かす担当はこの 1 つのフォルダを共有する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 要件と設計書を書く

出力された「要件」と「設計書」のパスに、Write ツールで Markdown を書く。レビュアーはこの会話を見られないので、この 2 つだけで判断できるように書く。

**要件**: 依頼した人の立場で「何を求めたか」を書く。

- **依頼と背景**: ユーザーの元の依頼。できるだけユーザーの言葉のまま引用し、会話でわかった背景（なぜ今か）を添える
- **要件・受け入れ条件**: 機能要件、非機能要件、変えてはいけないもの。番号を振る（R1, R2, …）
- **ユーザーが決めた仕様・制約**: 会話の中でユーザーが決めた「何をするか」「何をしないか」。ユーザー自身が作り方を指定したなら、それも制約として書く
- **スコープ外**: ユーザーが明示的に外したもの

要件があいまいなら、あいまいなまま書く（Claude の解釈で補わない）。

**設計書**: 設計そのものを書く。

- **設計**: 構成、データの流れ、主要なインターフェース、状態の持ち方（必要なら Mermaid 図）。データの移行やリリースの手順があれば含める
- **検討した代替案**と選ばなかった理由
- **関連する既存コード**: 作業フォルダからの相対パス（レビュアーが読んで確かめる）
- **外部の挙動の前提**: 設計が外部のツール・ライブラリ・API の挙動に頼るなら、確かめた版、公式の資料の該当箇所（URL と短い引用）、試した結果を書く。確かめていない前提は「未確認」と書き、実装に入る前に確かめる（レビュアーは外部にアクセスできないので、設計書にない根拠は確かめられない）

Claude が自信のない判断は、自分で確かめるか、ユーザーへの確認に回す。設計書には書かず、レビュアーの注意を偏らせない。

ファイルで渡された設計書は、要件にあたる部分を要件へ、設計を設計書へ分けて写し、書いた人の不安の記述は写さない。この会話で設計したのでなければ、要件はわかる範囲で書く。秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. レビューさせる

まず、同じ依頼（`prompt.md`）を作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/prepare.sh" [--cd <dir>] <実行フォルダ>
```

続けて、動かす担当を**同じメッセージで**動かす。**すべて終わるまで、要件・設計書と読み先のコードを編集しない。**

Sol は Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと 10 分以上かかる）。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} <実行フォルダ>
```

Opus は Agent ツールで呼ぶ。

- `subagent_type`: `opus-reviewer`（必ず指定する。`fork` や省略で会話を引き継ぐ形にしない）
- `effort`: 上の「Claude の推論レベル」。空や `auto` のときは `high`
- `model`: **渡さない**（引数は別名しか受け付けず、親と同じ系統なら親のモデルになって、定義の `claude-opus-5-5` の固定が外れる）
- `prompt`: 次の 1 行だけにする

  ```text
  <実行フォルダ>/prompt.md を読み、その指示に従ってレビューしてください。
  ```

- どちらも終わると通知が来るので、それまで待つ。ポーリングはしない。
- Opus の返答は、そのまま `<実行フォルダ>/review-opus.md` に Write で保存する。Sol の結果は `<実行フォルダ>/review.md` に保存される。
- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- Sol は読み取り専用のサンドボックスと 1M コンテキストで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。Opus は Read / Grep / Glob しか使えず、この会話・auto memory・ユーザー用の CLAUDE.md・MCP は読み込まない。
- `prepare.sh` が失敗したら、原因（要件や設計書の書き忘れなど）を直して実行し直す。直せないときは、そのことを伝えてレビューなしで設計を提示する。
- 片方が失敗したら、全部の結果が出揃ってから、成功した分で判断して失敗を報告する。どれも結果を返さなかったら、そのことを伝えてレビューなしで設計を提示し、実行状態を `decisions.md` に残す。
- `codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。`opus-reviewer` が見つからないときは、エージェントがリンクされていない（このスキル集の `scripts/link-skills.sh --claude` で `~/.claude/agents` にリンクする）か、リンクする前に始めたセッション。

### 5. 指摘を判断して報告する

すべての結果が揃ってから、「要件ごとの判定」で「一部だけ」「満たさない」「判断できない」としたものを確かめる。判定が食い違えば、R 番号ごとに設計とコードで確かめる。

同じ原因の指摘を 1 件にまとめ、見つけた担当を頭に書く（`[Sol]`・`[Opus]`・`[Sol・Opus]`・`[Astra]`）。指摘はうのみにしない。必要なら指摘されたファイルを Read / Grep で確かめ、根拠をもって判断する。誤りなら「不採用」とし、理由を書く。

判断の表、各レビューの実行状態（成功・失敗・省略）、件数の行を `<実行フォルダ>/decisions.md` に Write で保存する。あとでモデルごとの効果を確かめるのに使う。

Sol を動かしたら、スクリプトの出力の先頭（設定・所要時間・保存先・`codex resume` の行）をそのまま表示する。Opus を動かしたら、設定（`opus-reviewer` / effort）・所要時間とトークン（完了の通知）・保存先を短く添える。続けて次を日本語で簡潔に書く。レビューの全文は貼らない（保存先にある）。

```markdown
## レビューの総評
（動かした担当ごとに 1 行で要約）

## 要件の充足
（どちらかが「満たす」以外とした要件と、その扱い。すべて満たしていれば「すべて満たす」の 1 行）

## 指摘への判断
| 重要度 | 指摘 | 判断 | 理由 |
| --- | --- | --- | --- |
| 高 | [Sol・Opus] ... | 採用 / 一部採用 / 不採用 / 要確認 | ... |

両方 n 件、Sol だけ n 件、Opus だけ n 件（うち採用 n 件、不採用 n 件）

## 設計の修正案
（採用した指摘をもとに、設計のどこをどう変えるか。箇条書きで）

## ユーザーに確認したいこと
（「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 件数の行は Sol と Opus の両方が成功した回だけ書き、それ以外は「比較なし」と書く。
- 修正案は提案にとどめ、設計書やコードはユーザーの了承なしに書き換えない（自分の判断で使った場合の、提示前の設計案への反映は除く）。
- 修正後にもう一度レビューする場合は、新しい実行フォルダに同じ要件と、修正した設計書の全体を書いて 2. からやり直す。要件の解釈を変えたときは、そのことを報告で伝える。前回の指摘や対応は書かない（先入観を渡さないため）。
