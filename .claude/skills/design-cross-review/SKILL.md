# Astra と Fable による設計レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が考えた設計を、Astra（Codex CLI の GPT-6 Astra）と Fable（`fable-reviewer`）に**同じ依頼で**レビューさせ、その指摘を Claude が吟味する。同じ観点を別のモデルで見て、単一モデルの見落としを補う。どちらも要件と設計から読み解くので、実装者の不安に注意が偏らない。要件との一致や前提の誤りに加えて、データ・認可・お金・外部への送信・移行・並行処理など壊れると影響の大きい部分では、壊れ方と戻しやすさも重点的に見る。Astra が使えないときは Sol（GPT-6.1 Sol）で、Fable の利用枠が足りないときは Opus（`opus-reviewer`）で代わりに動かす。直したあとの再レビューは、直した部分の確認に絞って Astra に任せる。プロンプトの組み立てと Codex の呼び出しはスクリプトに任せ、Claude は「要件と設計書をまとめる」「指摘を判断する」だけを行う。結果は `artifacts/design-cross-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Claude が設計や実装計画をまとめ、ユーザーに提示する（または実装を始める）前に、次の基準で判断する。**迷ったら使う。**

**使う**: 作り方の判断を含む設計や実装計画すべて。たとえば次のもの。

- 新しい機能・画面・API・モジュールを作る、新しいライブラリやアーキテクチャ上の仕組みを持ち込む
- 複数の案を比べて 1 つを選ぶ（選ばなかった案との比較を独立に確かめる）
- DB スキーマ、公開 API・インターフェース、設定ファイルの形式、データ移行、認証・権限・課金・個人情報・秘密情報、並行処理、キャッシュ、分散、再試行、データの整合性、後から戻しにくいもの（外部公開、互換性を壊す変更、データの削除・変換）に触れる
- 外部のツール・ライブラリ・プラットフォーム・API の挙動を前提にする（公式の資料や実際の動作で確かめていない前提を含む）
- 既存の設計・規約・命名から外れる
- haiku-implementation で Haiku に任せる前の、分割や指示書の前提を決める

**使わない**（設計の欠陥が起こりえない、次の場合だけ）

- 設計の判断を含まない変更: 原因と直し方が一通りに決まる修正、意味や動作を変えない修正（typo・整形・コメント）
- ユーザーが「レビューは不要」と言っている
- 下の「レビュアーの決め方」で、動かす担当が残らない

**再レビュー**: 1 回目のレビューで別のモデルどうしの目は通っているので、再レビューは直した部分の確認に絞り、Astra に任せる（下の「確認のレビュー」）。確かめるのは、直しで元の問題が解決したか、直したことで新しい欠陥が生じていないか、直した節とほかの節の前提がずれていないか。1 か所の直しがほかの節に響くことがあるので、レビューには同じ要件と、直した設計書の全体を渡す。要否は直した分だけで判断し、重要度「高」の指摘を直すために新しい仕組み（状態・ロック・再試行・新しいメッセージや項目など）を設計に足したとき、直す中で指摘の範囲を超えて設計を足したとき、新たにリスク領域に触れたときに使う。この条件に当たらなければ使わない。直す中で選ぶ案か要件の解釈を変えたときは、直した部分の確認では足りないので、1 回目と同じく Astra と Fable にゼロからレビューさせる（下の「ゼロからレビューし直すとき」）。どちらも再レビューに数え、同じ設計への再レビューは 1 回までにし、残る指摘はユーザーに伝える。

**自分の判断で使うときの違い**

- 見つけるのは設計の欠陥（前提の誤り・要件の抜け・壊れやすい構造・戻しにくい判断）。
- 始める前に「提示する前に <動かす担当> に要件と設計だけでレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。
- まだユーザーに見せていない Claude 自身の設計案なので、5. で「採用」とした指摘は設計に反映してから提示してよい。その場合も、5. の表で何を採用し何を変えたかを示す。

## レビュアーの決め方

次の順に決める。

1. **指定**: `--only astra`・`--only fable`、または「Astra だけ」「Codex だけ」「Fable だけ」と言われたら、その担当だけを動かす（レビュー済みでも動かす）。`--only` の値が `astra` / `sol` / `fable` / `opus` 以外なら、そのことを伝えて止める。「Fable で設計をレビューして」「Codex にレビューしてもらって」のように名前を挙げただけの依頼は、指定に数えない。
2. **直接の依頼**: `/design-cross-review` やレビューを頼まれたら、レビュー済みでも Astra と Fable を動かす。
3. **自分の判断で使うとき**: Astra と Fable を対象にする。そこから、同じ設計をこの会話ですでにレビューして結果を受け取った担当を除く。残りがなければ動かさない。

「Sol で」と言われたとき、`--only sol` や「Sol だけ」と言われたとき、この会話で Astra がモデルを使えない・プランの対象外の理由で失敗していたときは、Astra の代わりに Sol で動かす（4. で `--model gpt-6.1-sol` を渡す。`--only sol`・「Sol だけ」なら Fable は動かさない）。

「Opus で」と言われたとき、`--only opus` や「Opus だけ」と言われたとき、4. で確かめた Fable の利用枠が足りないとき、利用枠を確かめられないうえに、この会話で Fable が利用枠の不足で失敗していたときは、Fable の代わりに Opus（`opus-reviewer`）で動かす（`--only opus`・「Opus だけ」なら Astra は動かさない）。Opus で代わりに動かした回も Fable の担当として数え、レビュー済みの担当を除くときも同じに扱う。

確認のレビューは Astra（使えなければ上のとおり Sol）1 体で動かす。ユーザーが 1. で担当を指定していたときはその担当、この会話で Astra が `codex` が見つからない・ログインしていない・ネットワークなどの理由で動かなかったときは Fable（利用枠によっては Opus）で動かす。

## 手順

### 1. 引数を読む

- `--only` は「レビュアーの決め方」に使う（`prepare.sh` には渡さない）。
- ファイルパスがあれば、それをレビュー対象の設計書とする（3. で要件と設計に分けて写す）。
- パスがなければ、この会話で Claude が考えた直近の設計案を対象にする。設計案が会話にないときは、何をレビューするかを尋ねて終わる。
- `--cd <dir>` があれば、4. の `prepare.sh` に渡す。設計が今のフォルダ以外のリポジトリについてのものなら、`--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

設計の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。動かす担当はこの 1 つのフォルダを共有する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 要件と設計書を書く

出力された「要件」と「設計書」のパスに、Write ツールで Markdown を書く。レビュアーはこの会話を見られないので、この 2 つだけで判断できるように書く。

**要件**: 依頼した人の立場で「何を求めたか」を書く。

- **依頼と背景**: ユーザーの元の依頼。できるだけユーザーの言葉のまま引用し、会話でわかった背景（なぜ今か）を添える
- **要件・受け入れ条件**: 機能要件、非機能要件、変えてはいけないもの。番号を振る（R1, R2, …）
- **ユーザーが決めた仕様・制約**: 会話の中でユーザーが決めた「何をするか」「何をしないか」。ユーザー自身が作り方を指定したなら、それも制約として書く
- **スコープ外**: ユーザーが明示的に外したもの

要件があいまいなら、あいまいなまま書く（Claude の解釈で補わない）。

**設計書**: 設計そのものを書く。

- **設計**: 構成、データの流れ、主要なインターフェース、状態の持ち方（必要なら Mermaid 図）。データの移行やリリースの手順（既存データの扱い、デプロイの順序、新旧のコードが混在する期間、ロールバックの方法）があれば含める
- **本番の前提**: わかる範囲で、データの量、同時実行の度合い、外部サービスの制約。わかっている事実だけを書き、推測で補わない
- **検討した代替案**と選ばなかった理由
- **関連する既存コード**: 作業フォルダからの相対パス（レビュアーが読んで確かめる）
- **外部の挙動の前提**: 設計が外部のツール・ライブラリ・API の挙動に頼るなら、確かめた版、公式の資料の該当箇所（URL と短い引用）、試した結果を書く。確かめていない前提は「未確認」と書き、実装に入る前に確かめる（レビュアーは外部にアクセスできないので、設計書にない根拠は確かめられない）

Claude が自信のない判断は、自分で確かめるか、ユーザーへの確認に回す。設計書には書かず、レビュアーの注意を偏らせない。

ファイルで渡された設計書は、要件にあたる部分を要件へ、設計を設計書へ分けて写し、書いた人の不安の記述は写さない。この会話で設計したのでなければ、要件はわかる範囲で書く。秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. レビューさせる

まず、同じ依頼（`prompt.md`）を作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/prepare.sh" [--cd <dir>] <実行フォルダ>
```

続けて、動かす担当を**同じメッセージで**動かす。**すべて終わるまで、要件・設計書と読み先のコードを編集しない。**

Astra は Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと数十分かかることがある）。Sol で動かすときは `--effort` の前に `--model gpt-6.1-sol` を加える。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} <実行フォルダ>
```

Fable は Agent ツールで呼ぶ。Fable を動かす予定なら、呼ぶ前に利用枠を確かめて、Fable と Opus のどちらで動かすかを決める。

- `mcp__ccd_session_mgmt__get_usage` を呼ぶ（読み込まれていなければ ToolSearch で `select:mcp__ccd_session_mgmt__get_usage` を読み込む）。`plan.windows` のうちラベルに Fable を含む枠の `percentUsed` が 1 つでも 95 以上なら、Fable の代わりに Opus で動かす（レビューを最後まで終えられる残りを確保するため）。`--only fable`・「Fable だけ」のときも同じにする。Opus に変えたときは、どの場合もそのことを 1 行伝える。
- ツールがない（ターミナルの Claude Code など）、呼び出しが失敗した・断られた、`plan.status` が `ok` でない、Fable の枠がないときは、利用枠を確かめられないとして Fable で動かす（この会話で Fable が利用枠の不足で失敗していたときは Opus で動かす）。この確認は担当を選ぶためだけに使い、結果によらずレビューと呼び出し元の作業を進める。
- この確認は担当を動かす前に済ませ、動かす担当はそのあと同じメッセージで動かす。

Agent ツールには次を指定する。

- `subagent_type`: `fable-reviewer`、Opus で動かすときは `opus-reviewer`（必ず指定する。`fork` や省略で会話を引き継ぐ形にしない）
- `effort`: 上の「Claude の推論レベル」。空や `auto` のときは `high`
- `model`: **渡さない**（引数は別名しか受け付けず、親と同じ系統なら親のモデルになって、定義の `claude-fable-5-2`・`claude-opus-5-5` の固定が外れる）
- `prompt`: 次の 1 行だけにする

  ```text
  <実行フォルダ>/prompt.md を読み、その指示に従ってレビューしてください。
  ```

- どちらも終わると通知が来るので、それまで待つ。ポーリングはしない。
- Fable の返答は、そのまま `<実行フォルダ>/review-fable.md`（Opus なら `review-opus.md`）に Write で保存する。Astra（または Sol）の結果は `<実行フォルダ>/review.md` に保存される。
- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- Codex（Astra / Sol）は読み取り専用のサンドボックスと 1M コンテキストで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。Fable・Opus は Read / Grep / Glob しか使えず、この会話・auto memory・ユーザー用の CLAUDE.md・MCP は読み込まない。
- `prepare.sh` が失敗したら、原因（要件や設計書の書き忘れなど）を直して実行し直す。直せないときは、そのことを伝えてレビューなしで設計を提示する。
- Astra が、モデルを使えない・プランの対象外・使用量の上限などの理由で失敗したら、同じ実行フォルダに対して `--model gpt-6.1-sol` を加えて、Sol で 1 回だけやり直す（同じく `run_in_background: true`）。やり直すと Astra のログは上書きされるので、先に Astra の失敗の理由（エラーの要点）を控え、5. で `decisions.md` の実行状態に書く。その担当は報告で Sol と書く。モデルによらない失敗（`codex` がない・ログインしていない・ネットワークなど）はやり直さない。
- Fable が、利用枠・使用量の上限・レート制限などの理由で失敗したら、`opus-reviewer` で同じ 1 行の依頼を 1 回だけやり直す（Agent ツールの指定は Fable と同じ）。先に Fable の失敗の理由（エラーの要点）を控え、5. で `decisions.md` の実行状態に書く。その担当は報告で Opus と書く。利用枠によらない失敗（エージェントが見つからないなど）はやり直さない。
- 片方が失敗したら、全部の結果が出揃ってから、成功した分で判断して失敗を報告する。どれも結果を返さなかったら、そのことを伝えてレビューなしで設計を提示し、実行状態を `decisions.md` に残す。
- `codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。`fable-reviewer`・`opus-reviewer` が見つからないときは、エージェントがリンクされていない（このスキル集の `scripts/link-skills.sh --claude` で `~/.claude/agents` にリンクする）か、リンクする前に始めたセッション。

### 5. 指摘を判断して報告する

すべての結果が揃ってから、「要件ごとの判定」で「一部だけ」「満たさない」「判断できない」としたものを確かめる。判定が食い違えば、R 番号ごとに設計とコードで確かめる。

同じ原因の指摘を 1 件にまとめ、見つけた担当を頭に書く（`[Astra]`・`[Fable]`・`[Astra・Fable]`。Sol・Opus で代わりに動かしたときは、Astra を Sol、Fable を Opus と書く）。指摘はうのみにしない。必要なら指摘されたファイルを Read / Grep で確かめ、根拠をもって判断する。誤りなら「不採用」とし、理由を書く。

**設計に入れるかどうか**: 正しいと確かめた指摘でも、設計に入れるかどうかは別に決める。入れると仕組み・状態・設定が増え、増えた分が新しい不具合の元になり、次のレビューで読まれる範囲も広がる。入れて防げる害が、増える複雑さに見合うものだけを「採用」にする。

- 重要度「高」（データの破損・消失、セキュリティの穴、お金の誤り、戻せない判断、要件を満たせない設計）は採用する。重要度はレビュアーの付けたものをうのみにせず、この定義で付け直す。付け直したときは、表の重要度を `高→中` のように両方書き、理由の欄に根拠を書く。
- 重要度「中」は、要件の範囲の中（この設計で壊れる既存の動きを含む）で、本番の前提（3. に書いたもの。なければこのプロジェクトの使われ方）で現実に起こりうるものを採用する。特殊な条件が重ならないと起きないものや、防ぐのに新しい仕組み（ロック・再試行・状態の記録など）が要る割に起きたときの害が小さいものは「見送り」にする。
- 重要度「低」は「見送り」にする。入れても仕組みが増えないもの（意味を変えない誤記の修正、記述どうしの食い違いを片方に合わせる修正）は採用してよい。条件・手順・例外の追記は、仕組みを足す修正に当たる。
- 確認のレビューの回は、直した部分に関わる指摘だけを上の基準で判断する。それ以外の箇所の指摘は、重要度「高」を除いて「見送り」にする（確認のレビューの目的は、直したことで生じた欠陥を見つけること）。「修正ごとの判定」で「解決」以外とされたものも、設計とコードで確かめる。

「見送り」は、指摘の正しさを認めたうえで設計に入れないもの。指摘が誤りの「不採用」とは分けて書き、ユーザーに入れるよう言われたら入れる。

判断の表、各レビューの実行状態（成功・失敗・省略）、件数の行を `<実行フォルダ>/decisions.md` に Write で保存する。あとでモデルごとの効果を確かめるのに使う。

Astra（または Sol）を動かしたら、スクリプトの出力の先頭（設定・所要時間・保存先・`codex resume` の行）をそのまま表示する。Fable（または Opus）を動かしたら、設定（`fable-reviewer` または `opus-reviewer` / effort）・所要時間とトークン（完了の通知）・保存先を短く添える。続けて次を日本語で簡潔に書く。レビューの全文は貼らない（保存先にある）。

```markdown
## レビューの総評
（動かした担当ごとに 1 行で要約）

## 要件の充足
（どちらかが「満たす」以外とした要件と、その扱い。すべて満たしていれば「すべて満たす」の 1 行）

## 指摘への判断
| 重要度 | 指摘 | 判断 | 理由 |
| --- | --- | --- | --- |
| 高 | [Astra・Fable] ... | 採用 / 一部採用 / 見送り / 不採用 / 要確認 | ... |

両方 n 件、Astra だけ n 件、Fable だけ n 件（うち採用 n 件、見送り n 件、不採用 n 件）

## 設計の修正案
（採用した指摘をもとに、設計のどこをどう変えるか。箇条書きで）

## 実装・リリースで守ること
（「実装・リリースで守るべきこと」のうち妥当なもの。なければ省く）

## ユーザーに確認したいこと
（「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 件数の行は Codex の担当（Astra または Sol）と Claude の担当（Fable または Opus）の両方が成功した回だけ書き、それ以外は「比較なし」と書く。
- 「見送り」があれば、表のあとに「入れたいものがあれば指示してください」と 1 行添える。
- 「実装・リリースで守ること」は、実装に入ったら守る。
- 修正案は提案にとどめ、設計書やコードはユーザーの了承なしに書き換えない（自分の判断で使った場合の、提示前の設計案への反映は除く）。
- 修正後にもう一度レビューするのは、上の「再レビュー」の条件に当たるときだけにし、下の「再レビューの手順」で行う。SendMessage で続けず、新しい実行フォルダと新しいエージェントで動かす。

## 再レビューの手順

### 確認のレビュー

1. 前回（1 回目）の実行フォルダを指定して、新しい実行フォルダを作る。要件と設計書は前回から写される。「再レビューは 1 回まで」と出たら上限なので、残る指摘をユーザーに伝える（示された作成済みのフォルダでまだレビューしていなければ、そのフォルダで続ける）。

   ```bash
   bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" --followup <前回の実行フォルダ> <slug>-r2
   ```

2. 写された設計書の、直した節だけを Edit ツールで書き換える（全体を書き直すと、直していない節の言い回しまで差分に入る）。
3. 出力された「修正の一覧」のパスに、Write ツールで次を書く。レビュアーは、これと直した設計書で直しを確かめる。
   - **直したこと**: 前回の判断で採用した指摘ごとに、指摘の要約と、設計のどこをどう変えたか。「一部採用」は入れた部分を書く。採用した指摘のほかに変えたもの（ユーザーに頼まれて入れた見送りなど）も書く
   - **決定済み**: 「見送り」「不採用」「要確認」にした指摘と、一部採用で入れなかった部分を、1 行の理由とともに書く
   - 直した理由の弁解や、Claude が自信のない判断は書かない（レビュアーの注意を偏らせない）
4. 手順の 4. と同じく `prepare.sh` を実行する。`--cd` を省けば前回の作業フォルダを使う。前回の設計書からの差分も渡る。前回の実行フォルダが見つからないなどで失敗したら、`--followup` を付けずに新しい実行フォルダを作り、手順の 2. から、確認のレビューの担当 1 体で設計書の全体をレビューする（前回の指摘や対応は書かない）。
5. 「レビュアーの決め方」で決めた確認のレビューの担当 1 体を、手順の 4. と同じ呼び方で動かす。**終わるまで、設計書と読み先のコードを編集しない。**
6. 手順の 5. と同じく判断し、`decisions.md` の実行状態に「確認のレビュー（前回: <前回の実行フォルダ名>）」と書く。
7. 再レビューで採用した指摘（「未解決」とされた直しを含む）は、直し方が一通りに決まるものだけ設計に入れ、報告に「確認のレビューのあとの修正（未レビュー）」として挙げる。仕組みを足さないと直せないものは入れず、ユーザーに伝える。
8. 手順の 5. の形で報告する。「要件の充足」は「修正ごとの判定」（「解決」以外のものと、その扱い）に替え、件数の行は「比較なし」と書く。担当が結果を返さなかったら、報告に「直した部分は未確認」と書いて直したことの一覧を添える。

### ゼロからレビューし直すとき

選ぶ案か要件の解釈を変えたときは、`--followup` を付けずに新しい実行フォルダを作り、1 回目と同じく手順の 2. から Astra と Fable でやり直す。要件と、変えたあとの設計書の全体を書き、前回の指摘や対応は書かない（先入観を渡さないため）。要件の解釈を変えたことは報告で伝える。この回で採用した指摘も、確認のレビューの 7. と同じ扱いにする。
