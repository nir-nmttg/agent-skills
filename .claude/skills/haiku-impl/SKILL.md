# Haiku 5.5 に実装を任せる

引数: $ARGUMENTS

コードを書く作業を、この会話を共有しない Haiku 5.5 のサブエージェント `haiku-implementer` に任せ、Claude は「分割する」「指示書を書く」「差分をレビューして反映する」「仕上げる」だけを行う。Claude が自分でコードを読み書きする量を減らし、その間に別の作業を進めて、全体の時間とコンテキストを節約するのが目的。モデル・推論レベル（max）・使えるツールはエージェントの定義で固定している。結果は `artifacts/haiku-impl/` に保存される。

Haiku は Claude の使用量になる（Haiku は安いが無料ではない）。**1 本ずつ順番に任せるより、独立した小タスクに分けて並行で動かす**のを基本にする。各 Haiku は専用の git worktree で動くので互いにぶつからず、その間 Claude は作業フォルダで Haiku に向かない部分を進められる。進み具合はデスクトップアプリの Background tasks から見たり止めたりできる。

## 前提

- Haiku はサンドボックスなしで、メインのセッションと同じ権限モードで動く。**メインのセッションが auto モード**であることを前提にする（分類器が Haiku の操作も判定する）。
  - default モードでは、Haiku の Bash の確認がメインのセッションに次々と出る。並行数を 1〜2 本に減らすか、そのことをユーザーに伝えてから使う。
  - bypassPermissions では、下の guard.sh だけが歯止めになる。
- `haiku-implementer` の hook（`scripts/guard.sh`）が、worktree の外への書き込み、`cd <worktree> &&` で始まらない Bash（サブエージェントの Bash は毎回メインの作業フォルダで始まるため）、リポジトリの状態を変える git コマンド、依存パッケージのインストールを止める。事故防止のためのもので、悪意のある回避は想定していない。
- エージェントの定義（`~/.claude/agents/haiku-implementer.md`）と hook のスクリプト（`~/.claude/skills/haiku-impl`）は、このスキル集の `scripts/link-skills.sh --claude` でリンクしておく。prepare.sh がリンクを確かめる。

## いつ使うか

ユーザーに頼まれたときに加えて、頼まれていなくても積極的に使う。Claude がこれから実装に取りかかるときに次の基準で判断する。実装の全体が当てはまらなくても、当てはまる部分だけを任せ、残りは Claude が並行して書く。

**任せる部分**（すべてに当たる）

- 要件と完了の条件がはっきりしていて、指示書に検証できる形で書ける（ユーザーとの会話や Issue・設計書で決まっている）
- まねできる既存の実装がある、または量は多いが判断は少ない作業（既存パターンに沿った機能追加・CRUD・画面・API、テストの追加、機械的な置き換え）
- テスト・型チェック・リンターのどれかで確かめられる（DB や Docker が要るテストも、ロックつきで Haiku が実行できる）
- 250 行以上（目安。テストを含む追加・変更の合計）の作業（大きければ分割する。上限はない）

**任せない部分**（Claude が自分で書く）

- 250 行に満たない作業、原因と直し方が明らかなバグ修正（指示書を書いて差分を読むより、Claude が直接書く方が速い）
- 要件があいまい、設計から考える必要がある（先に設計を固め、codex-design-review の条件で設計レビューを使う）
- 原因のわからないバグの調査
- 外部サービス・認証情報がないと動かせない・確かめられない
- 認証・権限・課金・個人情報・秘密情報の扱いに関わる（細かいレビューが要り、任せても速くならない）
- ユーザーが「自分で書いて」「Haiku は使わないで」と言っている、または急ぎで待てない

250 行以上の作業で、ほかの条件に当たるか迷ったら任せる。250 行に満たないなら迷わず Claude が書く。実装の全体が「任せない部分」に当たっても、テストの追加や既存パターンに沿った周辺の作業など、250 行以上の切り出せる部分があればそこだけでも任せる。

**自分の判断で使うときの違い**

- 始める前に「〇〇 は Haiku 5.5 N 本に並行で任せ、Claude は △△ を進めてからレビューします」と 1 行だけ伝え、確認は待たずに進める。
- `haiku-implementer` が見つからない・prepare.sh がリンクの不足で止まった・エラーで動かなかったときは、そのことを 1 行伝えて Claude が自分で実装する（途中までの変更が worktree に残っていれば、diff.sh で確かめて踏まえる）。

頼まれて使うときに向いていないと判断したら、その理由を 1 行伝え、Claude が自分で実装するかユーザーに確認する。

## 手順

### 1. 引数を読む

- 実装してほしいことを読み取る。足りない前提（どの画面・どの API か、完了の条件など）があり、推測では決められなければユーザーに確認する。
- 対象が今のフォルダ以外のリポジトリなら、4. の prepare.sh に `--cd <そのリポジトリのパス>` をつける。

### 2. 分ける

実装を、Haiku に任せる小タスクと Claude が書く部分に分ける。

- **小タスクどうしは独立させる**: できるだけ別々のファイルを触り、ほかの小タスクの成果物を前提にしない。分け方の例: 画面ごと・API エンドポイントごと・モジュールごと、既存実装に対するテストの追加、ディレクトリごとの機械的な置き換え。
- **共通の土台が要るなら先に作る**: 複数の小タスクが使う型・スキーマ・インターフェース・共通関数は、先に Claude が書く（または Haiku 1 本に任せて反映する）。未コミットのままでよい（worktree は未コミットの変更を含めて切られる）。土台ができてから小タスクを並行で動かす。
- **同時に動かすのは 4 本まで**を目安にする。それより多ければ、終わった分から順に次を動かす。
- 1 本あたりも 250 行以上を目安にし、それより細かくは分けない（指示書を書いて差分を読む手間が本数だけ増える）。分けるほどでもない大きさなら 1 本でよい（1 本でも worktree で動かす）。

### 3. 実行フォルダを作り、指示書を書く

小タスクごとに、内容を表す短い英数字の名前（例: `csv-export`）を決めて実行フォルダを作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

出力された「実装の指示」のパスに、Write ツールで Markdown を書く。Haiku はこの会話もほかの小タスクも見られないので、指示書だけで実装できるように書く。ただし時間とコンテキストの節約が目的なので、Claude がコードを読み込むのは指示書に必要な範囲（関連ファイルの特定、既存パターンの確認）にとどめ、細部の調査は Haiku に任せる。作業場所のルートの CLAUDE.md・AGENTS.md は prepare.sh が Haiku に渡すので、そこにあるルールは書き写さなくてよい。

- **目的**: 何のための変更か
- **要件・受け入れ条件**: 何ができれば完了か。箇条書きで検証できる形に
- **手がかり**: 関係しそうなファイル・関数、まねるべき既存の実装（リポジトリのルートからの相対パスで書く。Haiku は worktree の中で読み替える）
- **決定事項**: ユーザーとの会話で決まったこと
- **やらないこと**: スコープ外にするもの。並行で動かすときは、ほかの小タスクや Claude が担当するファイルを「触らないファイル」として書く
- **確認方法**: 実行してほしいテスト・型チェックのコマンド（わかれば）。DB や Docker が要るテストは、worktree のコードをテストするコマンドを、ロックつきの形（`bash <prepare.sh が出す locked.sh のパス> <コマンド>`）で書く（下の「DB や Docker が要るテスト」）。Haiku に「DB を使うか」を判断させない

秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. worktree を用意して Haiku に任せる

小タスクごとに worktree を用意する。作業フォルダの今の状態（未コミットの変更を含む）から `<実行フォルダ>/worktree` が切られ、`prompt.md`（作業場所・ロックのコマンド・プロジェクトの指示・指示書）が作られる。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/prepare.sh" [--cd <dir>] <実行フォルダ>
```

続けて、小タスクごとに Agent ツールで呼ぶ。並行で動かすときは、1 つのメッセージで複数の Agent 呼び出しを同時に出す。

- `subagent_type`: `haiku-implementer`
- `model` と `effort`: **渡さない**（定義の `claude-haiku-5-5` と `max` を使う。`model` に別名を渡すと固定が外れる）
- `prompt`: 次の形で書く

  ```text
  <実行フォルダ>/prompt.md を読み、指示どおりに実装してください。作業場所: <実行フォルダ>/worktree
  ```

- バックグラウンドで動き、終わると 1 本ずつ通知が来る。推論レベル max なので時間がかかることがある。ポーリングはしない。
- **実行中も Claude は作業フォルダで自分の担当部分を進めてよい**（Haiku は worktree の中だけを変える）。待つ間は、Claude の担当部分を書く、次の小タスクの指示書を書く、などを進める。
- 依存パッケージのフォルダ（`node_modules`、`.venv` など）は作業フォルダのものをリンクするので、Haiku もテストを動かせる。Haiku は依存パッケージのインストール・更新はできない（リンク先の作業フォルダを変えてしまうため、guard.sh が止める）。
- Haiku は個人の auto memory やメインの会話を読まず、CLAUDE.md も自動では読まない（`omitClaudeMd`）。作業場所のルートの CLAUDE.md・`.claude/CLAUDE.md`・AGENTS.md は prompt.md で渡る。
- エラーや停止で結果が返らなかったら内容を伝える。途中までの変更が worktree に残っていれば（5. の diff.sh で確かめる）そのことも伝え、続けるか捨てるかをユーザーに確認する（勝手に捨てない）。

**DB や Docker が要るテスト**

Haiku はサンドボックスなしで動くので、DB や Docker を使うテストも自分で実行できる。ただし並行する Haiku どうしが同じテスト用 DB を取り合わないよう、prompt.md の「ロック」のコマンド（`locked.sh`）を通して 1 本ずつ実行させる（待つのは既定で 300 秒まで。`HAIKU_IMPL_LOCK_WAIT` で変えられる）。

- 指示書の「確認方法」は、**作業フォルダではなく worktree のコードをテストするコマンド**にする。たとえば、作業フォルダをマウントしたコンテナで動く `docker compose exec` は、Haiku が書いたコードをテストしない。Docker Compose のプロジェクトなら、worktree をマウントした使い捨てのコンテナで動かす。

  ```bash
  docker compose -f <もとのリポジトリ>/compose.yaml --project-directory <worktree> -p <プロジェクト名> run --rm --no-deps <サービス> <テストのコマンド>
  ```

  `-p` に作業フォルダで動いているプロジェクトの名前（`docker compose ls` で確かめる）を指定すると、DB のコンテナや gem などのボリュームを共有できる。DB のコンテナは先に起動しておく。
- ロックは Haiku どうしの順番を守るだけなので、Haiku が動いている間は、Claude やユーザーが作業フォルダで同じ DB を使うテストを実行しない。
- テストのコマンドは Haiku が書いたコードを動かす。本番環境や外部サービスに書き込むコマンドは指示書に書かない。

### 5. 差分を保存してレビューする

終わった小タスクから順に、差分を保存してレビューする。Haiku の報告はうのみにしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/diff.sh" <実行フォルダ>
```

- 出力された差分（`diff-<回>.patch`。差し戻したあとは、全体の `diff-all.patch` も）を Read で読み、受け入れ条件を満たしているか、既存コードとの整合、エラー処理、セキュリティ、指示書の範囲外の変更がないかを確かめる。必要な周辺コードだけ Read / Grep する。
- 報告の「止められた操作」があれば、Haiku がやろうとして止められたことが実装に影響していないか（テストを実行できていない、など）を確かめる。diff.sh が「HEAD が動いています」と出したら、Haiku が git の状態を変えていないかを確かめる。
- **大きな問題**（要件の取り違え、複数ファイルにまたがる作り直し）は、反映する前に Haiku に差し戻す。実行フォルダの `feedback.md` に、問題点・期待する動き・根拠（`path:line`）を Write で書き（上書きしてよい）、**同じ Haiku に SendMessage** で頼む（同じ worktree と文脈のまま続けられる）。

  ```text
  <実行フォルダ>/feedback.md を読み、同じ作業場所で対応してください。最後の報告は同じ形式で書いてください。
  ```

  終わったらもう一度 diff.sh を実行してレビューする。差し戻しは 2 回までにする。それでも直らなければ、反映してから Claude が直すか、ユーザーに相談する。
- 使えない結果なら、反映せずに捨てて（`apply.sh --discard`）、Claude が書くか指示書を直して新しい実行フォルダで出し直す。

### 6. 作業フォルダに反映する

レビューで問題がなければ作業フォルダに反映する。終わった順に 1 本ずつでも、まとめてでもよい。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/apply.sh" <実行フォルダ>...
```

- worktree を切った時点をベースにした 3-way マージなので、その後に Claude やほかの小タスクが作業フォルダで変えた分とも混ざる。ステージ（インデックス）やブランチには触れない。反映した worktree は片づけられる。
- 競合があると、競合マーカーを残すか `<ファイル>.haiku` に Haiku 版を置き、終了コード 2 で終わる（worktree は残る）。Claude がマーカーを解消し、`.haiku` ファイルを取り込んで消してから、`apply.sh --discard <実行フォルダ>` で worktree を片づける。
- 反映せずに捨てるときは `apply.sh --discard <実行フォルダ>`。

### 7. 仕上げる

- すべて反映したら、作業フォルダで指示書の「確認方法」のテスト・型チェックを実行する（Haiku が worktree で通したテストも、組み合わせた結果としてもう一度確かめる）。小タスクを組み合わせた結果として正しく動くかもここで確かめる。実行は haiku-check スキルに任せ、報告だけを読む。
- **小さな問題**（数行の修正、命名、漏れたエッジケース、小タスクどうしのつなぎ目）は Claude が直接直し、もう一度テストを実行する。
- 不要な変更が混ざっていたら、その部分だけ取り除く。ユーザーのもとからの未コミットの変更には触れない。
- テストが通ったら、codex-impl-review でレビューする（ユーザーが不要と言ったときを除き、Haiku に書かせた変更には必ず使う。2 本以上を組み合わせたなら総合と観点ごとの重点で並列にする）。続けて、opus-final-review も使う（Haiku に実装させた変更は、その条件に当たる）。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 8. 報告する

小タスクごとに、diff.sh の出力の先頭（変更・差分の保存先）と、完了の通知の所要時間・トークンを短くまとめて表示し、続けて次を日本語で簡潔に書く。Haiku の報告の全文や差分は貼らない（保存先にある）。

```markdown
## 分担
| 担当 | 内容 | 結果 |
| --- | --- | --- |
| Haiku: csv-export | ... | 反映済み（差し戻し 1 回） / 破棄して Claude が実装 |
| Claude | ... | 実装済み |

## Claude のレビュー
| 指摘 | 場所 | 対応 |
| --- | --- | --- |
| ... | `path:line` | Claude が修正 / Haiku に差し戻して修正 / 未対応（理由） |

## 確認したこと
（実行したテスト・型チェックとその結果）

## ユーザーに確認したいこと
（Haiku の「判断したこと」やレビューで出た、ユーザーにしか決められないもの。なければ省く）
```
