# 作業を分けて並列に進める

引数: $ARGUMENTS

依頼を独立した作業に分け、作業ごとにいちばん安い手段へ振り分けて同時に進める。Claude が担当するのは「分け方を決める」「共通部分を先に書く」「最長の道筋の上の作業を進める」「終わった作業をつなぐ」だけにする。触るファイルの重なり・依存の循環・実行の順番のチェックと、作業ごとの指示書づくりはスクリプトが行う。計画と指示書は `artifacts/parallel-tasks/` に保存される。

効率を上げるために、次の 4 つを守る。

- **待たない**: 段ごとに足並みをそろえず、依存が終わった作業からすぐに始める。待つ間は Claude が自分の担当を進める。
- **依存を消す**: 複数の作業が使う型・インターフェース・関数のシグネチャを先に決めてスタブとして置き、同時に動かせる作業を増やす。
- **トークンを減らす**: 指示書はスクリプトが作るので Claude は読まない。報告は決まった短い形式で受け取る。
- **確かめるのは最後に 1 回**: テストやレビューは、すべてを反映してからまとめて行う。

## いつ使うか

ユーザーに頼まれたときに加えて、頼まれていなくても、作業に取りかかる前に次の基準で判断する。

**使う**（すべてに当たる）

- 独立して進められる作業が 2 つ以上ある。互いの結果を前提にせず、触るファイルが重ならない（共通の型やインターフェースを先に決めれば独立させられるものも含む）
- そのうち少なくとも 2 つが、それだけで 10 分以上かかるまとまった作業（目安: 実装なら 50 行以上、調査ならファイル 10 個以上を読む）

**使わない**

- 一本道の作業（前の結果を見て次を決める調査、原因のわからないバグの調査）
- 全体が小さい（実装の合計が 100 行未満、読むファイルが数個）
- 要件や設計が決まっていない（先に決める。規模が大きければ codex-design-review を使う）
- ユーザーが「順番に進めて」「並列にしないで」と言っている
- plan モードで計画が承認された直後は、アプリの決まり（独立した手順を別セッションとして提案する）に従う。このスキルは、その手順を選ぶ前に 3.〜4. で重なりと依存を確かめるのにだけ使う

まとまった作業が 2 つあり、使うかどうか迷ったら使う。4. のチェックで「並列にする効果がない」と出たら、そこでやめて順番に進める。

**自分の判断で使うときの違い**

- 始める前に「〇〇 を N 本に分けて並列で進めます（Explore 1・Luna 2・別セッション 1、Claude は △△）」と 1 行だけ伝え、確認は待たずに進める。
- 別セッションは提案カードとして出すので、始めるかどうかはユーザーがカードで決める。

## 振り分けの基準

作業ごとに `runner` を 1 つ選ぶ。上にあるものほど Claude のトークンを使わないので、当てはまるならそちらを選ぶ。

| runner | 手段 | 向いている作業 | 向いていない作業 |
| --- | --- | --- | --- |
| `explore` | Explore サブエージェント（`model: "sonnet"`。ファイル名や文字列を探すだけなら `"haiku"`） | 読むだけの調査、複数の場所の洗い出し | ファイルを書き込む作業 |
| `codex` | codex-impl の Luna（専用の worktree で実装する） | 要件と完了の条件がはっきりした 100 行以上の実装（codex-impl の「任せる部分」に当たるもの） | 100 行未満の実装、認証・課金・秘密情報に関わる実装 |
| `session` | 別セッション（`start_session`。専用の worktree で動く） | 判断を含む実装や設計、ユーザーが途中で口を出したい作業、長い作業 | ほかの作業に依存する作業や、ほかの作業から依存される作業（未コミットの変更を見られず、結果はマージするまで入らないため） |
| `self` | Claude 本体（作業フォルダで直接進める） | 最長の道筋の上の作業、つなぎこみ、数分で終わる作業、細かい判断が続く作業 | — |

- `codex` が見つからない・ログインしていないときは、`self` か `session` に置き換える。
- `start_session` がない環境（ターミナルの Claude Code など）では、`session` を `self` に置き換える。
- 対象が今のフォルダ以外のリポジトリ（`plan.json` に `repo` を書く）なら、`session` は使わず `self` か `codex` にする。提案カードには作業するフォルダを付けられないため。ユーザーがそのリポジトリでの別セッションを自分の言葉で頼んだときだけ、`initiation: "user_asked"` と `cwd` で始めてよい。
- 同時に動かすのは、Luna・別セッション・Explore のそれぞれ 4 本までを目安にする。それより多ければ、終わった分から次を動かす。

## 手順

### 1. 引数を読む

- 進めたいことを読み取る。足りない前提があり、推測では決められなければユーザーに確認する。
- 対象が今のフォルダ以外のリポジトリなら、3. で `plan.json` の `repo` にそのリポジトリの絶対パスを書く（plan-check.sh と to-codex.sh が使う。Explore の指示書にもこのパスが入る）。

### 2. 分け方を決める

- 作業を書き出し、作業ごとに触るファイルと依存（どの作業が終わっていないと始められないか）を決める。Claude がコードを読むのは、分け方を決めるのに要る範囲（関連するファイルやフォルダの特定）にとどめる。細部の調査は `explore` の作業にする。
- **共通部分を先に決める**: 複数の作業が使う型・インターフェース・関数のシグネチャ・設定のキーは `contracts` に書き、5. で Claude がスタブとして先に書く。こうすると、それを使う作業どうしの依存がなくなり、同時に始められる。
- **Claude 本体は最長の道筋の上の作業を担当する**: 見積もりの合計がいちばん長い依存の道筋の上の作業（多くは最後のつなぎこみか、いちばん大きい作業）を `self` にし、ほかの作業を待つ時間をなくす。
- 1 本が小さすぎるほど細かく分けない（指示書と報告の手間が本数だけ増える）。

### 3. 計画を書く

作業全体を表す短い英数字の名前（例: `csv-export`）を決めて計画フォルダを作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-plan.sh" <slug>
```

出力された「計画」のパスに、Write ツールで `plan.json` を書く。

```json
{
  "goal": "CSV エクスポート機能を追加する",
  "decisions": ["文字コードは UTF-8（BOM あり）"],
  "contracts": [
    {"file": "src/export/types.ts", "what": "ExportRow 型と exportCsv() のシグネチャ"}
  ],
  "tasks": [
    {"id": "survey", "runner": "explore", "title": "既存のエクスポート処理を調べる",
     "goal": "既存の PDF エクスポートの流れと、まねるべき部分を特定する", "files": ["src/export/"], "est_min": 5},
    {"id": "api", "runner": "codex", "title": "エクスポート API",
     "files": ["src/api/export/"], "done": ["GET /export?format=csv が CSV を返す"],
     "verify": ["npm test -- export"], "notes": ["src/api/report/ の実装をまねる"], "est_min": 30},
    {"id": "ui", "runner": "codex", "title": "エクスポートボタン",
     "files": ["src/ui/Export*.tsx"], "done": ["一覧画面に CSV ボタンがある"], "est_min": 20},
    {"id": "wire", "runner": "self", "title": "つなぎこみ",
     "files": ["src/app.ts"], "depends_on": ["api", "ui"], "est_min": 10}
  ]
}
```

| 項目 | 内容 |
| --- | --- |
| `repo` | 対象のリポジトリの絶対パス（今のフォルダなら省く） |
| `goal` | 作業全体の目的。すべての指示書に入る |
| `decisions` | ユーザーとの会話で決まったこと。すべての指示書に入る |
| `contracts` | 先に Claude が書く共通部分（`file` と `what`）。指示書には「中身は変えない前提」として入る |
| `tasks[].id` | 英数字・ハイフン・下線（60 文字まで） |
| `tasks[].runner` | `self` / `explore` / `codex` / `session` |
| `tasks[].title` / `goal` | 作業の名前と目的（`goal` を省くと `title` を使う） |
| `tasks[].files` | 書き込む作業は触るファイル（必須）、`explore` は読む範囲（任意）。パス（フォルダならその下すべて）か glob（`*`・`**`・`?`） |
| `tasks[].depends_on` | 終わっていないと始められない作業の id |
| `tasks[].done` / `verify` / `notes` | 完了の条件 / 確認のコマンド / 手がかり（関係するファイル、まねる実装） |
| `tasks[].est_min` | 見積もり（分）。最長の道筋の計算に使う（省くと 15） |

秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. 確かめる

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/plan-check.sh" <計画フォルダ>
```

- 依存先がない・依存が循環している・依存の順がついていない書き込む作業どうしで触るファイルが重なる、といった問題があれば、終了コード 1 で内容を出力する。`plan.json` を直してもう一度実行する。
- 問題がなければ、実行の順番（段）・最長の道筋・注意点を出力し、`self` 以外の作業の指示書を `briefs/<id>.md` に書く。指示書には、同時に動きうる（依存の順がついていない）ほかの作業が触るファイルが「触らないファイル」として、`contracts` と依存先が「前提にしてよいもの」として、計画フォルダの `results/<依存先の id>.md` が「依存先の結果」として入る。**Claude は指示書を読まない**（トークン節約のため。中身は `plan.json` から決まる）。
- 注意点は、直すか、そのまま進めるかを判断する。「並列にする効果がない」と出たら、このスキルはやめて順番に進める。
- ファイルの重なりは、パスとリポジトリのファイルの一覧から判定する目安なので、まだないファイルどうしの重なりは見逃すことがある。

### 5. 共通部分を書いて、始める

1. `contracts` のファイルを Claude が書く。中身は型・シグネチャ・空の実装（スタブ）でよい。
2. 今すぐ始められる作業を出す。

   ```bash
   bash "${CLAUDE_SKILL_DIR}/scripts/next.sh" <計画フォルダ>
   ```

3. 出てきた作業を、**1 つのメッセージでまとめて**始める。その前に、codex の作業ごとに to-codex.sh を実行し、session の作業の指示書を Read で読んでおく。

   - **explore**: Agent ツールで `subagent_type: "Explore"`、`model: "sonnet"`（または `"haiku"`）、`run_in_background: true`。prompt は「次の指示書を Read で読み、その指示に従って調査し、指示書の『報告の形式』だけで報告して: <指示書のパス>」とする。
   - **codex**: 指示書を codex-impl に渡してから、codex-impl の手順 4. のとおり `run_in_background: true` で実装させる。codex-impl の SKILL.md を読み込んでいなければ、`${CLAUDE_SKILL_DIR}/../codex-impl/SKILL.md` の 4.〜6. を Read で読む。

     ```bash
     bash "${CLAUDE_SKILL_DIR}/scripts/to-codex.sh" <計画フォルダ> <id>
     ```

     to-codex.sh が出力した impl.sh のコマンド（`repo` があれば `--cd` つき）を、そのまま `run_in_background: true` で実行する。

   - **session**: `start_session` を `initiation: "own_initiative"`、`context: "fresh"`、作業ごとに 1 枚で出す。prompt には指示書の中身をそのまま入れる（別セッションは計画フォルダを読めないことがあるため、この作業の指示書だけは Read で読む）。title は作業の `title` にする。
   - **self**: ほかの作業を始めたあと、作業フォルダで Claude が進める。

4. 実行中は、ほかの作業の「触ってよいファイル」を Claude も変えない。

### 6. 終わった作業からつなぐ

ポーリングはしない。Explore と Luna は終わると 1 本ずつ通知が来る。別セッションは、ターンを終えると報告が届く。

作業が終わるたびに、次のように受け取る。

- **explore**: 報告だけを読む。分け方が変わる内容（触るファイルが違った、作業が増えた）なら、まだ始めていない作業について `plan.json` を直す。
- **codex**: codex-impl の手順 5.（差分のレビュー、大きな問題なら差し戻し）と 6.（`apply.sh` で作業フォルダに反映）を行う。反映したら終わりとする。
- **session**: 報告をうのみにせず、ブランチの差分で結果を確かめる。作業フォルダへのマージは、ユーザーが自分の言葉で頼んだときだけ行う（マージするかをユーザーに聞く）。
- **self**: 終わったら次へ進む。

終わった作業に依存する `self` 以外の作業があるなら、その報告（Claude 本体なら、後の作業に要ることの要約）を Write で計画フォルダの `results/<id>.md` に保存し、もう一度 4. を実行してから次の作業を始める。指示書が作り直され、依存する作業の指示書に「依存先の結果」として入る（Explore の調査結果は、こうしないと後の作業に渡らない）。すでに始めた作業には影響しない。依存する作業が `self` だけなら、Claude が報告を読んでいるので保存は要らない。

終わったら、すぐに次に始められる作業を出し、出てきた作業を始める（段の全体が終わるのを待たない）。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/next.sh" <計画フォルダ> --started <実行中の id,...> <終わった id>...
```

うまくいかなかった作業は、codex なら codex-impl の基準（差し戻しは 2 回まで）に従い、explore なら指示書を直して出し直すか Claude が調べる。それに依存する作業は始めない。

### 7. まとめて確かめる

- すべてを作業フォルダに反映したら、各作業の `verify` を合わせたテスト・型チェックを **1 回だけ**実行する。実行は codex-test スキルで Luna に任せ、報告だけを読む。作業どうしのつなぎ目もここで確かめる。
- レビューも、変更の全体に対して 1 回だけ行う（codex-impl-review などの基準に当たれば使う）。
- 小さな問題（数行の修正、つなぎ目のずれ）は Claude が直し、もう一度テストする。
- コミットやプッシュは、ユーザーに頼まれない限りしない。

### 8. 報告する

日本語で簡潔に書く。サブエージェントや Codex の報告の全文、差分は貼らない。

```markdown
## 分担
| 作業 | 担当 | 結果 |
| --- | --- | --- |
| api: エクスポート API | Luna | 反映済み（差し戻し 1 回） |
| survey: 既存処理の調査 | Explore | 完了 |
| docs: ドキュメント | 別セッション | ブランチ `refs/heads/...` に完了（未マージ） |
| wire: つなぎこみ | Claude | 実装済み |

## 確認したこと
（実行したテスト・型チェックとその結果）

## ユーザーに確認したいこと
（マージの可否など、ユーザーにしか決められないもの。なければ省く）
```

## 守ること

- 別セッションのブランチのマージやプッシュは、ユーザーが頼んだときだけ行う。
- 指示書や `plan.json` に秘密情報を書かない。
- サブエージェントや別セッションの報告は、結果（差分・ファイル）を確かめてから完了として扱う。
