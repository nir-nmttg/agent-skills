# Sol と Opus による設計への適合のレビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が実装した変更が、対象プロジェクトの既存の設計（明文化された方針と、複数の実装から読み取れる慣習）に沿っているかを、Sol（Codex CLI の GPT-6.2 Sol）と Opus（`opus-reviewer`）に**同じ依頼で**確かめさせ、根拠のある逸脱を Claude が直す。正しさ・バグ・セキュリティは implementation-cross-review が見るので、ここでは扱わない。設計に合わせる直しは責務やファイルの移動になりやすいので、正しさのレビューより先に形を整える。差分の取り出し・プロンプトの組み立て・Codex の呼び出しはスクリプトに任せ、Claude は「決定事項をまとめる」「指摘を確かめて判断する」「採用した指摘を直す」だけを行う。結果は `artifacts/architecture-alignment-cross-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Claude が実装を終え、haiku-check でテストが通ったあと、ui-behavior-check と implementation-cross-review の前に、次の基準で判断する。**迷ったら使う。**

**使う**: 処理の置き場所・責務・依存・共通の仕組みの使い方を選ぶ変更。既存のファイルや関数の中だけの変更でも、ここに当たれば使う。たとえば次のもの。

- 新しいファイル・モジュール・クラス・層を足す
- 責務や処理を別の場所に置く・移す、既存の処理に新しい種類の責務を足す
- モジュールの間に新しい依存を足す
- エラー処理・ログ・設定・データアクセス・認可・DI・バリデーションなどを書く（共通の仕組みを使うか、自前で書くかを選ぶ）
- 同じ種類の処理（ハンドラー・コマンド・コンポーネント・テストのヘルパーなど）を新しく書き足す

**使わない**（次の場合だけ）

- 直し方が一通りに決まる不具合修正で、上のどれにも当たらないもの
- 意味を変えない修正: typo・整形・コメントだけの変更、自動生成ファイルの再生成だけの変更
- 動作を決めない文書（README など）だけの変更、依存パッケージのバージョンだけを変える変更
- プロジェクトに設計の手がかりがほとんどない（作り始めたばかりで、比べる実装がない）
- codebase-cleanup-workflow の工程の中（工程 1 の architecture-alignment-refactor が同じ観点を受け持つため）
- ユーザーが「不要」と言っている
- 対象が git リポジトリでない

見送るときは、当てはまる項目を完了報告に 1 行書く。書けないときは実行する。

**再レビュー**: 要否は、直した分の内容で判断する（このスキルの指摘で直した分も、implementation-cross-review や ui-behavior-check の指摘で直した分も同じ）。直す中で指摘の範囲を超えて変更したとき、新しいモジュール・層・依存を足したときは、直した部分の確認に絞って Sol 1 体で確かめる（下の「確認のレビュー」）。作り方（選ぶ置き場所・仕組み）を変えたときは、直した部分の確認では足りないので、1 回目と同じく Sol と Opus でレビューし直す（`${CLAUDE_SKILL_DIR}/references/followup.md` の「ゼロからレビューし直すとき」）。どちらにも当たらなければ使わない。同じ変更への再レビューは、どちらの形でも 1 回までにし、残る指摘はユーザーに伝える。前回と同じ根拠で決めた判断は、別の書き方も成立するという理由だけで覆さない。

**自分の判断で使うときの違い**

- 始める前に「実装レビューの前に Sol と Opus に既存の設計への適合を確かめさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。
- レビューが動いている間は、ファイルを編集しない（どのレビュアーも作業ツリーを読むため）。

## レビュアーと代わり

- Sol と Opus を同じメッセージで同時に動かす。Sol は Codex を使うので git の履歴も読め、Opus は Read / Grep / Glob だけで読む。Sol は読み取り専用のサンドボックスで動き、個人設定（MCP サーバー・プラグイン・`~/.agents/skills` のスキル）は読み込まない。
- 片方が結果を返さなければ、結果の出た方の意見で判断し、失敗したことを報告に書く。
- 両方とも結果を返さなければ、設計への適合を未確認として報告に書き、次へ進む。
- 確認のレビューは Sol 1 体で動かし、結果を返さなければ Opus で 1 回だけ動かす。
- `codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。`opus-reviewer` が見つからないときは、エージェントがリンクされていない（このスキル集の `scripts/link-skills.sh --claude` で `~/.claude/agents` にリンクする）か、リンクする前に始めたセッション。どちらも失敗に数える。

## 手順

### 1. 引数を読む

- 範囲の指定があればそのまま 4. の `prepare.sh` に渡す。「未コミットだけ」→ `--uncommitted`、「このコミット」→ `--commit <sha>`、「develop との差分」→ `--base develop`。指定がなければ渡さない（既定ブランチから分岐して以降の変更を、未コミットも含めてすべてレビューする）。
- 対象が今のフォルダ以外のリポジトリなら、4. の `prepare.sh` に `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

変更の内容を表す短い英数字の名前（例: `export-csv`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 決定事項を書く

会話の中でユーザーが置き場所・書き方・使う仕組みを決めていたら、出力された「決定事項」のパスに Write ツールで箇条書きにする（ユーザーの言葉で）。なければ書かない。要件・実装の経緯・Claude が自信のない箇所・ほかのレビューの指摘は書かない（設計への適合は要件と独立に判断でき、先入観を渡さないため）。秘密情報は書かない。

### 4. レビューさせる

まず、同じ依頼（`prompt.md`）を作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/prepare.sh" [--cd <dir>] [--base <ref> | --commit <sha> | --uncommitted] <実行フォルダ>
```

- 「レビューする変更がありません」と出たら、範囲を確かめてユーザーに伝える。その他のエラーなら内容を伝えて終わる。

続けて、Sol と Opus を**同じメッセージで**動かす。**すべて終わるまでファイルを編集しない。**

Sol は Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと長くかかることがある）。`--effort` には上の「Claude の推論レベル」をそのまま渡す（空や `auto` のときは省略してよい）。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} <実行フォルダ>
```

Opus は Agent ツールで呼ぶ。

- `subagent_type`: `opus-reviewer`（必ず指定する。省略や `fork` では、定義のモデルと読み取り専用の設定が効かない）
- `effort`: 上の「Claude の推論レベル」。空や `auto` のときは `high`
- `model`: **渡さない**（引数は別名しか受け付けず、定義の `claude-opus-5-5` の固定が外れる）
- `prompt`: 次の 1 行だけにする

  ```text
  <実行フォルダ>/prompt.md を読み、その指示に従ってレビューしてください。
  ```

- どちらも終わると通知が来るので、それまで待つ。ポーリングはしない。
- Opus の結果は、5. の decisions.md の表に出どころ付きで残す。Sol の結果は `<実行フォルダ>/review.md` に保存される。
- 失敗したときは、上の「レビュアーと代わり」のとおりにする。

### 5. 指摘を確かめて判断する

すべての結果が揃ってから判断する。原因が同じ指摘は 1 件にまとめ、見つけた担当を頭に書く（`[Sol]`・`[Opus]`・`[Sol・Opus]`）。

指摘はうのみにしない。両方が挙げたものも同じで、指摘ごとに根拠と反例のファイルを Read / Grep で確かめる。書き方が 2 つ以上並んでいるときは、`git log`・`git blame` や文書で今の方針がどちらかを確かめる（多い書き方が古い書き方のこともある）。

確かめた指摘は、次を**上から順に**当てはめ、最初に当たったもので決める。

1. 根拠を確かめたら成り立たない、または慣習を根拠にしているのに根拠が 1 か所だけ → **不採用**
2. ユーザーの決定（決定事項・会話）に反する → **要確認**
3. 合わせると、要件・受け入れ条件か、この変更より前からある振る舞いが変わる → **要確認**
4. 書き方が 2 つ以上並ぶ、または文書と実装が矛盾していて、今の方針がどちらか確かめられない → **保留**
5. 直しがこの差分の外（ほかのコード）に及ぶ → **見送り**（architecture-alignment-refactor を勧める）
6. 今も有効な明文化された方針（根拠は 1 か所でよい）、または 2 か所以上の慣習からの逸脱 → **採用**

判断の表、各レビューの実行状態（成功・失敗）、件数の行を `<実行フォルダ>/decisions.md` に Write で保存する。どれも結果を返さなかった回も残す。

### 6. 直す

- **この会話で Claude か Haiku が書いた部分**なら、「採用」とした指摘を直す。修正の担当は haiku-implementation の基準で決める。直したら、haiku-check で関係するテストを実行する。
- **それ以外**（ユーザーや他の人のコード、既存のコミット）は直さず、修正案の提示にとどめる。
- 処理を移すときは、戻り値・エラー・処理順序・トランザクション・権限を保つ。
- 直すのは実装の側にする。文書や方針のほうを変えるべきだと考えたときは、書き換えずに「要確認」として報告する。
- 「要確認」「保留」「見送り」は直さず、報告に残す。ユーザーに直すよう言われたら直す。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

Sol を動かしたら、スクリプトの出力の先頭（設定・範囲・所要時間・保存先・`codex resume` の行）をそのまま表示する。Opus を動かしたら、設定（`opus-reviewer` / effort）・所要時間とトークン（完了の通知）・判断の記録（`<実行フォルダ>/decisions.md`）を短く添える。続けて次を日本語で簡潔に書く。レビューの全文は貼らない（Sol の全文は保存先にある）。

```markdown
## 設計への適合の総評
（動かした担当ごとに 1 行で要約）

## 指摘への判断
| 種類 | 指摘 | 場所 | 判断 | 理由・対応 |
| --- | --- | --- | --- | --- |
| 明文化 / 慣習 | [Sol・Opus] ... | `path:line` | 採用（修正済み） / 採用（修正案） / 要確認 / 保留 / 見送り / 不採用 | ... |

両方 n 件、Sol だけ n 件、Opus だけ n 件（うち採用 n 件、要確認 n 件、保留 n 件、見送り n 件、不採用 n 件）

## 修正内容
（6. で直したものと、テストの結果。直していなければ修正案を箇条書きで）

## ユーザーに確認したいこと
（「要確認」と、「〇〇と△△のどちらを今の方針にするか」の問いの形の「保留」。なければ省く）
```

- 件数の行は両方が成功した回だけ書き、それ以外は「比較なし」と書く。
- 「見送り」があれば、表のあとに「直したいものがあれば指示してください」と 1 行添える。
- 自分の判断で使ったときは、報告のあと、続けて ui-behavior-check・implementation-cross-review の条件を確かめて進む。

## 確認のレビュー

上の「再レビュー」の条件に当たったら、`${CLAUDE_SKILL_DIR}/references/followup.md` を読んで従う。確認のレビューの実行フォルダは、前回の実行フォルダを指定して次のコマンドで作る（ゼロからレビューし直すときは `--followup` を付けない）。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" --followup <前回の実行フォルダ> <slug>-r2
```
