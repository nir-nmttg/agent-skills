# 過剰実装を取り除く

現在の要件に対して不要な複雑さを取り除き、読みやすく変えやすいコードにする。必要十分な実装を残すことを優先し、削除行数や変更件数を目標にしない。過剰実装を無理に探し出さず、現状が適切なら変更しなくてよい。

## 探索して候補を集める

- リポジトリの指示と作業中の差分を確認する。対象が指定されていればその範囲と関連する呼び出し元・依存先を調べる。指定がなければプロジェクト全体の構成と主要な処理経路を把握し、領域ごとに探索する。生成物・依存パッケージ・外部から取り込んだコードは直接編集しない。
- README、設計文書、設定、CI、公開インターフェースから、現在の要件と、外部からの利用・将来の利用が明示されている仕組みを把握する。
- 次の観点で候補を探す。

| 観点 | 例 |
| --- | --- |
| 不要な抽象化 | 実装が 1 つしかないインターフェース、委譲するだけのレイヤー、要件に対して重いデザインパターン |
| 過剰な汎用化 | 使われていない拡張ポイント・設定項目・プラグイン機構、常に同じ値で呼ばれる引数 |
| 不要な防御的実装 | 型や呼び出し元の制約で起きない状態への対処、根拠のないフォールバック、握りつぶすだけの例外処理 |
| 不要な互換性維持 | 利用されなくなった旧仕様、移行の終わった移行用処理、旧形式の読み替え |
| 冗長な処理 | 同じ層での重複した検証、往復するだけのデータ変換、使われない中間状態 |
| 不要なコード | 未使用の関数・クラス・設定・依存関係、到達不能な分岐 |
| 過剰な分割 | 一度しか呼ばれない細かな関数やファイルで、処理を追う往復が増えているもの |
| 過剰な複雑化 | より単純な構成で同じ要件を満たせる実装（標準機能で足りる自前実装、不要な状態管理・キャッシュ・非同期化） |

- 候補ごとに、呼び出し元、依存関係、テスト、設定、外部インターフェース、必要なら変更履歴を確かめ、不要と判断した根拠を押さえる。未探索の領域まで問題がないと断定しない。

## 残すか取り除くかを判断する

- 現在の要件に必要な実装は残す。将来の仮定だけに基づく複雑さは、原則として取り除く。
- 抽象化は、実際の重複の解消や変更の局所化に明確な効果があれば残す。
- セキュリティ、データ整合性、外部入力や I/O の失敗に対する必要なエラーハンドリング、並行処理の安全性に関わる処理は残す。防御的な処理は、その状態が起きないことをコードや型で確かめられたときだけ取り除く。互換性のための処理は、旧仕様のデータや利用者が残っていないことを文書・履歴・設定で確かめられたときだけ取り除く。
- 公開 API、プラグインの登録口、設定ファイルのキー、永続化形式など、外部から使われうるものや利用予定が文書・コメント・Issue に明示されたものは、リポジトリ内で未使用という理由だけで削除しない。取り除くには契約の変更が要るので、理由と選択肢をユーザーに確認する。
- 単純化で可読性や保守性が下がる変更、既存の設計規約やアーキテクチャから外れる変更、明確な改善を説明できない変更はしない。
- 判断材料が足りない候補は推測で削除せず、根拠と不足している情報を報告に残す。
- 責務の混在の分割・共通化、設計方針の統一、宣言順だけの整理、テストの重複整理、文書の更新は、それぞれの整備スキルの範囲として一括して行わない。取り除いたコードに伴うテスト・設定・文書・依存関係の更新は一緒に行う。

## 振る舞いを保って実装する

- 対象の返り値、例外、境界条件、状態変更、外部 I/O を把握し、関連する既存テストを変更前に実行する。既存の失敗と実行不能を記録して、変更による失敗と区別する。
- 重要な箇所で振る舞いを保証するテストが不足していれば、取り除く前にそのテストを補う。
- 影響の大きい候補から、影響範囲を追える小さな単位で進める。インライン化・削除のたびに呼び出し元、import・export、設定、依存関係の宣言を追い、参照漏れを確かめる。
- 過剰実装を取り除くために、新しい過剰実装を足さない（抽象化を足すなら、現在の要件と明確な改善効果で判断する）。全面的な書き換えやアーキテクチャの変更をしない。ユーザーの未コミットの変更を上書き・巻き戻ししない。
- レビューだけを求められている場合は実装しない。

## 検証して結果を報告する

- 変更箇所と影響範囲のテスト、型チェック、lint、ビルドなど適切な既存の検証と、リポジトリで必須のチェックを実行する。実行できなかった検証は成功扱いにしない。
- 最終的な差分を読み直し、機能・仕様・公開インターフェースが変わっていないこと、新たな複雑さや依頼外の変更が混ざっていないことを確かめる。
- 日本語で簡潔に次を報告する。変更不要なら、確認した範囲と根拠を伝える。
  - 探索した範囲と、探索していない範囲
  - 見つけた主な過剰実装
  - 削除・簡素化した内容と、その理由・改善効果
  - 実行した検証と結果
  - 判断が難しく見送った箇所と、その理由
