# Codex（GPT-6 Luna）にテストを実行させる

引数: $ARGUMENTS

テストの実行と失敗の切り分けを Codex CLI の GPT-6 Luna に任せ、Claude は短い報告だけを読む。テストの出力（数百〜数千行のログやスタックトレース）を Claude が読まずに済むので、トークンを節約できる。モデル・推論レベル（max）・通常速度（Fast モードなし）はスクリプトで固定している。結果は `artifacts/codex-test/` に保存される。

## いつ使うか

ユーザーに頼まれたときに加えて、頼まれていなくても積極的に使う。**Claude がテスト・型チェック・リンター・ビルドを実行するときは、原則このスキルで Luna に任せる**。Luna はほぼ無料なので、少しでも出力が出るものは任せた方が Claude のトークンを節約できる。

**必ず任せる**

- 実装や修正を終えて、正しく動くかを確かめるとき（haiku-impl で反映したあとを含む）
- 完了の報告、コミット、PR の作成の前に全体を確かめるとき
- テストスイート全体、複数のコマンド（テスト + 型チェック + リンターなど）、E2E、ビルドを実行するとき
- 失敗の原因を切り分けたいとき、失敗が多いとき
- このリポジトリのテストの実行方法がわからないとき（Luna が調べる）
- ユーザーが「テストして」「動くか確認して」「CI 通る？」などと言ったとき

**Claude が直接実行する**（これ以外は任せる）

- 出力が数行で済む 1 件〜数件のテストを、編集のたびに数秒で結果を見たい細かい繰り返しの最中（区切りがついたら、全体の確認は任せる）
- ユーザーが「自分で実行して」「Codex は使わないで」と言っている
- 本番環境や外部サービスに書き込むテスト、秘密情報を手で渡す必要があるテスト

迷ったら任せる。

**自分の判断で使うときの違い**

- 始める前に「テストの実行は Codex（GPT-6 Luna）に任せます」と 1 行だけ伝え、確認は待たずに進める。
- `codex` が見つからない・ログインしていない・エラーで動かなかったときは、そのことを 1 行伝えて Claude が自分で実行する。

## 手順

### 1. 依頼をまとめる

- 実行するコマンドがわかっていれば、それを依頼に書く（例: `npm test と npx tsc --noEmit を実行`）。わからなければ省略してよい。Codex がリポジトリから実行方法を調べる。
- 範囲を絞るなら書く（例: `src/billing 配下に関係するテストだけ`）。Claude が変えたファイルがわかっていれば、それも書くと切り分けが速くなる。
- 対象が今のフォルダ以外のリポジトリなら `--cd <そのリポジトリのパス>` をつける。
- **ネットワーク**: サンドボックスは既定でネットワークなし（localhost の DB や Docker への接続も含む）。テストに DB やネットワークが要るとわかっていれば、ユーザーに確認してから `--network` をつける。わからなければつけずに実行し、報告で「実行できなかったもの」に挙がったら確認して再実行する。
- 秘密情報（トークン、パスワード、個人情報）は依頼に書かない。

### 2. Codex に実行させる

Bash ツールを **`run_in_background: true`** で実行する。推論レベル max・通常速度なので、数十秒〜10 分以上かかることがある。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/run.sh" [--cd <dir>] [--network] "<依頼>"
```

- Codex は作業フォルダでそのままテストを実行する。**実行中は Claude もユーザーも作業フォルダのファイルを変更しない**（結果が食い違ううえ、Codex が変更したと誤って警告される）。待つ間は、ファイルを変えない作業（コードを読む、次の作業を考える）だけを進める。
- Codex はファイルを変更しないよう指示されており、それでも追跡対象のファイルが変わったら、スクリプトが差分を保存して警告する。警告が出たら差分を Read で確かめ、Codex による不要な変更なら取り除く（テストの実行で自然にできる生成物なら残してよい）。ユーザーのもとからの変更には触れない。
- エラーなら内容を伝える。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。

### 3. 報告を読んで判断する

- スクリプトの出力（Codex の報告）だけを読む。原因の見立てに挙がった `path:line` は、直すのに必要な範囲で Read する。
- Codex の見立てはうのみにしない。「テストが古い・誤り」とされたものは、テストを直すべきかコードを直すべきかを Claude が判断する（仕様の変更を伴うならユーザーに確認する）。
- 報告だけでは判断できないときに限り、実行ログ（`commands-<回>.log`）を Grep で必要な箇所だけ読む。ログ全体は Read しない。

### 4. 直して再実行する

Claude が直したあとの再実行は、同じ実行フォルダを `--resume` で渡すと、前回の文脈を引き継いで失敗したテストだけを確かめさせられる（依頼を省略すると、前回失敗したテストと実行できなかったテストを再実行する）。2. と同じく background で実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/run.sh" --resume <実行フォルダ> ["<依頼>"]
```

失敗したテストが 1〜2 件で出力も短いなら、Claude が直接そのテストだけを実行してもよい。最後に全体を確かめるときは、もう一度 Codex に任せる。

## 報告する

スクリプトの出力の先頭（設定・所要時間・トークン）を 1 行にまとめ、続けて次を日本語で簡潔に書く。Codex の報告の全文やログは貼らない（保存先にある）。

```markdown
## テスト結果
（成功 / 失敗あり / 実行できず と、コマンドごとの件数）

## 失敗と対応
| テスト | 場所 | 原因 | 対応 |
| --- | --- | --- | --- |
| ... | `path:line` | コードの不具合 / テストが古い / 環境 | Claude が修正して再実行で成功 / 未対応（理由） |

## 実行できなかったもの
（理由と、何があれば実行できるか。なければ省く）
```
