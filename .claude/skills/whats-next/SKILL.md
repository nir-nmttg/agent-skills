# 次にやるべきアクション

並行して進めているセッションに戻ってきたとき、「このセッションで何をしていて、次に何をすればいいか」を思い出し、そのままワンクリックで続きに取りかかれるようにする。このスキルのターンでは**報告と提案だけ**を行い、次のアクションを実行したり、ファイルやセッションを変更したりはしない。

引数: $ARGUMENTS

- 補足があれば、次のアクションを決めるときの材料にする（例: 「今日は 30 分しかない」「レビュー対応を優先」）。
- 扱うのはこのセッションだけ。ほかのセッションの状況は、サイドバーと session-status-emoji の絵文字で見てもらう。

## 今のフォルダの状態

!`bash "${CLAUDE_SKILL_DIR}/scripts/state.sh" 2>&1`

## 手順

1. この会話（要約された前半も含む）を振り返り、次を整理する。
   - **目的**: ユーザーが最初に頼んだことと、途中で変わった方針。
   - **終わったこと**: 実装・調査・コミット・PR など、確かに済んだこと。
   - **残っていること**: 依頼のうち、まだ終わっていないこと。後回しにしたことや、確認していないことも含める。
   - **待っているもの**: ユーザーの判断・承認、CI、ほかのセッション、外部の返事など。
2. 上の「今のフォルダの状態」と食い違いがないかを確かめる（会話では「コミットした」のに未コミットの変更が残っている、PR の CI が失敗している、など）。食い違いがあれば、状態のほうを正として扱い、報告に書く。
3. このセッションから始めたセッションがあれば、`mcp__ccd_session_mgmt__list_sessions`（`linked: true`）で状態を確かめる（ツールが読み込まれていなければ ToolSearch で読み込む。ツールがない環境では飛ばす）。
4. 次にやるべきアクションを **1 つ**に決める。
   - ユーザーが動かないと進まないもの（判断・承認・ログインなど）を、Claude が進められるものより先にする。
   - 「確認する」「検討する」ではなく、すぐ取りかかれる具体的な行動にする（例: 「PR #12 の CI の失敗（型エラー）を直す」「設計案 A / B のどちらにするか決める」）。
   - 依頼がすべて終わっていて残りがなければ、「次にやることはない」と書き、必要ならアーカイブなどの片付けを示す。
5. アクションの種類に応じて提案を作る（下の「提案の作り方」）。
6. 下の形で報告し、`wrap_up` で返事のボタンを出す（下の「返事のボタン」）。会話がまだほとんどなく、振り返る作業がないときは、そう書いて終える。

## 提案の作り方

| 次のアクション | 提案すること |
| --- | --- |
| Claude が進められる | 「Claude がやること」として、実行する手順を 2〜4 個と、**どこで止まるか**（例: 「コミットの前で止める」「設計が 2 案に分かれたら止めて聞く」）を書く |
| ユーザーが選ぶ・決める | 選択肢を 2〜3 個と、**おすすめ**を 1 つ（理由を 1 文）書く。決まったあとに Claude が続けてやることも 1 行添える |
| ユーザーにしかできない（ログイン・社外への連絡・権限の付与など） | ユーザーがやる手順を短く書く。終わったあとに Claude が続けてやることがあれば 1 行添える |

- 手順は、承認されたらそのまま実行できる粒度で書く。範囲をあいまいにしない（「テストを直す」ではなく「`tests/api.test.ts` の 2 件の失敗を直し、テストを再実行する」）。
- コミット・push・PR の作成・マージ・削除・社外への送信は、手順に書いたときだけ行う。迷ったら手順に入れず、その手前で止める。
- 次のアクションがないときは提案を作らない。

## 報告の形

```markdown
## 次にやること
**<具体的な行動>**（<あなた / Claude>）
<なぜそれが次か、を 1 文>

## 提案
<Claude がやること（手順と止まるところ）／ 選択肢とおすすめ ／ ユーザーがやる手順>

## いまの状況
- 目的: <1〜2 文>
- 終わったこと: <箇条書きで最大 3 つ。多ければまとめる>
- 残っていること: <箇条書き。なければ「なし」>
- 待っているもの: <なければ「なし」>
```

- 状態のうち、報告に関係するもの（未コミットの変更・push していないコミット・PR の CI など）だけを書く。状態をそのまま貼らない。
- 前置きや手順の説明は書かず、「次にやること」から始める。日本語で簡潔に書く。

## 返事のボタン

`mcp__ccd_turn__wrap_up` が使えるとき（デスクトップアプリ）は、報告のあとに呼び、ボタンで返事ができるようにする。

| 次のアクション | ask | actions（1 つ目がおすすめ） |
| --- | --- | --- |
| Claude が進められる | 「提案どおり進めますか？」 | 「進めて」（message に手順と止まるところを要約して入れる）、必要なら「別の案で」 |
| ユーザーが選ぶ・決める | 「どれにしますか？」 | おすすめの選択肢、次点の選択肢（message に「〇〇にする。続けて △△ を進めて」） |
| ユーザーにしかできない | 「終わったら知らせてください」 | 「終わった」（message に「〇〇を済ませた。続きを進めて」） |
| 次にやることがない | 付けない（recap だけ） | なし |

- `wrap_up` がない環境では、最後に「進めてよければ『進めて』と送ってください」（選ぶときは「どれにするか送ってください」）と添える。
- ボタンの message には `@` を含めず、`/` や `!` で始めない（アプリが落とすため）。

## 承認されたあと

返事が来たら、次のターンで提案のとおりに実行する。

- 実行するのは提案に書いた手順だけ。止まるところに来たら、そこで報告して止まる。
- 途中で提案になかった判断や、手順に書いていないコミット・push・PR の作成などが必要になったら、進める前に聞く。
- 返事が提案と違うこと（「別の案で」や補足つきの返事）なら、その内容に従う。

## 守ること

- このスキルのターンでは、ファイルの変更・コミット・セッションへのメッセージ送信・アーカイブ・名前の変更をしない（session-status-emoji によるこのセッション名の更新は除く）。
- 返事が来るまで次のアクションに取りかからない。
