# プロジェクトの設計に合わせてリファクタリングする

根拠のある逸脱だけを、振る舞いを変えずに既存の設計へ寄せる。プロジェクト自身の設計思想・責務分担・依存関係に実装を揃える。定期的な整備として繰り返し使い、修正件数や見た目の統一を目標にしない。根拠のある逸脱がなければ変更しなくてよい。

## 探索して設計の根拠をつかむ

- リポジトリの指示と作業中の変更を確認する。対象が指定されていればその範囲と関連する呼び出し元・依存先を調べる。指定がなければプロジェクト全体のディレクトリと主要なモジュールを把握し、各領域の代表的な実装と主要な処理経路から探索する。直近の差分だけを対象にせず、逸脱の兆候がある箇所を掘り下げる。生成物・依存パッケージ・外部から取り込んだコードは直接の修正対象にしない。
- README、設計文書、ADR、CONTRIBUTING、モジュール構成、公開 API、設定、代表的な実装とテストを照合する。必要に応じて関連する履歴を確認し、責務の境界、依存の向き、データの流れ、エラーや副作用の扱い、拡張方法を読み取る。特定のアーキテクチャや自分の好みを持ち込まない。
- 明文化された方針と、複数の実装から推定した慣習を区別し、判断に使うファイルやコード箇所を押さえる。多い書き方をそれだけで正解にせず、古い文書、移行途中の実装、意図的な例外も見分ける。

## 逸脱と修正範囲を決める

- 次の観点で候補を探す。局所的な命名や形式の違いだけを設計違反と決めつけない。

  1. 置き場所: ファイル・モジュールが、ディレクトリ構成が意味する場所にあるか
  2. 責務の境界: 層・モジュールの責務を越えた処理（表示の層の業務ルール、データアクセスの層の表示の都合など）がないか、データの流れが層の境界に沿っているか
  3. 依存の向き: 依存が既存の向きと逆になっていないか、循環がないか
  4. 共通の仕組み: エラー処理・ログ・設定・データアクセス・認可・DI・バリデーションなど、すでにある共通の仕組みを迂回したり、同じものを作り直したりしていないか、エラーや副作用の扱いがプロジェクトの方針に沿っているか
  5. 書き方と拡張の仕方: 同じ種類の処理（ハンドラー・コマンド・コンポーネント・テストなど）の書き方・登録の仕方・命名の型が揃っているか
  6. 業務ルールの置き場所: 同じ業務ルールが別の場所に重複・分散していないか

- 候補ごとに「設計の根拠」「逸脱している実装」「具体的な問題」「既存の設計へ合わせる方法」を説明できるようにする。根拠は、今も有効な明文化された方針なら 1 か所、慣習なら同じ層の 2 か所以上とし、違う書き方をしている箇所（反例）も確かめる。
- 候補ごとに次を上から順に当てはめ、最初に当たったもので決める。

  1. 根拠が上の基準に満たない → 直さない
  2. 合わせると公開 API・永続化形式・業務ルール・外部への副作用などの振る舞いが変わる → 要確認（その箇所だけユーザーに確認し、設計の判断が要らない独立した修正は進める）
  3. 書き方が 2 つ以上並ぶ、または文書と実装が矛盾していて、今の方針がどちらか決められない → 保留
  4. 正当な例外、移行途中の実装、未採用の将来構想 → 直さない
  5. それ以外で、具体的な問題を説明できる → 直す（説明できなければ直さない）

- 設計を実装に合わせて書き換えることで逸脱を解消したことにしない。設計自体の変更が必要な場合は、リファクタリングと分けて理由と選択肢を報告する。
- 再実行でも同じ設計の根拠を使い、以前と異なる案も成立するという理由だけで変更を往復させない。新しい要件や根拠がある場合はそれを説明する。設計からの逸脱を伴わない責務整理や、宣言順だけの変更まで目的を広げない。
- 「直す」とした修正を、影響範囲を追える単位に分けて進める。探索結果と採用する方針を簡潔に伝え、通常の内部リファクタリングは提案だけで終わらせず実施する。レビューだけの依頼なら指摘と提案に留める。対象範囲を黙って広げず、保留や未探索の範囲を明らかにする。

## 振る舞いを保って変更する

- 対象の契約と影響範囲を確認し、変更前に関連する既存のチェックを実行する。既存の失敗と実行不能を記録し、変更による失敗と区別する。重要な振る舞いを守るテストが足りなければ、必要な回帰テストを追加する。
- 既存の抽象化・共通処理・依存の渡し方を活かし、責務や処理を適切な場所へ移す。呼び出し元、依存先、設定、テストまで追って整合させる。一律の共通化や、将来のためだけの層・フレームワークの導入は避ける。
- 戻り値、エラー、処理順序、トランザクション、権限、外部 I/O など、対象に関係する契約を維持する。振る舞いを固定するテストは残し、内部構造に依存するテストは観測する契約を保って更新する。失敗を隠すためにテストや必須チェックを弱めない。
- ユーザーの未コミット変更を上書き・巻き戻しせず、自分の変更と区別して扱う。関連する説明や参照先が変更で古くなる場合は、必要な範囲で更新する。

## 確認と報告

- 変更した処理と影響範囲のテスト、型チェック、lint、ビルドなど適切な既存の検証と、リポジトリで必須のチェックを実行する。差分を読み直し、呼び出し経路や依存関係が設計へ揃ったことと、振る舞いが維持されていることを確かめる。
- 日本語で簡潔に、探索した範囲、採用した設計の根拠、実行コマンドと結果、未探索・未検証の事項を報告する。逸脱が見つからなければ、確認した範囲と変更不要と判断した根拠を伝える。限られた探索でプロジェクト全体に問題がないと断定しない。
- 「直す」「要確認」「保留」とした候補は、次の表にまとめる。レビューだけの依頼で直さなかったものは「修正案」と書く。

  ```markdown
  | 種類 | 逸脱 | 場所 | 根拠（反例） | 判断 | 理由・対応 |
  | --- | --- | --- | --- | --- | --- |
  | 明文化 / 慣習 | ... | `path:line` | `path:line` | 修正済み / 修正案 / 要確認 / 保留 | ... |
  ```
