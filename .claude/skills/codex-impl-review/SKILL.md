# Codex による実装レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が実装した変更を、別のモデル（Codex CLI の GPT-6.1 Sol）に独立してコードレビューさせ、その指摘を Claude が吟味する。差分の取り出し・Codex の呼び出し・保存はスクリプトに任せ、Claude は「実装の説明をまとめる」「指摘を判断する」「採用した指摘を直す」だけを行う。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、Claude が実装を終え、完了を報告する（またはコミット・PR を作る）前に、変更の規模で判断して使う。

**使う**（次のどれかに当たる）

- 複数のモジュール・サービスにまたがる変更
- DB スキーマ、公開 API・インターフェース、設定ファイルの形式を変える。データ移行がある
- 認証・権限・課金・個人情報・秘密情報の扱いに関わる
- 並行処理、キャッシュ、再試行、データの整合性が絡む

**使わない**

- 小さな変更（目安: 数ファイル・100 行程度まで）、原因と直し方が明らかなバグ修正、文言・設定値・ドキュメントだけの変更
- ユーザーが「レビューは不要」「急ぎ」と言っている
- 同じ変更をこの会話ですでにレビュー済みで、その後の修正が小さい
- 迷う程度の規模なら使わず、完了報告の最後に「Codex に実装レビューさせることもできます」と一言添える

**自分の判断で使うときの違い**

- 始める前に「変更の規模が大きいため、完了を報告する前に Codex にレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。Fast モードはユーザーの指定がない限り使わない。
- Codex がエラーで動かなかったら、そのことを 1 行伝えて、レビューなしで完了を報告する。

## 手順

### 1. 引数を読む

- `--fast` または `fast` があれば Fast モードにする（速いぶん Codex の使用量が増える）。それ以外の依頼文に「速く」「fast で」とあっても同じ。
- 範囲の指定があればそのまま 4. に渡す。「未コミットだけ」→ `--uncommitted`、「このコミット」→ `--commit <sha>`、「develop との差分」→ `--base develop`。指定がなければ渡さない（既定ブランチから分岐して以降の変更を、未コミットも含めてすべてレビューする）。
- 対象が今のフォルダ以外のリポジトリなら、4. で `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

変更の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 実装の説明を書く

出力された「実装の説明」のパスに、Write ツールで Markdown を書く。差分そのものはスクリプトが渡すので書き写さない。Codex はこの会話を見られないので、差分だけではわからないことを書く。

- **目的と要件**: 何のための変更か。満たすべき要件・制約（Issue や設計書があればその要点）
- **実装の概要**: どこをどう変えたか、主な判断
- **決定事項**: ユーザーとの会話で決まったこと（Codex が蒸し返さないように）
- **やっていないこと**: 意図的にスコープ外にしたもの
- **確認済みのこと**: 実行したテスト・ビルド・手動確認とその結果
- **気になっている点**: Claude 自身が自信のない箇所

秘密情報（トークン、パスワード、個人情報）は書かない。この会話で実装したのではない変更（ユーザーや他の人の変更）なら、わかる範囲で書けばよい。

### 4. Codex にレビューさせる

Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと 10 分以上かかる）。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} [--fast] [--cd <dir>] [--base <ref> | --commit <sha> | --uncommitted] <実行フォルダ>
```

- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- Codex は読み取り専用のサンドボックスで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。コードを書き換えることはない。
- 「レビューする変更がありません」と出たら、範囲を確かめてユーザーに伝える（例: すでに既定ブランチにコミット・プッシュ済みなら `--commit` で指定してもらう）。
- その他のエラーなら内容を伝えて終わる。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。

### 5. 指摘を判断する

指摘はうのみにしない。指摘ごとに、該当のファイルを Read / Grep で確かめ、「再現」に書かれた条件で本当に問題が起きるかを根拠をもって判断する。Codex の指摘が誤っていれば「不採用」とし、理由を書く。

### 6. 直す

- **この会話で Claude が実装した変更**なら、「採用」とした指摘は直してよい（実装の続きとして扱う）。直したら関係するテストを実行する。ただし、設計を大きく変える修正や、ユーザーの決定事項に反する修正は直さず「要確認」にする。
- **それ以外の変更**（ユーザーや他の人のコード、既存の PR など）は直さず、修正案の提示にとどめる。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

スクリプトの出力の先頭（設定・範囲・所要時間・保存先・`codex resume` の行）をそのまま表示し、続けて次を日本語で簡潔に書く。Codex のレビュー全文は貼らない（保存先にある）。

```markdown
## Codex の総評
（1〜2 行で要約）

## 指摘への判断
| 重要度 | 指摘 | 場所 | 判断 | 理由・対応 |
| --- | --- | --- | --- | --- |
| 高 | ... | `path:line` | 採用（修正済み） / 採用（修正案） / 不採用 / 要確認 | ... |

## 修正内容
（6. で直したものと、実行したテストの結果。直していなければ修正案を箇条書きで）

## ユーザーに確認したいこと
（Codex の「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 修正後にもう一度レビューする場合は、新しい実行フォルダを作り、実装の説明に「前回レビューへの対応」の節を加えてから 2. からやり直す。
