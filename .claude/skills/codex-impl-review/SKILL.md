# Codex による実装レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が実装した変更を、別のモデル（Codex CLI の GPT-6.1 Sol）に独立してコードレビューさせ、その指摘を Claude が吟味する。差分の取り出し・Codex の呼び出し・保存はスクリプトに任せ、Claude は「実装の説明をまとめる」「指摘を判断する」「採用した指摘を直す」だけを行う。結果は `artifacts/codex-impl-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Claude が実装を終えて完了を報告する前、またはコミット・PR を頼まれてまだレビューしていない変更があるときに、次の基準で判断する。**迷ったら使う。**

**使う**（次のどれかに当たる）

- 新機能の追加、既存の振る舞いを変える修正、リファクタリングで、ロジックの変更が 2 ファイル以上か、数十行（目安 30 行）以上ある
- 規模にかかわらず、次に触れる変更
  - DB スキーマ、公開 API・インターフェース、設定ファイルの形式、データ移行
  - 認証・権限・課金・個人情報・秘密情報
  - 並行処理、キャッシュ、再試行、データの整合性
  - 外部からの入力の解析・検証、データの削除・変換
- 原因の調査が必要だったバグ修正（直し方が正しいか、ほかを壊していないかを独立に確かめる）
- テストがない、または書きにくい箇所の変更
- haiku-impl で Haiku に書かせた変更をまとめ終えたとき（Claude のレビューとは別の目で見る）

**使わない**

- 数行の変更、typo レベルの修正、文言・設定値・コメント・ドキュメントだけの変更、自動生成ファイルや依存のバージョン更新だけの変更
- ユーザーが「レビューは不要」「急ぎ」と言っている
- 同じ変更をこの会話ですでにレビュー済みで、その後の修正が小さい（指摘への対応で大きく書き換えたら、もう一度レビューする）
- 対象が git リポジトリでない

**自分の判断で使うときの違い**

- 1 つの変更に自分の判断で付けるレビュアーは、基本はこのスキルの Sol 1 本だけにする。増やすのは「観点ごとに分けて並列でレビューするとき」の条件に当たるときだけ。
- 変更が codex-risk-impl-review の「聞く」条件（データ移行・認可・課金・外部への送信など、壊れると影響が大きく戻しにくいもの）に当たるときは、先に codex-risk-impl-review の聞き方で Astra を使うかをユーザーに聞き、その答えに従う（Astra を選ばれたらこのスキルは使わない）。
- 始める前に「完了を報告する前に Codex にレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。Fast モードはユーザーの指定がない限り使わない。
- Codex が動いている間に、テストの実行や完了報告の下書きなど、レビュー結果に左右されない作業を進めてよい。
- Codex がエラーで動かなかったら、そのことを 1 行伝えて、レビューなしで完了を報告する。

## 観点ごとに分けて並列でレビューするとき

**基本は Sol 1 本**で全観点を見る。並列にすると観点ごとに深く見られ、所要時間は一番遅い観点とほぼ同じで済むが、Codex の使用量も、Claude が読んで判断する指摘も観点の数だけ増える。そのため、次のどれかに**はっきり当たるときだけ**、確認を待たずに観点ごとに分けて Sol を並列に動かす。当たるか迷ったら 1 本にする。

1. ユーザーに「観点ごとに分けて」「並列でレビューして」と頼まれた
2. 変更が大きい: 15 ファイル以上か、差分が 500 行以上（追加と削除の合計。自動生成ファイル・ロックファイル・スナップショットは数えない）
3. 次の領域のうち 2 つ以上に触れる: DB スキーマ・データ移行 / 認証・権限 / 課金・決済 / 個人情報・秘密情報 / 並行処理・トランザクション / 外部からの入力の解析・検証 / 外部への送信・公開 API

「重要そう」「なんとなく不安」だけでは並列にしない。

分けるときは、変更に関係する観点だけを 2〜3 本選ぶ（例: 外部からの入力も権限も扱わないなら `security` は外す）。4 本すべてにするのは、ユーザーに頼まれたときだけにする。

2. か 3. に当たって自分の判断で並列にしたときは、Sol の指摘を直し終えたあと、仕上げに opus-final-review も使う（1. だけのときは使わない）。

| 観点 | 見るもの |
| --- | --- |
| `correctness` | バグ・ロジックの誤り、要件との一致、既存コードとの整合 |
| `reliability` | 例外・再試行・競合・部分的な失敗、性能 |
| `security` | 入力の検証、認可、秘密情報、インジェクション |
| `maintainability` | テストの不足、重複・不要な抽象化 |

自分の判断で分けるときは、「完了を報告する前に Codex に観点ごとに並列でレビューさせます（correctness / reliability、effort=<レベル>）」と 1 行伝える。

## 手順

### 1. 引数を読む

- `--fast` または `fast` があれば Fast モードにする（速いぶん Codex の使用量が増える）。それ以外の依頼文に「速く」「fast で」とあっても同じ。
- `--focus <観点>,...` があれば、そのまま 4. に渡す。「観点ごとに分けて」「並列で」とあれば、「観点ごとに分けて並列でレビューするとき」の表から関係する観点を選んで渡す。
- 範囲の指定があればそのまま 4. に渡す。「未コミットだけ」→ `--uncommitted`、「このコミット」→ `--commit <sha>`、「develop との差分」→ `--base develop`。指定がなければ渡さない（既定ブランチから分岐して以降の変更を、未コミットも含めてすべてレビューする）。
- 対象が今のフォルダ以外のリポジトリなら、4. で `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

変更の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 実装の説明を書く

出力された「実装の説明」のパスに、Write ツールで Markdown を書く。差分そのものはスクリプトが渡すので書き写さない。Codex はこの会話を見られないので、差分だけではわからないことを書く。

- **目的と要件**: 何のための変更か。満たすべき要件・制約（Issue や設計書があればその要点）
- **実装の概要**: どこをどう変えたか、主な判断
- **決定事項**: ユーザーとの会話で決まったこと（Codex が蒸し返さないように）
- **やっていないこと**: 意図的にスコープ外にしたもの
- **確認済みのこと**: 実行したテスト・ビルド・手動確認とその結果
- **気になっている点**: Claude 自身が自信のない箇所

秘密情報（トークン、パスワード、個人情報）は書かない。この会話で実装したのではない変更（ユーザーや他の人の変更）なら、わかる範囲で書けばよい。

### 4. Codex にレビューさせる

Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと 10 分以上かかる）。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} [--fast] [--cd <dir>] [--base <ref> | --commit <sha> | --uncommitted] [--focus <観点>,...] <実行フォルダ>
```

- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- 観点ごとに分けるときは `--focus correctness,reliability` のように観点をカンマ区切りで渡す。1 回の呼び出しの中で観点の数だけ Codex が並列に動き、全員に同じ差分と説明が渡る。結果は観点ごとに `review-<観点>.md` に保存される。一部の観点だけ失敗したら、成功した観点の結果で判断し、失敗した観点を報告で伝える。
- Codex は読み取り専用のサンドボックスと 1M コンテキストで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。コードを書き換えることはない。
- 「レビューする変更がありません」と出たら、範囲を確かめてユーザーに伝える（例: すでに既定ブランチにコミット・プッシュ済みなら `--commit` で指定してもらう）。
- その他のエラーなら内容を伝えて終わる。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。

### 5. 指摘を判断する

観点ごとに分けたときは、観点をまたいで同じ指摘をまとめてから判断する（7. の表では「指摘」の列の頭に `[security]` のように観点を書く）。「[担当外]」の指摘も同じように判断する。

指摘はうのみにしない。指摘ごとに、該当のファイルを Read / Grep で確かめ、「再現」に書かれた条件で本当に問題が起きるかを根拠をもって判断する。Codex の指摘が誤っていれば「不採用」とし、理由を書く。

### 6. 直す

- **この会話で Claude が実装した変更**なら、「採用」とした指摘は直してよい（実装の続きとして扱う）。直したら関係するテストを実行する。ただし、設計を大きく変える修正や、ユーザーの決定事項に反する修正は直さず「要確認」にする。
- **それ以外の変更**（ユーザーや他の人のコード、既存の PR など）は直さず、修正案の提示にとどめる。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

スクリプトの出力の先頭（設定・範囲・所要時間・保存先・`codex resume` の行）をそのまま表示し、続けて次を日本語で簡潔に書く。Codex のレビュー全文は貼らない（保存先にある）。

```markdown
## Codex の総評
（1〜2 行で要約）

## 指摘への判断
| 重要度 | 指摘 | 場所 | 判断 | 理由・対応 |
| --- | --- | --- | --- | --- |
| 高 | ... | `path:line` | 採用（修正済み） / 採用（修正案） / 不採用 / 要確認 | ... |

## 修正内容
（6. で直したものと、実行したテストの結果。直していなければ修正案を箇条書きで）

## ユーザーに確認したいこと
（Codex の「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 修正後にもう一度レビューする場合は、新しい実行フォルダを作り、実装の説明に「前回レビューへの対応」の節を加えてから 2. からやり直す。
