# Codex Astra による設計のリスクレビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

壊れると影響が大きく後から戻しにくい設計を、実装に入る前に、最も強いモデル（Codex CLI の GPT-6 Astra）に「どう壊れるか」の観点で独立してレビューさせ、その指摘を Claude が吟味する。Codex の呼び出しと保存はスクリプトに任せ（codex-design-review のスクリプトを、モデルとレビューの指示書だけ差し替えて使う）、Claude は「設計書をまとめる」「指摘を判断する」だけを行う。結果は `artifacts/codex-risk-design-review/` に保存される。

## 使うかどうかをユーザーに聞くとき

Astra は重く、使用量も多い。**ユーザーに頼まれていなければ、自分の判断では実行しない。** 代わりに、次の条件に当たるときだけ使うかどうかを聞く。

**聞く**（Claude が設計や実装計画をまとめ、ユーザーに提示する（または実装を始める）前に、設計が次のどれかに触れる）

- DB スキーマの設計・変更、データ移行、本番データの削除・一括変換
- 認証・認可・権限の仕組み、セッション・トークンの扱い
- 課金・決済・ポイントなどお金に関わる処理
- 個人情報・秘密情報の保存・送信・ログ出力、暗号
- 並行処理、ロック、トランザクション、分散環境での整合性・冪等性
- メール・Webhook・外部 API など、取り消せない外部への送信
- 公開 API・保存形式・ID の体系・外部との契約の決定や破壊的変更、デプロイ・インフラの構成
- その他、壊れると影響が大きく、後から戻しにくいとはっきり言えるもの

**聞かない**

- 上に当てはまらない通常の設計（それは codex-design-review の範囲）
- ユーザーが「レビューは不要」「急ぎ」と言っている、またはこの会話で同じ設計について一度断られた
- 同じ設計をこの会話ですでに Astra でレビュー済みで、その後の変更が小さい

**聞き方**

- AskUserQuestion で 1 問だけ聞く。質問には、どのリスクに当たるか（例: 「既存の注文テーブルを分割する移行がある」）を 1 行で添える。選択肢は「Astra でレビューする」「Fast モードで Astra レビューする」「Sol の通常レビューにする」「レビューしない」。
- 「Astra」を選ばれたら、このスキルの手順を進める。codex-design-review は重ねて実行しない。
- それ以外を選ばれたら、このスキルは使わず、その答えに従う（「Sol の通常レビュー」なら codex-design-review を使う）。
- 聞いている間は設計を提示しない。答えを待ってから、レビューの結果とあわせて提示する（「レビューしない」なら、そのまま提示する）。

## 手順

### 1. 引数を読む

- `--fast` または `fast` があれば Fast モードにする（速いぶん Codex の使用量が増える）。それ以外の依頼文に「速く」「fast で」とあるときや、聞いたときに Fast を選ばれたときも同じ。
- ファイルパスがあれば、それをレビュー対象の設計書とする。
- パスがなければ、この会話で Claude が考えた直近の設計案を対象にする。設計案が会話にないときは、何をレビューするかを尋ねて終わる。

### 2. 実行フォルダを作る

設計の内容を表す短い英数字の名前（例: `order-table-split`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 設計書を書く

出力された「設計書」のパスに、Write ツールで Markdown を書く。ファイルを渡された場合も、内容をそのまま書き写したうえで、下の不足分を補う。

Codex はこの会話を見られないので、設計書だけで判断できるように次を含める。

- **目的と背景**: 何を解決するか、なぜ今か
- **要件・制約**: 機能要件、非機能要件、変えてはいけないもの
- **リスクのある箇所**: どこが、なぜ危ないと考えたか（データ移行、認可、課金など）
- **設計**: 構成、データの流れ、主要なインターフェース、状態の持ち方（必要なら Mermaid 図）
- **移行とリリースの手順**: 既存データの扱い、デプロイの順序、新旧のコードが混在する期間、ロールバックの方法（わかる範囲で）
- **本番の前提**: わかる範囲で、データの量、同時実行の度合い、外部サービスの制約
- **検討した代替案**と選ばなかった理由
- **関連する既存コード**: 作業フォルダからの相対パス（Codex が読んで確かめる）
- **決定事項**: ユーザーとの会話で決まったこと（Codex が蒸し返さないように）
- **気になっている点**: Claude 自身が自信のない判断

秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. Codex にレビューさせる

Bash ツールを **`run_in_background: true`** で実行する（Astra は推論レベルが高いと数十分かかることがある）。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} [--fast] [--cd <dir>] <実行フォルダ>
```

- `--effort` には上の「Claude の推論レベル」をそのまま渡す（Claude が high なら Codex も high）。空や `auto` のときは省略してよい（スクリプトが high にする）。
- 設計が今のフォルダ以外のリポジトリについてのものなら、`--cd <そのリポジトリのパス>` をつける。
- Codex は読み取り専用のサンドボックスで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。
- エラーなら内容を伝えて終わる。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。Astra が使えない（プランの対象外など）ときは、そのことを伝え、codex-design-review（Sol）に切り替えるかを聞く。

### 5. 報告する

スクリプトの出力の先頭（設定・所要時間・保存先・`codex resume` の行）をそのまま表示し、続けて次を日本語で簡潔に書く。Codex のレビュー全文は貼らない（保存先にある）。

```markdown
## Codex の総評
（1〜2 行で要約。実装に進めてよいかの判断と、最悪の場合に何が起きるか）

## 指摘への判断
| 重要度 | 指摘 | 判断 | 理由 |
| --- | --- | --- | --- |
| 高 | ... | 採用 / 一部採用 / 不採用 / 要確認 | ... |

## 設計の修正案
（採用した指摘をもとに、設計のどこをどう変えるか。箇条書きで）

## 実装・リリースで守ること
（Codex の「実装・リリースで守るべきこと」のうち妥当なもの。なければ省く）

## ユーザーに確認したいこと
（Codex の「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 指摘はうのみにしない。必要なら指摘されたファイルを Read / Grep で確かめ、根拠をもって判断する。Codex の指摘が誤っていれば「不採用」とし、理由を書く。本番の状態に左右されて判断できないものは「要確認」にする。
- まだユーザーに見せていない Claude 自身の設計案なら、「採用」とした指摘を設計に反映してから提示してよい。その場合も、表で何を採用し何を変えたかを示す。それ以外（ユーザーが書いた設計書など）は修正案の提示にとどめ、了承なしに書き換えない。
- 「実装・リリースで守ること」は、実装に入ったら守り、実装後に codex-risk-impl-review を使うときは実装の説明の「リスクのある箇所」に書き写す。
- 修正後にもう一度レビューする場合は、新しい実行フォルダを作り、設計書に「前回レビューへの対応」の節を加えてから 2. からやり直す（重要度「高」を直したときは、もう一度 Astra にかけるかをユーザーに聞く）。
