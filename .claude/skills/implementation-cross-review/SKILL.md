# Sol と Opus による実装レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が実装した変更を、Sol（Codex CLI の GPT-6.1 Sol）と Opus（`opus-reviewer`）に**同じ依頼で**レビューさせ、その指摘を Claude が吟味する。同じ観点を別のモデルで見て、単一モデルの見落としを補う。どちらも要件と差分から実際の動きを読み解くので、実装者の先入観が入らない。差分の取り出し・プロンプトの組み立て・Codex の呼び出しはスクリプトに任せ、Claude は「要件をまとめる」「指摘を判断する」「採用した指摘を直す」だけを行う。結果は `artifacts/implementation-cross-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Claude が実装を終えて完了を報告する前、またはコミット・PR を頼まれてまだレビューしていない変更があるときに、次の基準で判断する。**迷ったら使う。**

**使う**: 動作が変わりうる変更すべて。テストだけの変更や、文章が動作を決めるファイル（プロンプト、スキルやエージェントの定義、設定ファイル）の変更も含む。動作を決めない文書（README など）だけの変更は、内容のずれを Opus だけで確かめる。haiku-implementation で Haiku に書かせた変更は、まとめ終えたときに、ユーザーが不要と言ったときを除き必ず使う（Claude のレビューとは別の目で見る）。

**使わない**（コードや内容の欠陥が起こりえないか、このレビューでは見つけられない、次の場合だけ）

- 意味を変えない修正: typo・整形・コメントだけの変更、自動生成ファイルの再生成だけの変更
- 依存パッケージのバージョンだけを変える変更（レビュアーは外部の変更点を確かめられないので、haiku-check でテストと依存の脆弱性検査を確かめる）
- ユーザーが「レビューは不要」と言っている
- 下の「レビュアーの決め方」で、動かす担当が残らない
- 対象が git リポジトリでない

見送るときは、当てはまる項目を完了報告に 1 行書く。書けないときは実行する。

**再レビュー**: 要否は、直した分の差分だけで判断する。レビューで重要度「高」の指摘を直したとき、直す中で要件の解釈を変えたとき、指摘の範囲を超えて変更したとき、新たにリスク領域に触れたときにもう一度使う。レビューには全体の差分を渡す。担当は下の「レビュアーの決め方」で決め、この会話で片方だけを指定されていれば同じ担当にする。同じ変更への再レビューは 2 回までにし、残る指摘はユーザーに伝える。

**自分の判断で使うときの違い**

- Sol と Opus は同じ依頼で、別のモデルの見落としを補い合う。codex-risk-implementation-review の Astra は壊れ方を、テストは回帰を見る。それぞれの条件に当たるものはすべて使う。
- レビューの前に haiku-check でテストを済ませる。範囲は変更に関係するテストと型チェック・リンター（完了の報告の前には全体）。環境がない・もとから失敗しているなどで実行できないときは、その理由を報告に書いてレビューに進む。テストの結果はレビュアーに渡さない。
- 変更が codex-risk-implementation-review の「聞く」条件（データ移行・認可・課金・外部への送信など、壊れると影響が大きく戻しにくいもの）に当たるとき、または当たるか迷うときは、先に codex-risk-implementation-review の聞き方で Astra を加えるかをユーザーに聞く（そのスキルの「聞かない」に当たるとき、たとえばユーザーが「急ぎ」と言っているときは聞かず、Astra なしで進める）。加えると選ばれたら、codex-risk-implementation-review の手順で、このスキルと同じ範囲・同じ変更の状態に対して並べて実行する（**すべて終わるまでファイルを編集しない**）。
- 始める前に「完了を報告する前に <動かす担当> に要件と差分だけでレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。
- レビューが動いている間に、テストの実行や完了報告の下書きなど、レビュー結果に左右されない作業を進めてよい（ファイルは編集しない）。
- レビュアーが動かなかったら、そのことを 1 行伝える。ほかの担当や Astra を並べているときは、全部の結果が出揃ってから、成功した分で判断して報告する。どれも結果を返さなければ、レビューなしで完了を報告する。ただし、Haiku に書かせた変更で、動かしたレビューがどれも結果を返さなかったら、未レビューと明記し、完了を保留してユーザーに確認する。

## レビュアーの決め方

次の順に決める。

1. **指定**: `--only sol`・`--only opus`、または「Sol だけ」「Codex だけ」「Opus だけ」と言われたら、その担当だけを動かす（レビュー済みでも動かす）。`--only` の値が `sol` / `opus` 以外なら、そのことを伝えて止める。「Opus でレビューして」「Codex にレビューしてもらって」のように名前を挙げただけの依頼は、指定に数えない。
2. **直接の依頼**: `/implementation-cross-review` やレビューを頼まれたら、文書だけの変更でも、レビュー済みでも、Sol と Opus を動かす。
3. **自分の判断で使うとき**: 動作を決めない文書（README など）だけの変更は Opus、それ以外は Sol と Opus を対象にする。そこから、同じ変更の状態をこの会話ですでにレビューして結果を受け取った担当を除く。残りがなければ動かさない。

## 手順

### 1. 引数を読む

- `--only` は「レビュアーの決め方」に使う（`prepare.sh` には渡さない）。
- 範囲の指定があればそのまま 4. の `prepare.sh` に渡す。「未コミットだけ」→ `--uncommitted`、「このコミット」→ `--commit <sha>`、「develop との差分」→ `--base develop`。指定がなければ渡さない（既定ブランチから分岐して以降の変更を、未コミットも含めてすべてレビューする）。
- 対象が今のフォルダ以外のリポジトリなら、4. の `prepare.sh` に `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

変更の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。動かす担当はこの 1 つのフォルダを共有する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 要件を書く

出力された「要件」のパスに、Write ツールで Markdown を書く。依頼した人の立場で「何を求めたか」だけを書く。レビュアーに渡る説明はこれだけなので、要件の判定の基準になる。

**書くもの**

- **依頼**: ユーザーの元の依頼。できるだけユーザーの言葉のまま引用する
- **要件・受け入れ条件**: 満たすべきこと。Issue・設計書・仕様があればその要点（URL やファイルのパスがあれば添える）。番号を振る（R1, R2, …）
- **ユーザーが決めた仕様・制約**: 会話の中でユーザーが決めた「何をするか」「何をしないか」。ユーザー自身が実装の方法を指定したなら、それも制約として書く
- **スコープ外**: ユーザーが明示的に外したもの

**書かないもの**

- どこをどう変えたか、なぜその書き方にしたか、どの案から選んだか
- 実行したテストとその結果、Claude が自信のない箇所
- ほかのレビューの指摘とその対応

要件があいまいなまま実装したなら、あいまいなまま書く（Claude の解釈で補わない）。この会話で実装したのではない変更なら、わかる範囲で書けばよい。秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. レビューさせる

まず、同じ依頼（`prompt.md`）を作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/prepare.sh" [--cd <dir>] [--base <ref> | --commit <sha> | --uncommitted] <実行フォルダ>
```

- 「レビューする変更がありません」と出たら、範囲を確かめてユーザーに伝える（例: すでに既定ブランチにコミット・プッシュ済みなら `--commit` で指定してもらう）。その他のエラーなら内容を伝えて終わる。
- `--commit` では当時のソースを `<実行フォルダ>/tree` に展開して読ませる。

続けて、動かす担当を**同じメッセージで**動かす。**すべて終わるまでファイルを編集しない**（どのレビュアーも作業ツリーを読むため）。

Sol は Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと 10 分以上かかる）。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} <実行フォルダ>
```

Opus は Agent ツールで呼ぶ。

- `subagent_type`: `opus-reviewer`（必ず指定する。`fork` や省略で会話を引き継ぐ形にしない）
- `effort`: 上の「Claude の推論レベル」。空や `auto` のときは `high`
- `model`: **渡さない**（引数は別名しか受け付けず、親と同じ系統なら親のモデルになって、定義の `claude-opus-5-5` の固定が外れる）
- `prompt`: 次の 1 行だけにする

  ```text
  <実行フォルダ>/prompt.md を読み、その指示に従ってレビューしてください。
  ```

- どちらも終わると通知が来るので、それまで待つ。ポーリングはしない。
- Opus の返答は、そのまま `<実行フォルダ>/review-opus.md` に Write で保存する。Sol の結果は `<実行フォルダ>/review.md` に保存される。
- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- Sol は読み取り専用のサンドボックスと 1M コンテキストで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。Opus は Read / Grep / Glob しか使えず、この会話・auto memory・ユーザー用の CLAUDE.md・MCP は読み込まない（作業場所のルートの CLAUDE.md・`.claude/CLAUDE.md`・AGENTS.md は `prompt.md` に入る）。どちらもコードを書き換えない。
- `codex` や `opus-reviewer` が失敗しても、全部の結果が出揃ってから、成功した分で判断して失敗を報告で伝える。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。`opus-reviewer` が見つからないときは、エージェントがリンクされていない（このスキル集の `scripts/link-skills.sh --claude` で `~/.claude/agents` にリンクする）か、リンクする前に始めたセッション。Haiku に書かせた変更で、動かしたレビューがどれも結果を返さなかったら、未レビューと明記し、完了を保留してユーザーに確認する。

### 5. 指摘を判断する

すべての結果が揃ってから、次をまとめて判断する。Astra を並べたときも同じ表にまとめる。

- **この変更がしていること**: Claude が意図した実装と照らし合わせる。食い違いがあれば、レビュアーの読み違いか、実装が意図どおりになっていないかのどちらかなので、コードで確かめる。
- **要件ごとの判定**: どちらかが「一部だけ」「満たさない」「判断できない」としたものを確かめる。判定が食い違えば、R 番号ごとにコードで確かめる。
- **指摘と要件にない変更**: 原因が同じものは 1 件にまとめ、見つけた担当を頭に書く（`[Sol]`・`[Opus]`・`[Sol・Opus]`・`[Astra]`）。

指摘はうのみにしない。両方が挙げたものも同じで、指摘ごとに該当のファイルを Read / Grep で確かめ、「再現」に書かれた条件で本当に問題が起きるかを根拠をもって判断する。誤りなら「不採用」とし、理由を書く。レビュアーは実装の経緯を知らないので、ユーザーとの会話で決めたことに反する指摘は「不採用（決定事項）」としてよい。ただし、その決定事項を 3. の要件に書き漏らしていたなら、それも報告で触れる。

判断の表（7. の「指摘への判断」と同じ形）、各レビューの実行状態（成功・失敗・省略）、件数の行を `<実行フォルダ>/decisions.md` に Write で保存する。どれも結果を返さなかった回も、実行状態を残す。あとでモデルごとの効果を確かめるのに使う。

### 6. 直す

- **この会話で Claude が実装した変更**なら、「採用」とした指摘は直してよい（実装の続きとして扱う）。直したら関係するテストを実行する。ただし、設計を大きく変える修正や、ユーザーの決定事項に反する修正は直さず「要確認」にする。
- **それ以外の変更**（ユーザーや他の人のコード、既存の PR など）は直さず、修正案の提示にとどめる。
- 修正の担当は、Haiku に任せるかどうかも含めて haiku-implementation の基準で決める。
- 「要件にない変更」で、意図しない変更や残ったデバッグコードだったものは取り除く。意図した変更なら、報告でその理由を書く。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

Sol を動かしたら、スクリプトの出力の先頭（設定・範囲・所要時間・保存先・`codex resume` の行）をそのまま表示する。Opus を動かしたら、設定（`opus-reviewer` / effort）・範囲（`prepare.sh` の出力）・所要時間とトークン（完了の通知）・保存先を短く添える。続けて次を日本語で簡潔に書く。レビューの全文は貼らない（保存先にある）。

```markdown
## レビューの総評
（動かした担当ごとに 1 行で要約）

## 要件の充足
（どちらかが「満たす」以外とした要件と、その扱い。すべて満たしていれば「すべて満たす」の 1 行）

## 指摘への判断
| 重要度 | 指摘 | 場所 | 判断 | 理由・対応 |
| --- | --- | --- | --- | --- |
| 高 | [Sol・Opus] ... | `path:line` | 採用（修正済み） / 採用（修正案） / 不採用 / 要確認 | ... |

両方 n 件、Sol だけ n 件、Opus だけ n 件（うち採用 n 件、不採用 n 件）

## 修正内容
（6. で直したものと、実行したテストの結果。直していなければ修正案を箇条書きで）

## ユーザーに確認したいこと
（「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 件数の行は Sol と Opus の両方が成功した回だけ書き、それ以外は「比較なし」と書く。
- 直したあとは haiku-check でもう一度テストを実行する。
- 同じレビューについて Opus に追加で確かめたいことがあれば、SendMessage で聞いてよい。
- もう一度レビューするのは、上の「再レビュー」の条件に当たるときだけにする。そのときは SendMessage で続けず、新しい実行フォルダと新しいエージェントで、同じ要件を書いて 2. からやり直す。前回の指摘や対応は書かない（先入観を渡さないため）。
