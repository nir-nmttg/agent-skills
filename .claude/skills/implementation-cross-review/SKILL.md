# Astra と Fable による実装レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が実装した変更を、Astra（Codex CLI の GPT-6 Astra）と Fable（`fable-reviewer`）に**同じ依頼で**レビューさせ、その指摘を Claude が吟味する。同じ観点を別のモデルで見て、単一モデルの見落としを補う。どちらも要件と差分から実際の動きを読み解くので、実装者の先入観が入らない。正しさや要件との一致に加えて、データ・認可・お金・外部への送信・移行・並行処理など壊れると影響の大きい部分では、壊れ方も重点的に見る。Astra が使えないときは Sol（GPT-6.1 Sol）で、Fable の利用枠が足りないときは Opus（`opus-reviewer`）で代わりに動かす。直したあとの再レビューは、直した部分の確認に絞って Astra に任せる。差分の取り出し・プロンプトの組み立て・Codex の呼び出しはスクリプトに任せ、Claude は「要件をまとめる」「指摘を判断する」「採用した指摘を直す」だけを行う。結果は `artifacts/implementation-cross-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Claude が実装を終えて完了を報告する前、またはコミット・PR を頼まれてまだレビューしていない変更があるときに、次の基準で判断する。**迷ったら使う。**

**使う**: 動作が変わりうる変更すべて。テストだけの変更や、文章が動作を決めるファイル（プロンプト、スキルやエージェントの定義、設定ファイル）の変更も含む。動作を決めない文書（README など）だけの変更は、内容のずれを Fable だけで確かめる。haiku-implementation で Haiku に書かせた変更は、まとめ終えたときに、ユーザーが不要と言ったときを除き必ず使う（Claude のレビューとは別の目で見る）。

**使わない**（次の場合だけ）

- 意味を変えない修正: typo・整形・コメントだけの変更、自動生成ファイルの再生成だけの変更
- 依存パッケージのバージョンだけを変える変更（レビュアーは外部の変更点を確かめられないので、haiku-check でテストと依存の脆弱性検査を確かめる）
- ユーザーが「レビューは不要」と言っている
- 下の「レビュアーの決め方」で、動かす担当が残らない
- 対象が git リポジトリでない

見送るときは、当てはまる項目を完了報告に 1 行書く。書けないときは実行する。

**再レビュー**: 1 回目のレビューを通っているので、再レビューは直した部分の確認に絞り、Astra に任せる（下の「確認のレビュー」）。確かめるのは、直しで元の問題が解決したかと、直したことで新しい不具合が生じていないかの 2 つ。要否は直した分だけで判断し、重要度「高」の指摘を直すために新しい仕組み（状態・ロック・再試行・新しいメッセージや項目など）を足したとき、直す中で指摘の範囲を超えて変更したとき、新たにリスク領域に触れたときに使う。この条件に当たらなければ使わず、直した部分はテストで確かめる。直す中で作り方（選ぶ案）か要件の解釈を変えたときは、直した部分の確認では足りないので、1 回目と同じく Astra と Fable にゼロからレビューさせる（下の「ゼロからレビューし直すとき」）。どちらも再レビューに数え、同じ変更への再レビューは 1 回までにし、残る指摘はユーザーに伝える。

**自分の判断で使うときの違い**

- Astra と Fable は同じ依頼で、別のモデルの見落としを補い合う。テストは回帰を見る。それぞれの条件に当たるものはすべて使う。
- レビューの前に haiku-check でテストを済ませる。範囲は変更に関係するテストと型チェック・リンター（完了の報告の前には全体）。環境がない・もとから失敗しているなどで実行できないときは、その理由を報告に書いてレビューに進む。テストの結果はレビュアーに渡さない。
- 始める前に「完了を報告する前に <動かす担当> に要件と差分だけでレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。
- レビューが動いている間に、テストの実行や完了報告の下書きなど、レビュー結果に左右されない作業を進めてよい（ファイルは編集しない）。
- レビュアーが動かなかったら、そのことを 1 行伝える。ほかの担当を並べているときは、全部の結果が出揃ってから、成功した分で判断して報告する。どれも結果を返さなければ、レビューなしで完了を報告する。ただし、Haiku に書かせた変更で、動かしたレビューがどれも結果を返さなかったら、未レビューと明記し、完了を保留してユーザーに確認する。

## レビュアーの決め方

次の順に決める。

1. **指定**: `--only astra`・`--only fable`、または「Astra だけ」「Codex だけ」「Fable だけ」と言われたら、その担当だけを動かす（レビュー済みでも動かす）。`--only` の値が `astra` / `sol` / `fable` / `opus` 以外なら、そのことを伝えて止める。「Fable でレビューして」「Codex にレビューしてもらって」のように名前を挙げただけの依頼は、指定に数えない。
2. **直接の依頼**: `/implementation-cross-review` やレビューを頼まれたら、文書だけの変更でも、レビュー済みでも Astra と Fable を動かす。
3. **自分の判断で使うとき**: 動作を決めない文書（README など）だけの変更は Fable、それ以外は Astra と Fable を対象にする。そこから、同じ変更の状態をこの会話ですでにレビューして結果を受け取った担当を除く。残りがなければ動かさない。

「Sol で」と言われたとき、`--only sol` や「Sol だけ」と言われたとき、この会話で Astra がモデルを使えない・プランの対象外・使用量の上限の理由で失敗していたときは、Astra の代わりに Sol で動かす（4. で `--model gpt-6.1-sol` を渡す。`--only sol`・「Sol だけ」なら Fable は動かさない）。

「Opus で」と言われたとき、`--only opus` や「Opus だけ」と言われたとき、4. で確かめた Fable の利用枠が足りないとき、利用枠を確かめられないうえに、この会話で Fable が利用枠の不足で失敗していたときは、Fable の代わりに Opus（`opus-reviewer`）で動かす（`--only opus`・「Opus だけ」なら Astra は動かさない）。Opus で代わりに動かした回も Fable の担当として数え、レビュー済みの担当を除くときも同じに扱う。

確認のレビューは Astra（使えなければ上のとおり Sol）1 体で動かす。文書だけの変更でも同じにする。ユーザーが 1. で担当を指定していたときはその担当、この会話で Astra が `codex` が見つからない・ログインしていない・ネットワークなどの理由で動かなかったときは Fable（利用枠によっては Opus）で動かす。

## 手順

### 1. 引数を読む

- `--only` は「レビュアーの決め方」に使う（`prepare.sh` には渡さない）。
- 範囲の指定があればそのまま 4. の `prepare.sh` に渡す。「未コミットだけ」→ `--uncommitted`、「このコミット」→ `--commit <sha>`、「develop との差分」→ `--base develop`。指定がなければ渡さない（既定ブランチから分岐して以降の変更を、未コミットも含めてすべてレビューする）。
- 対象が今のフォルダ以外のリポジトリなら、4. の `prepare.sh` に `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

変更の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。動かす担当はこの 1 つのフォルダを共有する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 要件を書く

出力された「要件」のパスに、Write ツールで Markdown を書く。依頼した人の立場で「何を求めたか」だけを書く。レビュアーに渡る説明はこれだけなので、要件の判定の基準になる。

**書くもの**

- **依頼**: ユーザーの元の依頼。できるだけユーザーの言葉のまま引用する
- **要件・受け入れ条件**: 満たすべきこと。Issue・設計書・仕様があればその要点（URL やファイルのパスがあれば添える）。番号を振る（R1, R2, …）
- **ユーザーが決めた仕様・制約**: 会話の中でユーザーが決めた「何をするか」「何をしないか」。ユーザー自身が実装の方法を指定したなら、それも制約として書く
- **スコープ外**: ユーザーが明示的に外したもの
- **本番の前提**（壊れると影響の大きい変更で、わかっているときだけ）: データの量、同時実行の度合い、デプロイの手順（新旧のコードが混在するか）、ロールバックの方法。会話・Issue・設定でわかっている事実だけを書き、推測で補わない

**書かないもの**

- どこをどう変えたか、なぜその書き方にしたか、どの案から選んだか
- 実行したテストとその結果、Claude が自信のない箇所
- ほかのレビューの指摘とその対応

要件があいまいなまま実装したなら、あいまいなまま書く（Claude の解釈で補わない）。この会話で実装したのではない変更なら、わかる範囲で書けばよい。秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. レビューさせる

まず、同じ依頼（`prompt.md`）を作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/prepare.sh" [--cd <dir>] [--base <ref> | --commit <sha> | --uncommitted] <実行フォルダ>
```

- 「レビューする変更がありません」と出たら、範囲を確かめてユーザーに伝える（例: すでに既定ブランチにコミット・プッシュ済みなら `--commit` で指定してもらう）。その他のエラーなら内容を伝えて終わる。
- `--commit` では当時のソースを `<実行フォルダ>/tree` に展開して読ませる。

続けて、動かす担当を**同じメッセージで**動かす。**すべて終わるまでファイルを編集しない**（どのレビュアーも作業ツリーを読むため）。

Astra は Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと数十分かかることがある）。Sol で動かすときは `--effort` の前に `--model gpt-6.1-sol` を加える。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} <実行フォルダ>
```

Fable は Agent ツールで呼ぶ。Fable を動かす予定なら、呼ぶ前に利用枠を確かめて、Fable と Opus のどちらで動かすかを決める。

- `mcp__ccd_session_mgmt__get_usage` を呼ぶ（読み込まれていなければ ToolSearch で `select:mcp__ccd_session_mgmt__get_usage` を読み込む）。`plan.windows` のうちラベルに Fable を含む枠の `percentUsed` が 1 つでも 95 以上なら、Fable の代わりに Opus で動かす（レビューを最後まで終えられる残りを確保するため）。`--only fable`・「Fable だけ」のときも同じにする。Opus に変えたときは、どの場合もそのことを 1 行伝える。
- ツールがない（ターミナルの Claude Code など）、呼び出しが失敗した・断られた、`plan.status` が `ok` でない、Fable の枠がないときは、利用枠を確かめられないとして Fable で動かす（この会話で Fable が利用枠の不足で失敗していたときは Opus で動かす）。この確認は担当を選ぶためだけに使い、結果によらずレビューと呼び出し元の作業を進める。
- この確認は担当を動かす前に済ませ、動かす担当はそのあと同じメッセージで動かす。

Agent ツールには次を指定する。

- `subagent_type`: `fable-reviewer`、Opus で動かすときは `opus-reviewer`（必ず指定する。省略や `fork` では、定義のモデルと読み取り専用の設定が効かない）
- `effort`: 上の「Claude の推論レベル」。空や `auto` のときは `high`
- `model`: **渡さない**（引数は別名しか受け付けず、親と同じ系統なら親のモデルになって、定義の `claude-fable-5-2`・`claude-opus-5-5` の固定が外れる）
- `prompt`: 次の 1 行だけにする

  ```text
  <実行フォルダ>/prompt.md を読み、その指示に従ってレビューしてください。
  ```

- どちらも終わると通知が来るので、それまで待つ。ポーリングはしない。
- Fable の返答は、そのまま `<実行フォルダ>/review-fable.md`（Opus なら `review-opus.md`）に Write で保存する。Astra（または Sol）の結果は `<実行フォルダ>/review.md` に保存される。
- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- Codex（Astra / Sol）は読み取り専用のサンドボックスと 1M コンテキストで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。Fable・Opus は Read / Grep / Glob しか使えず、この会話・auto memory・ユーザー用の CLAUDE.md・MCP は読み込まない（作業場所のルートの CLAUDE.md・`.claude/CLAUDE.md`・AGENTS.md は `prompt.md` に入る）。どちらもコードを書き換えない。
- Astra が、モデルを使えない・プランの対象外・使用量の上限などの理由で失敗したら、同じ実行フォルダに対して `--model gpt-6.1-sol` を加えて、Sol で 1 回だけやり直す（同じく `run_in_background: true`）。やり直すと Astra のログは上書きされるので、先に Astra の失敗の理由（エラーの要点）を控え、5. で `decisions.md` の実行状態に書く。その担当は報告で Sol と書く。モデルによらない失敗（`codex` がない・ログインしていない・ネットワークなど）はやり直さない。
- Fable が、利用枠・使用量の上限・レート制限などの理由で失敗したら、`opus-reviewer` で同じ 1 行の依頼を 1 回だけやり直す（Agent ツールの指定は Fable と同じ）。先に Fable の失敗の理由（エラーの要点）を控え、5. で `decisions.md` の実行状態に書く。その担当は報告で Opus と書く。利用枠によらない失敗（エージェントが見つからないなど）はやり直さない。
- `codex` や `fable-reviewer`・`opus-reviewer` が失敗しても、全部の結果が出揃ってから、成功した分で判断して失敗を報告で伝える。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。`fable-reviewer`・`opus-reviewer` が見つからないときは、エージェントがリンクされていない（このスキル集の `scripts/link-skills.sh --claude` で `~/.claude/agents` にリンクする）か、リンクする前に始めたセッション。Haiku に書かせた変更で、動かしたレビューがどれも結果を返さなかったら、未レビューと明記し、完了を保留してユーザーに確認する。

### 5. 指摘を判断する

すべての結果が揃ってから、次をまとめて判断する。

- **この変更がしていること**: Claude が意図した実装と照らし合わせる。食い違いがあれば、レビュアーの読み違いか、実装が意図どおりになっていないかのどちらかなので、コードで確かめる。
- **要件ごとの判定**: どちらかが「一部だけ」「満たさない」「判断できない」としたものを確かめる。判定が食い違えば、R 番号ごとにコードで確かめる。
- **指摘と要件にない変更**: 原因が同じものは 1 件にまとめ、見つけた担当を頭に書く（`[Astra]`・`[Fable]`・`[Astra・Fable]`。Sol・Opus で代わりに動かしたときは、Astra を Sol、Fable を Opus と書く）。

指摘はうのみにしない。両方が挙げたものも同じで、指摘ごとに該当のファイルを Read / Grep で確かめ、「再現」に書かれた条件で本当に問題が起きるかを根拠をもって判断する。誤りなら「不採用」とし、理由を書く。レビュアーは実装の経緯を知らないので、ユーザーとの会話で決めたことに反する指摘は「不採用（決定事項）」としてよい。ただし、その決定事項を 3. の要件に書き漏らしていたなら、それも報告で触れる。

**直すかどうか**: 本当に起きると確かめた指摘でも、直すかどうかは別に決める。直すとコードが増え、増えた分が新しい不具合の元になり、次のレビューで読まれる範囲も広がる。直して防げる害が、直して増える複雑さに見合うものだけを「採用」にする。

- 重要度「高」（データの破損・消失、セキュリティの穴、お金の誤り、戻せない変更、要件を満たさない不具合）は採用する。重要度はレビュアーの付けたものをうのみにせず、この定義で付け直す。付け直したときは、表の重要度を `高→中` のように両方書き、理由の欄に根拠を書く。
- 重要度「中」は、要件の範囲の中（この変更で壊れた既存の動きを含む）で、本番の前提（3. に書いたもの。なければこのプロジェクトの使われ方）で現実に起こりうるものを採用する。特殊な条件が重ならないと起きないものや、防ぐのに新しい仕組み（ロック・再試行・状態の記録など）が要る割に起きたときの害が小さいものは「見送り」にする。
- 重要度「低」は「見送り」にする。直しても分岐や状態が増えないもの（誤記、文言・メッセージの修正、文書とコードの食い違い）は採用してよい。確認やガードを足す修正は、数行で済んでも見送りにする。文章が動作を決めるファイルでは、条件・手順・例外の追記も分岐を足す修正に当たる。
- 確認のレビューの回は、直した部分に関わる指摘だけを上の基準で判断する。それ以外の箇所の指摘は、重要度「高」を除いて「見送り」にする（確認のレビューの目的は、直したことで生じた不具合を見つけること）。「修正ごとの判定」で「解決」以外とされたものも、コードで確かめる。

「見送り」は、不具合があると認めたうえで直さないもの。指摘が誤りの「不採用」とは分けて書く。

「テストの不足」に挙がったテストには重要度が付かない。採用した指摘の修正を確かめるテストだけを足し、ほかは「見送り」にして、表に重要度「—」で載せる。

判断の表（7. の「指摘への判断」と同じ形）、各レビューの実行状態（成功・失敗・省略）、件数の行を `<実行フォルダ>/decisions.md` に Write で保存する。どれも結果を返さなかった回も、実行状態を残す。あとでモデルごとの効果を確かめるのに使う。

### 6. 直す

- **この会話で Claude が実装した変更**なら、「採用」とした指摘は直してよい（実装の続きとして扱う）。直したら関係するテストを実行する。ただし、設計を大きく変える修正や、ユーザーの決定事項に反する修正は直さず「要確認」にする。
- 「見送り」とした指摘は直さず、報告に残す。ユーザーに直すよう言われたら直す。
- **それ以外の変更**（ユーザーや他の人のコード、既存の PR など）は直さず、修正案の提示にとどめる。
- 修正の担当は、Haiku に任せるかどうかも含めて haiku-implementation の基準で決める。
- 「要件にない変更」で、意図しない変更や残ったデバッグコードだったものは取り除く。意図した変更なら、報告でその理由を書く。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

Astra（または Sol）を動かしたら、スクリプトの出力の先頭（設定・範囲・所要時間・保存先・`codex resume` の行）をそのまま表示する。Fable（または Opus）を動かしたら、設定（`fable-reviewer` または `opus-reviewer` / effort）・範囲（`prepare.sh` の出力）・所要時間とトークン（完了の通知）・保存先を短く添える。続けて次を日本語で簡潔に書く。レビューの全文は貼らない（保存先にある）。

```markdown
## レビューの総評
（動かした担当ごとに 1 行で要約）

## 要件の充足
（どちらかが「満たす」以外とした要件と、その扱い。すべて満たしていれば「すべて満たす」の 1 行）

## 指摘への判断
| 重要度 | 指摘 | 場所 | 判断 | 理由・対応 |
| --- | --- | --- | --- | --- |
| 高 | [Astra・Fable] ... | `path:line` | 採用（修正済み） / 採用（修正案） / 見送り / 不採用 / 要確認 | ... |

両方 n 件、Astra だけ n 件、Fable だけ n 件（うち採用 n 件、見送り n 件、不採用 n 件）

## 修正内容
（6. で直したものと、実行したテストの結果。直していなければ修正案を箇条書きで）

## リリース前に確認すること
（「リリース前に確認すべきこと」のうち妥当なもの。なければ省く）

## ユーザーに確認したいこと
（「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 件数の行は Codex の担当（Astra または Sol）と Claude の担当（Fable または Opus）の両方が成功した回だけ書き、それ以外は「比較なし」と書く。
- 「見送り」があれば、表のあとに「直したいものがあれば指示してください」と 1 行添える。
- 直したあとは haiku-check でもう一度テストを実行する。
- 同じレビューについて Fable（または Opus）に追加で確かめたいことがあれば、SendMessage で聞いてよい。
- もう一度レビューするのは、上の「再レビュー」の条件に当たるときだけにし、下の「再レビューの手順」で行う。SendMessage で続けず、新しい実行フォルダと新しいエージェントで動かす。

## 再レビューの手順

### 確認のレビュー

1. 前回（1 回目）の実行フォルダを指定して、新しい実行フォルダを作る。要件は前回から写される。「再レビューは 1 回まで」と出たら上限なので、残る指摘をユーザーに伝える（示された作成済みのフォルダでまだレビューしていなければ、そのフォルダで続ける）。

   ```bash
   bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" --followup <前回の実行フォルダ> <slug>-r2
   ```

2. 出力された「修正の一覧」のパスに、Write ツールで次を書く。レビュアーは、これと前回からの差分で直しを確かめる。
   - **直したこと**: 前回の判断で採用して直した指摘ごとに、指摘の要約と、どう直したか（場所を添える）。「一部採用」は直した部分を書く。採用した指摘のほかに変えたもの（取り除いた要件にない変更、足したテスト、ユーザーに頼まれて直した見送り）も書く
   - **決定済み**: 「見送り」「不採用」「要確認」にした指摘と、一部採用で直さなかった部分を、1 行の理由とともに書く
   - 直した理由の弁解や、Claude が自信のない箇所は書かない（レビュアーの注意を偏らせない）
3. 手順の 4. と同じく `prepare.sh` を実行する。範囲の指定は渡さず、`--cd` を省けば前回のリポジトリを使う。前回のレビューのときの作業ツリーから今までの差分が、直したこととして渡る。「確認のレビューは使えない」と出たら（前回のスナップショットがない、rebase・マージを挟んだなど）、`--followup` を付けずに新しい実行フォルダを作り、手順の 2. から、確認のレビューの担当 1 体で全体の差分をレビューする（前回の指摘や対応は書かない）。
4. 「レビュアーの決め方」で決めた確認のレビューの担当 1 体を、手順の 4. と同じ呼び方で動かす。**終わるまでファイルを編集しない。**
5. 手順の 5. と同じく判断し、`decisions.md` の実行状態に「確認のレビュー（前回: <前回の実行フォルダ名>）」と書く。
6. 再レビューで採用した指摘（「未解決」とされた直しを含む）は、直し方が一通りに決まるものだけ直してテストし、報告に「確認のレビューのあとの修正（未レビュー）」として挙げる。仕組みを足さないと直せないものは直さず、ユーザーに伝える。
7. 手順の 7. の形で報告する。「要件の充足」は「修正ごとの判定」（「解決」以外のものと、その扱い）に替え、件数の行は「比較なし」と書く。担当が結果を返さなかったら、報告に「直した部分は未確認」と書いて直したことの一覧を添える（Haiku に書かせた直しなら、未レビューと明記し、完了を保留してユーザーに確認する）。

### ゼロからレビューし直すとき

作り方（選ぶ案）か要件の解釈を変えたときは、`--followup` を付けずに新しい実行フォルダを作り、1 回目と同じく手順の 2. から Astra と Fable でやり直す。要件は今の解釈で書き、前回の指摘や対応は書かない（先入観を渡さないため）。要件の解釈を変えたことは報告で伝える。この回で採用した指摘も、確認のレビューの 6. と同じ扱いにする。
