# Codex（GPT-6 Luna）に実装を任せる

引数: $ARGUMENTS

コードを書く作業を Codex CLI の GPT-6 Luna に任せ、Claude は「指示書を書く」「差分をレビューする」「仕上げる」だけを行う。Claude が自分でコードを読み書きする量を減らし、トークンを節約するのが目的。モデル・推論レベル（max）・Fast モードはスクリプトで固定している。

## いつ使うか

ユーザーに頼まれたときに加えて、頼まれていなくても、Claude がこれから実装に取りかかるときに次の基準で判断して使う。

**使う**（すべてに当たる）

- 要件と完了の条件がはっきりしていて、指示書に検証できる形で書ける（ユーザーとの会話や Issue・設計書で決まっている）
- まねできる既存の実装がある、または量は多いが判断は少ない作業（既存パターンに沿った機能追加・CRUD・画面・API、テストの追加、機械的な置き換え）
- オフラインで動くテスト・型チェック・リンターのどれかで確かめられる
- 規模が数ファイル〜十数ファイル、数十〜数百行程度（これより大きければ分割して何回かに分けて任せる）

**使わない**（Claude が自分で実装する）

- 数行で済む修正、原因と直し方が明らかなバグ修正（Claude が直接やる方が安い）
- 要件があいまい、設計から考える必要がある（先に設計を固める。規模が大きければ codex-design-review を使う）
- 原因のわからないバグの調査
- ネットワーク・外部サービス・認証情報がないと動かせない・確かめられない
- 認証・権限・課金・個人情報・秘密情報の扱いに関わる（細かいレビューが要り、節約にならない）
- ユーザーが「自分で書いて」「Codex は使わないで」と言っている、または急ぎで待てない
- 迷う程度なら使わず、Claude が自分で実装する

**自分の判断で使うときの違い**

- 始める前に「要件がはっきりした実装なので、Codex（GPT-6 Luna）に任せて Claude はレビューに回ります」と 1 行だけ伝え、確認は待たずに進める。
- `codex` が見つからない・ログインしていない・エラーで動かなかったときは、そのことを 1 行伝えて Claude が自分で実装する（途中までの変更が残っていれば、それを踏まえて続ける）。

頼まれて使うときに向いていないと判断したら、その理由を 1 行伝え、Claude が自分で実装するかユーザーに確認する。

## 手順

### 1. 引数を読む

- 実装してほしいことを読み取る。足りない前提（どの画面・どの API か、完了の条件など）があり、推測では決められなければユーザーに確認する。
- 対象が今のフォルダ以外のリポジトリなら、4. で `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

タスクを表す短い英数字の名前（例: `csv-export`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 指示書を書く

出力された「実装の指示」のパスに、Write ツールで Markdown を書く。Codex はこの会話を見られないので、指示書だけで実装できるように書く。ただしトークン節約が目的なので、Claude がコードを読み込むのは指示書に必要な範囲（関連ファイルの特定、既存パターンの確認）にとどめ、細部の調査は Codex に任せる。

- **目的**: 何のための変更か
- **要件・受け入れ条件**: 何ができれば完了か。箇条書きで検証できる形に
- **手がかり**: 関係しそうなファイル・関数、まねるべき既存の実装
- **決定事項**: ユーザーとの会話で決まったこと
- **やらないこと**: スコープ外にするもの
- **確認方法**: 実行してほしいテスト・型チェックのコマンド（わかれば）

秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. Codex に実装させる

Bash ツールを **`run_in_background: true`** で実行する（推論レベル max なので 10 分以上かかることがある）。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/impl.sh" [--cd <dir>] <実行フォルダ>
```

- Codex は作業フォルダの中だけ書き込めるサンドボックスで動き、ネットワークは使えない。個人設定（MCP サーバーやプラグイン）は読み込まない。
- **実行中は Claude もユーザーも作業フォルダのファイルを変更しない**（Codex の変更と混ざる）。待つ間はユーザーにそう伝える。
- 実行前から未コミットの変更があっても動く。差分には Codex が変えた分だけが入る。
- エラーなら内容を伝える。途中までの変更が残っていればそのことも伝え、続けるか戻すかをユーザーに確認する（勝手に戻さない）。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。

### 5. レビューする

Codex の報告はうのみにしない。

- 出力された差分（`diff-<回>.patch`）を Read で読み、受け入れ条件を満たしているか、既存コードとの整合、エラー処理、セキュリティ、余計な変更がないかを確かめる。必要な周辺コードだけ Read / Grep する。
- 指示書の「確認方法」のテスト・型チェックを Claude 自身が実行する（Codex のサンドボックスでは動かなかったものも含む）。

### 6. 仕上げる

- **小さな問題**（数行の修正、命名、漏れたエッジケース）は Claude が直接直す。
- **大きな問題**（要件の取り違え、複数ファイルにまたがる作り直し）は Codex に差し戻す。実行フォルダの `feedback.md` に、問題点・期待する動き・根拠（`path:line`）を Write で書き（上書きしてよい。過去の依頼は `prompt-<回>.md` に残る）、4. と同じく background で実行する。

  ```bash
  bash "${CLAUDE_SKILL_DIR}/scripts/impl.sh" [--cd <dir>] --resume <スレッド ID> <実行フォルダ>
  ```

  差し戻しは 2 回までにする。それでも直らなければ Claude が直すか、ユーザーに相談する。
- 直したらもう一度テストを実行する。
- 不要な変更が混ざっていたら、その部分だけ取り除く。ユーザーのもとからの未コミットの変更には触れない。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

スクリプトの出力の先頭（設定・変更・所要時間・トークン・差分の保存先・スレッド）をそのまま表示し（差し戻した場合は各回の分）、続けて次を日本語で簡潔に書く。Codex の報告の全文や差分は貼らない（保存先にある）。

```markdown
## 実装内容
（何をどう変えたか。ファイルごとに 1 行程度）

## Claude のレビュー
| 指摘 | 場所 | 対応 |
| --- | --- | --- |
| ... | `path:line` | Claude が修正 / Codex に差し戻して修正 / 未対応（理由） |

## 確認したこと
（実行したテスト・型チェックとその結果）

## ユーザーに確認したいこと
（Codex の「判断したこと」やレビューで出た、ユーザーにしか決められないもの。なければ省く）
```
