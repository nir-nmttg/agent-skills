# Codex（GPT-6 Luna）に実装を任せる

引数: $ARGUMENTS

コードを書く作業を Codex CLI の GPT-6 Luna に任せ、Claude は「分割する」「指示書を書く」「差分をレビューして反映する」「仕上げる」だけを行う。Claude が自分でコードを読み書きする量を減らし、トークンを節約するのが目的。モデル・推論レベル（max）・Fast モードはスクリプトで固定している。

Luna のトークンはほぼ無料なので、**1 本ずつ順番に任せるより、独立した小タスクに分けて並行で動かす**のを基本にする。各 Luna は専用の git worktree で動くので互いにぶつからず、その間 Claude は作業フォルダで Luna に向かない部分を進められる。

## いつ使うか

ユーザーに頼まれたときに加えて、頼まれていなくても、Claude がこれから実装に取りかかるときに次の基準で判断して使う。実装の全体が当てはまらなくても、当てはまる部分だけを任せ、残りは Claude が並行して書く。

**任せる部分**（すべてに当たる）

- 要件と完了の条件がはっきりしていて、指示書に検証できる形で書ける（ユーザーとの会話や Issue・設計書で決まっている）
- まねできる既存の実装がある、または量は多いが判断は少ない作業（既存パターンに沿った機能追加・CRUD・画面・API、テストの追加、機械的な置き換え）
- オフラインで動くテスト・型チェック・リンターのどれかで確かめられる
- 数十行以上の作業（大きければ分割する。上限はない）

**任せない部分**（Claude が自分で書く）

- 数行で済む修正、原因と直し方が明らかなバグ修正（指示書を書くより Claude が直接やる方が安い）
- 要件があいまい、設計から考える必要がある（先に設計を固める。規模が大きければ codex-design-review を使う）
- 原因のわからないバグの調査
- ネットワーク・外部サービス・認証情報がないと動かせない・確かめられない
- 認証・権限・課金・個人情報・秘密情報の扱いに関わる（細かいレビューが要り、節約にならない）
- ユーザーが「自分で書いて」「Codex は使わないで」と言っている、または急ぎで待てない
- 迷う程度なら任せず、Claude が自分で書く

**自分の判断で使うときの違い**

- 始める前に「〇〇 は Codex（GPT-6 Luna）N 本に並行で任せ、Claude は △△ を進めてからレビューします」と 1 行だけ伝え、確認は待たずに進める。
- `codex` が見つからない・ログインしていない・エラーで動かなかったときは、そのことを 1 行伝えて Claude が自分で実装する（途中までの変更が残っていれば、それを踏まえて続ける）。

頼まれて使うときに向いていないと判断したら、その理由を 1 行伝え、Claude が自分で実装するかユーザーに確認する。

## 手順

### 1. 引数を読む

- 実装してほしいことを読み取る。足りない前提（どの画面・どの API か、完了の条件など）があり、推測では決められなければユーザーに確認する。
- 対象が今のフォルダ以外のリポジトリなら、4. と 6. で `--cd <そのリポジトリのパス>` をつける。

### 2. 分ける

実装を、Luna に任せる小タスクと Claude が書く部分に分ける。

- **小タスクどうしは独立させる**: できるだけ別々のファイルを触り、ほかの小タスクの成果物を前提にしない。分け方の例: 画面ごと・API エンドポイントごと・モジュールごと、既存実装に対するテストの追加、ディレクトリごとの機械的な置き換え。
- **共通の土台が要るなら先に作る**: 複数の小タスクが使う型・スキーマ・インターフェース・共通関数は、先に Claude が書く（または Luna 1 本に任せて反映する）。土台ができてから小タスクを並行で動かす。
- **同時に動かすのは 4 本まで**を目安にする。それより多ければ、終わった分から順に次を動かす。
- 分けるほどでもない大きさなら 1 本でよい。

### 3. 実行フォルダを作り、指示書を書く

小タスクごとに、内容を表す短い英数字の名前（例: `csv-export`）を決めて実行フォルダを作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

出力された「実装の指示」のパスに、Write ツールで Markdown を書く。Codex はこの会話もほかの小タスクも見られないので、指示書だけで実装できるように書く。ただしトークン節約が目的なので、Claude がコードを読み込むのは指示書に必要な範囲（関連ファイルの特定、既存パターンの確認）にとどめ、細部の調査は Codex に任せる。

- **目的**: 何のための変更か
- **要件・受け入れ条件**: 何ができれば完了か。箇条書きで検証できる形に
- **手がかり**: 関係しそうなファイル・関数、まねるべき既存の実装
- **決定事項**: ユーザーとの会話で決まったこと
- **やらないこと**: スコープ外にするもの。並行で動かすときは、ほかの小タスクや Claude が担当するファイルを「触らないファイル」として書く
- **確認方法**: 実行してほしいテスト・型チェックのコマンド（わかれば）

秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. Codex に実装させる

小タスクごとに Bash ツールを **`run_in_background: true`** で実行する。並行で動かすときは、1 つのメッセージで複数の Bash 呼び出しを同時に出す。推論レベル max なので 10 分以上かかることがある。終わると 1 本ずつ通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/impl.sh" [--cd <dir>] --worktree <実行フォルダ>
```

- `--worktree` をつけると、作業フォルダの今の状態（未コミットの変更を含む）から専用の worktree（`<実行フォルダ>/worktree`）を切り、そこで実装させる。作業フォルダには触れないので、**実行中も Claude は作業フォルダで自分の担当部分を進めてよい**。依存パッケージのフォルダ（`node_modules`、`.venv` など）は作業フォルダのものをリンクするので、Codex もテストを動かせる（キャッシュの書き込みが要るツールは失敗することがある）。
- 1 本だけで、その間 Claude も何もしないなら `--worktree` なしでもよい。その場合 Codex は作業フォルダで直接実装し、反映（6.）は要らない。**実行中は Claude もユーザーも作業フォルダのファイルを変更しない**。
- Codex は書き込める場所が作業場所の中だけのサンドボックスで動き、ネットワークは使えない。個人設定（MCP サーバーやプラグイン）は読み込まない。
- 待つ間は、Claude の担当部分を書く、次の小タスクの指示書を書く、などを進める。
- エラーなら内容を伝える。途中までの変更が残っていればそのことも伝え、続けるか捨てるかをユーザーに確認する（勝手に捨てない）。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。

### 5. レビューする

終わった小タスクから順にレビューする。Codex の報告はうのみにしない。

- 出力された差分（`diff-<回>.patch`）を Read で読み、受け入れ条件を満たしているか、既存コードとの整合、エラー処理、セキュリティ、指示書の範囲外の変更がないかを確かめる。必要な周辺コードだけ Read / Grep する。
- **大きな問題**（要件の取り違え、複数ファイルにまたがる作り直し）は、反映する前に Codex に差し戻す。実行フォルダの `feedback.md` に、問題点・期待する動き・根拠（`path:line`）を Write で書き（上書きしてよい。過去の依頼は `prompt-<回>.md` に残る）、4. と同じく background で実行する。worktree で実装させた場合は、同じ worktree が自動で使われる。

  ```bash
  bash "${CLAUDE_SKILL_DIR}/scripts/impl.sh" --resume <スレッド ID> <実行フォルダ>
  ```

  差し戻しは 2 回までにする。それでも直らなければ、反映してから Claude が直すか、ユーザーに相談する。
- 使えない結果なら、反映せずに捨てて（`apply.sh --discard`）、Claude が書くか指示書を直して出し直す。

### 6. 作業フォルダに反映する

`--worktree` で実装させたものは、レビューで問題がなければ作業フォルダに反映する。終わった順に 1 本ずつでも、まとめてでもよい。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/apply.sh" <実行フォルダ>...
```

- worktree を切った時点をベースにした 3-way マージなので、その後に Claude やほかの小タスクが作業フォルダで変えた分とも混ざる。ステージ（インデックス）やブランチには触れない。反映した worktree は片づけられる。
- 競合があると、競合マーカーを残すか `<ファイル>.codex` に Codex 版を置き、終了コード 2 で終わる（worktree は残る）。Claude がマーカーを解消し、`.codex` ファイルを取り込んで消してから、`apply.sh --discard <実行フォルダ>` で worktree を片づける。
- 反映せずに捨てるときは `apply.sh --discard <実行フォルダ>`。

### 7. 仕上げる

- すべて反映したら、作業フォルダで指示書の「確認方法」のテスト・型チェックを Claude 自身が実行する（Codex のサンドボックスで動かなかったものも含む）。小タスクを組み合わせた結果として正しく動くかもここで確かめる。
- **小さな問題**（数行の修正、命名、漏れたエッジケース、小タスクどうしのつなぎ目）は Claude が直接直し、もう一度テストを実行する。
- 不要な変更が混ざっていたら、その部分だけ取り除く。ユーザーのもとからの未コミットの変更には触れない。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 8. 報告する

小タスクごとに、スクリプトの出力の先頭（設定・変更・所要時間・トークン・差分の保存先）を短くまとめて表示し、続けて次を日本語で簡潔に書く。Codex の報告の全文や差分は貼らない（保存先にある）。

```markdown
## 分担
| 担当 | 内容 | 結果 |
| --- | --- | --- |
| Luna: csv-export | ... | 反映済み（差し戻し 1 回） / 破棄して Claude が実装 |
| Claude | ... | 実装済み |

## Claude のレビュー
| 指摘 | 場所 | 対応 |
| --- | --- | --- |
| ... | `path:line` | Claude が修正 / Codex に差し戻して修正 / 未対応（理由） |

## 確認したこと
（実行したテスト・型チェックとその結果）

## ユーザーに確認したいこと
（Codex の「判断したこと」やレビューで出た、ユーザーにしか決められないもの。なければ省く）
```
