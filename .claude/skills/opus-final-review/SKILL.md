# Opus による仕上げのレビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

実装を終えた変更を、この会話を共有しない Opus 5.5 のサブエージェント（`opus-final-reviewer`）に最終レビューさせ、その指摘を Claude が吟味する。codex-impl-review との違いは、**実装の説明を渡さず、要件と差分だけを渡す**こと。実装した Claude の「こう書いたつもり」が伝わらないので、差分が実際に何をしていて、要件を本当に満たしているかを先入観なしに確かめられる。差分の取り出しとプロンプトの組み立てはスクリプトに任せ、Claude は「要件をまとめる」「Agent ツールで呼ぶ」「指摘を判断する」「採用した指摘を直す」だけを行う。結果は `artifacts/opus-final-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。見つけるのは**要件とのずれ**（実装者の思い込み、要件の取り違え・漏れ、指示書を介した伝言の誤り）で、codex-impl-review（コードの欠陥）とは役割が違う。Claude が実装を終えて完了を報告する前、またはコミット・PR を頼まれてまだ最終レビューしていない変更があるときに、次の基準で判断する。**迷ったら使う。**

**使う**: 要件とのずれが起こりうる変更は、規模にかかわらずすべて。codex-impl-review を使う変更には、同時に並べて使う。動作を決めない文書だけの変更は Sol を使わないが、内容のずれは起こりうるので、これだけを使う。

**使わない**（次の場合だけ）

- 意味を変えない修正: typo・整形・コメントだけの変更、自動生成ファイルの再生成だけの変更
- 依存パッケージのバージョンだけを変える変更
- ユーザーが「レビューは不要」と言っている
- 同じ変更の状態を、この会話ですでに Opus でレビュー済み（再レビューの要否は、直した分の差分だけで判断する。どのレビューの指摘を直したかは問わず、重要度「高」の指摘を直したとき、直す中で要件の解釈を変えたとき、指摘の範囲を超えて変更したとき、新たにリスク領域に触れたときにもう一度使う。レビューには直した分だけでなく全体の差分を渡す。同じ変更への再レビューは 2 回までにし、残る指摘はユーザーに伝える）
- 対象が git リポジトリでない

見送るときは、当てはまる項目を完了報告に 1 行書く。書けないときは実行する。

**ほかのレビューとの順番**

- codex-impl-review と**同時に**動かす（codex-risk-impl-review を選ばれたら、それも同時に）。同じ変更の状態をまだ Sol でレビューしていないなら、`/opus-final-review` で直接頼まれたときも同じで、ユーザーが「Opus だけ」と言ったときだけ省く。Sol の条件に当たらない変更や、Sol でレビュー済みの状態なら、これだけを使う。
- Sol 用の実装の説明は別に書き、Opus の要件には実装の説明も Sol の結果も書かない。prompt.md を作ってから、Agent ツールと review.sh を同じメッセージで動かす。範囲の指定（`--base` / `--commit` / `--uncommitted` / `--cd`）は `prepare.sh` と review.sh に同じものを渡し、`--focus` は review.sh だけに渡す。
- **すべて終わるまでファイルを編集しない**（どのレビュアーも作業ツリーを読むため）。結果の受け取りは終了の通知で行い、片方が失敗しても、全部の結果が出揃ってから、成功した分で判断して失敗を報告で伝える。
- テストは先に済ませておく（haiku-check）。Opus はテストを実行しない。指摘を直したあとも、もう一度テストを実行する。

**自分の判断で使うときの進め方**

- 始める前に「完了を報告する前に、会話を共有しない Opus に要件と差分だけでレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。Sol と同時に動かすときは、この案内も 1 行にまとめる。
- Opus が動いている間に、完了報告の下書きなど、レビュー結果に左右されない作業を進めてよい（ファイルは編集しない）。
- Opus が動かなかったら（`opus-final-reviewer` が見つからない、エラーや停止で結果が返らない）、そのことを 1 行伝えて、Opus のレビューなしで完了を報告する。

## 手順

### 1. 引数を読む

- 範囲の指定があればそのまま 4. の `prepare.sh` に渡す。「未コミットだけ」→ `--uncommitted`、「このコミット」→ `--commit <sha>`、「develop との差分」→ `--base develop`。指定がなければ渡さない（既定ブランチから分岐して以降の変更を、未コミットも含めてすべてレビューする）。
- 対象が今のフォルダ以外のリポジトリなら、4. の `prepare.sh` に `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

変更の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 要件を書く

出力された「要件」のパスに、Write ツールで Markdown を書く。**ここがこのスキルの要なので、実装についてはいっさい書かない。** 依頼した人の立場で「何を求めたか」だけを書く。

**書くもの**

- **依頼**: ユーザーの元の依頼。できるだけユーザーの言葉のまま引用する
- **要件・受け入れ条件**: 満たすべきこと。Issue・設計書・仕様があればその要点（URL やファイルのパスがあれば添える）。番号を振る（R1, R2, …）
- **ユーザーが決めた仕様・制約**: 会話の中でユーザーが決めた「何をするか」「何をしないか」。ユーザー自身が実装の方法を指定したなら、それも制約として書く
- **スコープ外**: ユーザーが明示的に外したもの

**書かないもの**

- どこをどう変えたか、なぜその書き方にしたか、どの案から選んだか
- 実行したテストとその結果、Claude が自信のない箇所
- ほかのレビュー（codex-impl-review など）の指摘とその対応

要件があいまいなまま実装したなら、あいまいなまま書く（Claude の解釈で補わない。Opus が「確認したい点」として挙げれば、それ自体が成果になる）。秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. Opus にレビューさせる

まず差分を取り出し、Opus に読ませるプロンプトを作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/prepare.sh" [--cd <dir>] [--base <ref> | --commit <sha> | --uncommitted] <実行フォルダ>
```

- 「レビューする変更がありません」と出たら、範囲を確かめてユーザーに伝える（例: すでに既定ブランチにコミット・プッシュ済みなら `--commit` で指定してもらう）。その他のエラーなら内容を伝えて終わる。
- `--commit` では当時のソースを `<実行フォルダ>/tree` に展開して読ませる（Opus は git を使えないため）。
- 作業場所のルートの CLAUDE.md・`.claude/CLAUDE.md`・AGENTS.md は prompt.md に入るので、プロジェクトの規約は伝わる。

続けて Agent ツールで呼ぶ。

- `subagent_type`: `opus-final-reviewer`（必ず指定する。`fork` や省略で会話を引き継ぐ形にしない）
- `effort`: 上の「Claude の推論レベル」。空や `auto` のときは `high`
- `model`: **渡さない**（引数は別名しか受け付けず、親と同じ系統なら親のモデルになって、定義の `claude-opus-5-5` の固定が外れる）
- `prompt`: 次の 1 行だけにする。**実装の説明・経緯・ほかのレビューの結果を足さない**（このスキルの要）

  ```text
  <実行フォルダ>/prompt.md を読み、システムプロンプトの手順と出力形式で最終レビューしてください。
  ```

- Opus は Read / Grep / Glob しか使えず、この会話・auto memory・ユーザー用の CLAUDE.md・MCP は読み込まない。推論レベルが高いと 10 分以上かかる。バックグラウンドで動き、終わると通知が来るので、それまで待つ（その間、レビュー結果に左右されない作業は進めてよい）。
- 返ってきた本文を、そのまま `<実行フォルダ>/review.md` に Write で保存する。
- `opus-final-reviewer` が見つからないときは、エージェントがリンクされていない（このスキル集の `scripts/link-skills.sh --claude` で `~/.claude/agents` にリンクする）か、リンクする前に始めたセッション。そのことを伝えて終わる（Sol や Astra を並べているときは、全部の結果が出揃ってから、その結果で進める）。

### 5. 指摘を判断する

まず「この変更がしていること」を、Claude が意図した実装と照らし合わせる。食い違いがあれば、Opus の読み違いか、実装が意図どおりになっていないかのどちらかなので、コードで確かめる。

次に「要件ごとの判定」で「一部だけ」「満たさない」「判断できない」となったもの、「指摘」「要件にない変更」を一つずつ判断する。うのみにせず、該当のファイルを Read / Grep で確かめ、「再現」に書かれた条件で本当に問題が起きるかを根拠をもって判断する。Opus の指摘が誤っていれば「不採用」とし、理由を書く。Opus は実装の経緯を知らないので、ユーザーとの会話で決めたことに反する指摘は「不採用（決定事項）」としてよい。ただし、その決定事項を 3. の要件に書き漏らしていたなら、それも報告で触れる。

### 6. 直す

- **この会話で Claude が実装した変更**なら、「採用」とした指摘は直してよい（実装の続きとして扱う）。直したら関係するテストを実行する。ただし、設計を大きく変える修正や、ユーザーの決定事項に反する修正は直さず「要確認」にする。
- **それ以外の変更**（ユーザーや他の人のコード、既存の PR など）は直さず、修正案の提示にとどめる。
- 「要件にない変更」で、意図しない変更や残ったデバッグコードだったものは取り除く。意図した変更なら、報告でその理由を書く。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

設定（`opus-final-reviewer` / effort）・範囲（`prepare.sh` の出力）・所要時間とトークン（完了の通知）・保存先（`review.md`）を短く表示し、続けて次を日本語で簡潔に書く。Opus のレビュー全文は貼らない（保存先にある）。

```markdown
## Opus の総評
（1〜2 行で要約）

## 要件の充足
（「満たす」以外の判定があった要件と、その扱い。すべて満たしていれば「すべて満たす」の 1 行）

## 指摘への判断
| 重要度 | 指摘 | 場所 | 判断 | 理由・対応 |
| --- | --- | --- | --- | --- |
| 高 | ... | `path:line` | 採用（修正済み） / 採用（修正案） / 不採用 / 要確認 | ... |

## 修正内容
（6. で直したものと、実行したテストの結果。直していなければ修正案を箇条書きで）

## ユーザーに確認したいこと
（Opus の「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- Sol と同時に動かしたときは、指摘を codex-impl-review の表に `[Opus]` を付けてまとめ、重複は 1 つにする。報告もそちらの形式にそろえ、「要件の充足」の節だけを加える。
- 同じレビューについて Opus に追加で確かめたいことがあれば、SendMessage で聞いてよい。
- 修正後にもう一度レビューする場合は、SendMessage で続けず、新しい実行フォルダと新しいエージェントで 2. からやり直す。要件は前回と同じものを使い、前回の指摘や対応は書かない（先入観を渡さないため）。
