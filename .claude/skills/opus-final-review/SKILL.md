# Opus による仕上げのレビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

実装を終えた変更を、この会話を共有しない別の Claude（Opus 5.5）に最終レビューさせ、その指摘を Claude が吟味する。codex-impl-review との違いは、**実装の説明を渡さず、要件と差分だけを渡す**こと。実装した Claude の「こう書いたつもり」が伝わらないので、差分が実際に何をしていて、要件を本当に満たしているかを先入観なしに確かめられる。差分の取り出し・Opus の呼び出し・保存はスクリプトに任せ、Claude は「要件をまとめる」「指摘を判断する」「採用した指摘を直す」だけを行う。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Opus の使用量は多いが、実装やテストやほかのレビューを Codex に任せて節約しているぶん、仕上げの確認にはこれを使ってよい。Claude が実装を終えて完了を報告する前、またはコミット・PR を頼まれてまだ最終レビューしていない変更があるときに、次の基準で判断する。**迷ったら使う。**

**使う**（次のどれかに当たる）

- 新機能の追加、既存の振る舞いを変える修正、リファクタリングで、ロジックの変更が 2 ファイル以上か、数十行（目安 30 行）以上ある
- 規模にかかわらず、次に触れる変更
  - DB スキーマ、公開 API・インターフェース、設定ファイルの形式、データ移行
  - 認証・権限・課金・個人情報・秘密情報
  - 並行処理、キャッシュ、再試行、データの整合性
  - 外部からの入力の解析・検証、データの削除・変換
- 原因の調査が必要だったバグ修正（要件どおりに直っているかを、経緯を知らない目で確かめる）
- codex-impl で Luna に書かせた変更をまとめ終えたとき

**使わない**

- 数行の変更、typo レベルの修正、文言・設定値・コメント・ドキュメントだけの変更、自動生成ファイルや依存のバージョン更新だけの変更
- ユーザーが「レビューは不要」「急ぎ」と言っている
- 同じ変更をこの会話ですでに最終レビュー済みで、その後の修正が小さい（指摘への対応で大きく書き換えたら、もう一度レビューする）
- 対象が git リポジトリでない

**ほかのレビューとの順番**

- これは**最後の確認**に使う。codex-impl-review や codex-risk-impl-review を使うときは、そちらの指摘を直し終えてから、直したあとの差分に対してこれを使う。ほかのレビューを使わない変更なら、これだけを使う。
- テストは先に済ませておく（codex-test など）。Opus はテストを実行しない。

**自分の判断で使うときの進め方**

- 始める前に「完了を報告する前に、会話を共有しない Opus に要件と差分だけで最終レビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。
- Opus が動いている間に、完了報告の下書きなど、レビュー結果に左右されない作業を進めてよい。
- Opus がエラーで動かなかったら、そのことを 1 行伝えて、最終レビューなしで完了を報告する。

## 手順

### 1. 引数を読む

- 範囲の指定があればそのまま 4. に渡す。「未コミットだけ」→ `--uncommitted`、「このコミット」→ `--commit <sha>`、「develop との差分」→ `--base develop`。指定がなければ渡さない（既定ブランチから分岐して以降の変更を、未コミットも含めてすべてレビューする）。
- 対象が今のフォルダ以外のリポジトリなら、4. で `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

変更の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 要件を書く

出力された「要件」のパスに、Write ツールで Markdown を書く。**ここがこのスキルの要なので、実装についてはいっさい書かない。** 依頼した人の立場で「何を求めたか」だけを書く。

**書くもの**

- **依頼**: ユーザーの元の依頼。できるだけユーザーの言葉のまま引用する
- **要件・受け入れ条件**: 満たすべきこと。Issue・設計書・仕様があればその要点（URL やファイルのパスがあれば添える）。番号を振る（R1, R2, …）
- **ユーザーが決めた仕様・制約**: 会話の中でユーザーが決めた「何をするか」「何をしないか」。ユーザー自身が実装の方法を指定したなら、それも制約として書く
- **スコープ外**: ユーザーが明示的に外したもの

**書かないもの**

- どこをどう変えたか、なぜその書き方にしたか、どの案から選んだか
- 実行したテストとその結果、Claude が自信のない箇所
- ほかのレビュー（codex-impl-review など）の指摘とその対応

要件があいまいなまま実装したなら、あいまいなまま書く（Claude の解釈で補わない。Opus が「確認したい点」として挙げれば、それ自体が成果になる）。秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. Opus にレビューさせる

Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと 10 分以上かかる）。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} [--cd <dir>] [--base <ref> | --commit <sha> | --uncommitted] <実行フォルダ>
```

- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- Opus は `claude -p` で別のセッションとして動き、この会話・ユーザーとプロジェクトの設定ファイル・MCP サーバー・スキルは読み込まない。使えるのはファイルの読み取りと読み取り専用の git コマンドだけで、コードを書き換えることはない。対象リポジトリの CLAUDE.md は読むので、プロジェクトの規約は伝わる。
- 「レビューする変更がありません」と出たら、範囲を確かめてユーザーに伝える（例: すでに既定ブランチにコミット・プッシュ済みなら `--commit` で指定してもらう）。
- その他のエラーなら内容を伝えて終わる。`claude` にログインしていないときは、ターミナルで `claude` を起動してログインするよう案内する。

### 5. 指摘を判断する

まず「この変更がしていること」を、Claude が意図した実装と照らし合わせる。食い違いがあれば、Opus の読み違いか、実装が意図どおりになっていないかのどちらかなので、コードで確かめる。

次に「要件ごとの判定」で「一部だけ」「満たさない」「判断できない」となったもの、「指摘」「要件にない変更」を一つずつ判断する。うのみにせず、該当のファイルを Read / Grep で確かめ、「再現」に書かれた条件で本当に問題が起きるかを根拠をもって判断する。Opus の指摘が誤っていれば「不採用」とし、理由を書く。Opus は実装の経緯を知らないので、ユーザーとの会話で決めたことに反する指摘は「不採用（決定事項）」としてよい。ただし、その決定事項を 3. の要件に書き漏らしていたなら、それも報告で触れる。

### 6. 直す

- **この会話で Claude が実装した変更**なら、「採用」とした指摘は直してよい（実装の続きとして扱う）。直したら関係するテストを実行する。ただし、設計を大きく変える修正や、ユーザーの決定事項に反する修正は直さず「要確認」にする。
- **それ以外の変更**（ユーザーや他の人のコード、既存の PR など）は直さず、修正案の提示にとどめる。
- 「要件にない変更」で、意図しない変更や残ったデバッグコードだったものは取り除く。意図した変更なら、報告でその理由を書く。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

スクリプトの出力の先頭（設定・範囲・所要時間・保存先・`claude --resume` の行）をそのまま表示し、続けて次を日本語で簡潔に書く。Opus のレビュー全文は貼らない（保存先にある）。

```markdown
## Opus の総評
（1〜2 行で要約）

## 要件の充足
（「満たす」以外の判定があった要件と、その扱い。すべて満たしていれば「すべて満たす」の 1 行）

## 指摘への判断
| 重要度 | 指摘 | 場所 | 判断 | 理由・対応 |
| --- | --- | --- | --- | --- |
| 高 | ... | `path:line` | 採用（修正済み） / 採用（修正案） / 不採用 / 要確認 | ... |

## 修正内容
（6. で直したものと、実行したテストの結果。直していなければ修正案を箇条書きで）

## ユーザーに確認したいこと
（Opus の「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 修正後にもう一度レビューする場合は、新しい実行フォルダを作り、2. からやり直す。要件は前回と同じものを使い、前回の指摘や対応は書かない（先入観を渡さないため）。
