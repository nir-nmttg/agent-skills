# Opus による設計レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が考えた設計を、この会話を共有しない Opus 5.5 のサブエージェント（`opus-reviewer`）にレビューさせ、その指摘を Claude が吟味する。渡すのは要件と設計だけで、指示書は Sol（codex-design-review）と同じ。結果は `artifacts/opus-design-review/` に保存される。

## 使うとき

ユーザーに Opus での設計レビューを頼まれたときと、同じ設計を Sol でレビュー済みで Opus だけを足すときに使う。Sol と並べるなら codex-design-review を起動して、その手順で進める。

## 手順

### 1. 引数を読む

- ファイルパスがあれば、それをレビュー対象の設計書とする。
- パスがなければ、この会話で Claude が考えた直近の設計案を対象にする。設計案が会話にないときは、何をレビューするかを尋ねて終わる。
- `--cd <dir>` があれば、3. の `prepare.sh` に渡す。設計が今のフォルダ以外のリポジトリについてのものなら、`--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

設計の内容を表す短い英数字の名前を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 要件と設計書を書く

出力された「要件」と「設計書」のパスに、Write ツールで Markdown を書く。書くものは codex-design-review の 3. と同じ。

- 要件: 依頼と背景、R 番号付きの要件（機能要件、非機能要件、変えてはいけないもの）、ユーザーが決めた仕様・制約、スコープ外
- 設計書: 設計、検討した代替案と選ばなかった理由、関連する既存コード、外部の挙動の前提
- Claude が自信のない判断や、書いた人の不安は書かない。ファイルで渡された設計書も、同じように分けて写す

秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. Opus にレビューさせる

まず依頼（`prompt.md`）を作る。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/prepare.sh" [--cd <dir>] <実行フォルダ>
```

続けて Agent ツールで呼ぶ。終わるまで、要件・設計書と読み先のコードを編集しない。

- `subagent_type`: `opus-reviewer`（必ず指定する。`fork` や省略で会話を引き継ぐ形にしない）
- `effort`: 上の「Claude の推論レベル」。空や `auto` のときは `high`
- `model`: **渡さない**（引数は別名しか受け付けず、親と同じ系統なら親のモデルになって、定義の `claude-opus-5-5` の固定が外れる）
- `prompt`: 次の 1 行だけにする

  ```text
  <実行フォルダ>/prompt.md を読み、その指示に従ってレビューしてください。
  ```

- 終わると通知が来るので、それまで待つ。返ってきた本文を、そのまま `<実行フォルダ>/review.md` に Write で保存する。
- `prepare.sh` が失敗したら、原因（要件や設計書の書き忘れなど）を直して実行し直す。
- `opus-reviewer` が見つからないときは、エージェントがリンクされていない（このスキル集の `scripts/link-skills.sh --claude` で `~/.claude/agents` にリンクする）か、リンクする前に始めたセッション。
- `prepare.sh` を直せないとき、Opus が見つからない・結果が返らないときは、そのことを伝えてレビューなしで設計を提示し、実行状態を `decisions.md` に残す。

### 5. 指摘を判断して報告する

「要件ごとの判定」で「一部だけ」「満たさない」「判断できない」となったものと「指摘」を一つずつ判断する。うのみにせず、必要なら指摘されたファイルを Read / Grep で確かめ、根拠をもって判断する。誤りなら「不採用」とし、理由を書く。判断の表と実行状態を `<実行フォルダ>/decisions.md` に Write で保存する。

設定（`opus-reviewer` / effort）・所要時間とトークン（完了の通知）・保存先を短く表示し、続けて次を日本語で簡潔に書く。レビュー全文は貼らない。

```markdown
## Opus の総評
（1〜2 行で要約）

## 要件の充足
（「満たす」以外の判定があった要件と、その扱い。すべて満たしていれば「すべて満たす」の 1 行）

## 指摘への判断
| 重要度 | 指摘 | 判断 | 理由 |
| --- | --- | --- | --- |
| 高 | ... | 採用 / 一部採用 / 不採用 / 要確認 | ... |

## 設計の修正案
（採用した指摘をもとに、設計のどこをどう変えるか。箇条書きで）

## ユーザーに確認したいこと
（「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

修正案は提案にとどめ、設計書やコードはユーザーの了承なしに書き換えない。もう一度レビューする場合は、新しい実行フォルダに同じ要件と修正した設計書の全体を書く。前回の指摘や対応は書かない（先入観を渡さないため）。
