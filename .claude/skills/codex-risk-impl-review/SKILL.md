# Codex Astra による実装のリスクレビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

壊れると影響の大きい変更を、最も強いモデル（Codex CLI の GPT-6 Astra）に「どう壊れるか」の観点で独立してレビューさせ、その指摘を Claude が吟味する。差分の取り出し・Codex の呼び出し・保存はスクリプトに任せ（codex-impl-review のスクリプトを、モデルとレビューの指示書だけ差し替えて使う）、Claude は「実装の説明をまとめる」「指摘を判断する」「採用した指摘を直す」だけを行う。結果は `artifacts/codex-risk-impl-review/` に保存される。

## 使うかどうかをユーザーに聞くとき

Astra は重いので、**ユーザーに頼まれていなければ、自分の判断では実行しない。** 代わりに、次の条件に当たるときに使うかどうかを聞く。**当たるか迷ったら聞く。** Astra は異常系・壊れ方を重点的に見る。正常系の正しさや要件との一致は Sol（codex-impl-review）が見るので、Astra は Sol と並べて使う。

**聞く**（Claude が実装を終えて完了を報告する前、またはまだレビューしていない変更のコミット・PR を頼まれたときに、変更が次のどれかに触れる）

- DB スキーマの変更、データ移行、本番データの削除・一括変換
- 認証・認可・権限、セッション・トークンの扱い
- 課金・決済・ポイントなどお金に関わる処理
- 個人情報・秘密情報の保存・送信・ログ出力、暗号
- 並行処理、ロック、トランザクション、分散環境での整合性・冪等性
- メール・Webhook・外部 API など、取り消せない外部への送信
- 公開 API・保存形式・設定の破壊的変更、デプロイ・インフラの設定
- その他、壊れると影響が大きく、後から戻しにくいとはっきり言えるもの

**聞かない**

- 上に当てはまらない通常の変更（それは codex-impl-review の範囲）
- ユーザーが「レビューは不要」「急ぎ」と言っている、またはこの会話で同じ変更について一度断られた
- 同じ変更をこの会話ですでに Astra でレビュー済み（もう一度聞くのは、重要度「高」の指摘を直したとき、または直す中で新たにリスク領域に触れたときだけ。同じ変更への再レビューは 2 回まで）
- 対象が git リポジトリでない

**聞き方**

- AskUserQuestion で 1 問だけ聞く。質問には、どのリスクに当たるか（例: 「マイグレーションで既存データを変換している」）を 1 行で添える。選択肢は「Sol に Astra を加えてレビューする（推奨）」「Sol だけでレビューする」「レビューしない」。
- Astra を加えると選ばれたら、このスキルの手順を進める（4. で codex-impl-review も並べて実行する）。
- それ以外を選ばれたら、このスキルは使わず、その答えに従う（「Sol だけ」なら codex-impl-review を使う）。

## 手順

### 1. 引数を読む

- 範囲の指定があればそのまま 4. に渡す。「未コミットだけ」→ `--uncommitted`、「このコミット」→ `--commit <sha>`、「develop との差分」→ `--base develop`。指定がなければ渡さない（既定ブランチから分岐して以降の変更を、未コミットも含めてすべてレビューする）。
- 対象が今のフォルダ以外のリポジトリなら、4. で `--cd <そのリポジトリのパス>` をつける。

### 2. 実行フォルダを作る

変更の内容を表す短い英数字の名前（例: `billing-retry`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 実装の説明を書く

出力された「実装の説明」のパスに、Write ツールで Markdown を書く。差分そのものはスクリプトが渡すので書き写さない。Codex はこの会話を見られないので、差分だけではわからないことを書く。

- **目的と要件**: 何のための変更か。満たすべき要件・制約（Issue や設計書があればその要点）
- **リスクのある箇所**: どこが、なぜ危ないと考えたか（データ移行、認可、課金など）
- **実装の概要**: どこをどう変えたか、主な判断
- **本番の前提**: わかる範囲で、データの量、同時実行の度合い、デプロイの手順（新旧のコードが混在するか）、ロールバックの方法
- **決定事項**: ユーザーとの会話で決まったこと（Codex が蒸し返さないように）
- **やっていないこと**: 意図的にスコープ外にしたもの
- **確認済みのこと**: 実行したテスト・ビルド・手動確認とその結果
- **気になっている点**: Claude 自身が自信のない箇所

秘密情報（トークン、パスワード、個人情報）は書かない。この会話で実装したのではない変更（ユーザーや他の人の変更）なら、わかる範囲で書けばよい。

### 4. Codex にレビューさせる

Bash ツールを **`run_in_background: true`** で実行する（Astra は推論レベルが高いと数十分かかることがある）。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} [--cd <dir>] [--base <ref> | --commit <sha> | --uncommitted] <実行フォルダ>
```

- codex-impl-review（Sol）も、同じ範囲・同じ変更の状態で並べて実行する。聞いて選ばれたときも、`/codex-risk-impl-review` で直接頼まれたときも同じで、ユーザーが「Astra だけ」と言ったときだけ省く。実装の説明は両方のスキルの 3. の項目をすべて含めて書き、同じ内容を両方の実行フォルダに置き、2 つの review.sh を同じ範囲の指定で同時に background で動かす。**両方が終わるまでファイルを編集しない。** 終わったら、指摘をまとめて判断する（重複は 1 つにし、食い違いはコードで確かめる）。
- `--effort` には上の「Claude の推論レベル」をそのまま渡す（Claude が high なら Codex も high）。空や `auto` のときは省略してよい（スクリプトが high にする）。
- Codex は読み取り専用のサンドボックスと 1M コンテキストで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。コードを書き換えることはない。
- 待っている間に、テストの実行など、レビュー結果に左右されない作業を進めてよい。
- 「レビューする変更がありません」と出たら、範囲を確かめてユーザーに伝える（例: すでに既定ブランチにコミット・プッシュ済みなら `--commit` で指定してもらう）。
- その他のエラーなら内容を伝えて終わる。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。Astra だけが失敗した（プランの対象外など）ときは、そのことを伝え、並べて実行した codex-impl-review（Sol）の結果で判断を進める（Sol を並べていなかったときは、Sol で実行するかを聞く）。

### 5. 指摘を判断する

指摘はうのみにしない。指摘ごとに、該当のファイルを Read / Grep で確かめ、「再現」に書かれた条件で本当に問題が起きるかを根拠をもって判断する。Codex の指摘が誤っていれば「不採用」とし、理由を書く。本番の状態に左右されて判断できないものは「要確認」にする。

codex-impl-review と並べたときは、両方の指摘をまとめてから判断する（7. の表では「指摘」の列の頭に `[Astra]`・`[Sol]` を書く。報告はこのスキルの形式にそろえる）。

### 6. 直す

- **この会話で Claude が実装した変更**なら、「採用」とした指摘は直してよい（実装の続きとして扱う）。直したら関係するテストを実行する。ただし、設計を大きく変える修正や、ユーザーの決定事項に反する修正は直さず「要確認」にする。
- **それ以外の変更**（ユーザーや他の人のコード、既存の PR など）は直さず、修正案の提示にとどめる。
- コミットやプッシュはユーザーに頼まれない限りしない。

### 7. 報告する

スクリプトの出力の先頭（設定・範囲・所要時間・保存先・`codex resume` の行）をそのまま表示し、続けて次を日本語で簡潔に書く。Codex のレビュー全文は貼らない（保存先にある）。

```markdown
## Codex の総評
（1〜2 行で要約。リリースしてよいかの判断と、最悪の場合に何が起きるか）

## 指摘への判断
| 重要度 | 指摘 | 場所 | 判断 | 理由・対応 |
| --- | --- | --- | --- | --- |
| 高 | ... | `path:line` | 採用（修正済み） / 採用（修正案） / 不採用 / 要確認 | ... |

## 修正内容
（6. で直したものと、実行したテストの結果。直していなければ修正案を箇条書きで）

## リリース前に確認すること
（Codex の「リリース前に確認すべきこと」のうち妥当なもの。なければ省く）

## ユーザーに確認したいこと
（Codex の「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 修正後にもう一度レビューする場合は、新しい実行フォルダを作り、実装の説明に「前回レビューへの対応」の節を加えてから 2. からやり直す（重要度「高」を直したときは、もう一度 Astra にかけるかをユーザーに聞く）。
