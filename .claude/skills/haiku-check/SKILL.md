# Haiku 5.5 に確認を任せる

引数: $ARGUMENTS

テスト・検査・CI のログの確認など、出力が長く状態を変えない確認を、Haiku 5.5（推論レベル max）のサブエージェント `haiku-checker` に任せ、Claude は短い報告だけを読む。数百〜数千行のログやスタックトレースを Claude が読まずに済むので、コンテキストを節約できる。モデル・推論レベル・使えるツール（Read / Grep / Glob / Bash）はエージェントの定義で固定している。ログと、確認の実行で変わったファイルの差分は `artifacts/haiku-check/` に保存される。

Haiku はサンドボックスなしで、メインのセッションと同じ権限で動く。DB・Docker・localhost のサービスに接続するテストもそのまま実行できる。

## 任せるもの

次の 3 つをすべて満たすものを任せる。

1. 出力が長い（数十行以上、またはログやスタックトレースが出る）
2. Claude が次の判断に使うのは要約（成否・場所・原因の見立て）だけ
3. 追跡対象のファイル、プロジェクトの環境（`node_modules`・仮想環境など）、外部の状態を変えない。GitHub やパッケージのレジストリへの読むだけの問い合わせはよい

| 種類 | 例 |
| --- | --- |
| テスト（E2E を含む） | `npm test`、`pytest` |
| 型チェック・リンター | `tsc --noEmit`、`eslint`、`ruff check` |
| ビルド | `npm run build`、`docker build` |
| フォーマットの検査・静的解析 | `prettier --check`、`semgrep` |
| カバレッジ | `pytest --cov`、`vitest --coverage` |
| 依存の脆弱性検査 | `npm audit`、`pip-audit`、`govulncheck` |
| CI の失敗ログの確認 | `gh pr checks`、`gh run view --log-failed` |
| 開発環境のログの調査 | `log/*.log`、立ち上がっているコンテナの `docker compose logs` |

## 任せないもの

| 種類 | 例 | 代わりに |
| --- | --- | --- |
| 状態を変えるコマンド | 依存のインストール・更新、マイグレーションの適用、デプロイ、`--fix`・`--write`・`-u`、コード生成、`gh run rerun` | Claude が直接実行する。リンターの自動修正は Claude が実行し、残りの確認を任せる |
| 出力の細部で戻しにくい判断をするもの | `terraform plan`、マイグレーションの SQL の確認 | Claude が自分で読む。要約で destroy などを落とすと事故になる |
| 出力をそのまま使うもの | `git diff`、コードの検索 | Claude が直接実行する。広い検索は Explore |
| 出力が数行で済むもの | 編集のたびに 1〜数件のテストを回す | Claude が直接実行する |
| 本番環境への接続 | 本番のログ・DB、外部に書き込むテスト | 任せない |
| サーバーやコンテナの起動・停止 | 開発サーバーを立ち上げて置いておく | 任せない。テストが自分で起動・停止するものはよい |

## いつ使うか

ユーザーに頼まれたときに加えて、頼まれていなくても積極的に使う。**Claude が上の「任せるもの」を実行するときは、原則このスキルで Haiku に任せる**。Haiku は Claude の使用量になるが、長い出力を Claude のコンテキストに入れずに済むので、少しでも出力が出るものは任せる。

**必ず任せる**

- 実装や修正を終えて、正しく動くかを確かめるとき（haiku-impl で反映したあとを含む）
- codex-impl-review・codex-risk-impl-review・opus-impl-review の前（変更に関係するテストと型チェック・リンター）と、レビューの指摘を直したあと
- 完了の報告、コミット、PR の作成の前に全体を確かめるとき
- テストスイート全体、複数のコマンド（テスト + 型チェック + リンターなど）、E2E、ビルドを実行するとき
- 失敗の原因を切り分けたいとき、失敗が多いとき
- このリポジトリのテストの実行方法がわからないとき（Haiku が調べる）
- CI が落ちたとき（ユーザーに言われた、PR の CI の失敗を知らされた）。失敗したジョブ・ステップと原因を調べさせる
- 依存を追加・更新したとき。テストと一緒に脆弱性検査も任せる
- 開発環境のログからエラーの原因を探すとき
- ユーザーが「テストして」「動くか確認して」「CI 通る？」「CI が落ちた理由を見て」などと言ったとき

**Claude が直接実行する**（「任せないもの」に加えて）

- ユーザーが「自分で実行して」「Haiku は使わないで」と言っている
- 秘密情報を手で渡す必要があるテスト

迷ったら任せる。

**自分の判断で使うときの違い**

- 始める前に「〇〇の確認は Haiku 5.5 のサブエージェントに任せます」と 1 行だけ伝え、確認は待たずに進める。
- `haiku-checker` が見つからない・エラーで結果が返らなかったときは、そのことを 1 行伝えて Claude が自分で実行する。

## 手順

### 1. 依頼をまとめる

- 実行するコマンドがわかっていれば、それを依頼に書く（例: `npm test と npx tsc --noEmit を実行`）。わからなければ省略してよい。Haiku がリポジトリから実行方法を調べる。
- 範囲を絞るなら書く（例: `src/billing 配下に関係するテストだけ`）。Claude が変えたファイルがわかっていれば、それも書くと切り分けが速くなる。
- 種類ごとに、次も書く。
  - CI のログ: PR 番号・ブランチ・run ID（と attempt）のどれか。なければ作業場所の今のブランチを使う。ローカルで再現させたいときだけ、そう書く
  - 依存の検査: 追加・更新した依存がわかっていれば書く
  - カバレッジ: 比較元（例: `main` からの差分、未コミットの変更）
  - ログの調査: ログのファイルやコンテナ、時刻の範囲、探しているエラーの手がかり
- 対象が今のフォルダ以外のリポジトリなら、2. で `--cd <そのリポジトリのパス>` をつける。
- haiku-impl の Haiku が DB を使うテストを実行している間は、同じ DB を使うテストを任せない（取り合って結果が食い違う）。
- 秘密情報（トークン、パスワード、個人情報）は依頼に書かない。

### 2. 実行フォルダを作る

ログの保存先を作り、確認の前の状態を記録する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/changes.sh" new [--cd <dir>]
```

### 3. Haiku に実行させる

Agent ツールで呼ぶ。

- `subagent_type`: `haiku-checker`
- `model` と `effort`: **渡さない**（定義の `claude-haiku-5-5` と `max` を使う。`model` に別名を渡すと固定が外れる）
- `prompt`: 次の形で書く

  ```text
  作業場所: <changes.sh が出した作業場所>
  ログの保存先: <changes.sh が出したログの保存先>
  依頼: <1. でまとめた内容。なければ「テスト・型チェック・リンターを一通り実行」>
  ```

- バックグラウンドで動き、終わると通知が来るので、それまで待つ。ポーリングはしない。
- **実行中は Claude もユーザーも作業フォルダのファイルを変更しない**（結果が食い違ううえ、Haiku が変更したと誤って警告される）。待つ間は、ファイルを変えない作業（コードを読む、次の作業を考える）だけを進める。

### 4. ファイルが変わっていないか確かめる

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/changes.sh" check <実行フォルダ>
```

- 「変わったファイル」が出たら差分を Read で確かめ、Haiku による不要な変更なら取り除く（テストやビルドで自然にできる生成物なら残してよい）。ユーザーのもとからの変更には触れない。

### 5. 報告を読んで判断する

- Haiku の報告だけを読む。原因の見立てに挙がった `path:line` は、直すのに必要な範囲で Read する。
- Haiku の見立てはうのみにしない。「テストが古い・誤り」とされたものは、テストを直すべきかコードを直すべきかを Claude が判断する（仕様の変更を伴うならユーザーに確認する）。
- CI のログでは、run の commit SHA が `HEAD` と一致しない・未コミットの変更があるという報告なら、ローカルの今のコードとずれている前提で読む。
- 指摘が多いときは、報告にある `issues-<番号>.txt` を Grep で必要な分だけ読む。「抜き出しが不完全」とあれば、ログも合わせて確かめる。
- 報告だけでは判断できないときに限り、ログ（`<実行フォルダ>/cmd-<番号>.log`）を Grep で必要な箇所だけ読む。ログ全体は Read しない。

### 6. 直して再実行する

Claude が直したあとの再実行は、同じ Haiku に SendMessage で頼むと、前回の文脈を引き継いで失敗したものだけを確かめさせられる。頼む前に `changes.sh snap <実行フォルダ>` で状態を記録し直し、終わったら 4. と同じく `check` する。

```text
失敗していたテストを直しました。前回失敗したテストと実行できなかったテストを、同じログの保存先に続きの番号で保存しながら再実行してください。
```

失敗したテストが 1〜2 件で出力も短いなら、Claude が直接そのテストだけを実行してもよい。最後に全体を確かめるときは、もう一度 Haiku に任せる。CI の失敗は、直してプッシュしたあとの新しい run をもう一度任せる。

## 報告する

所要時間とトークン（完了の通知）を 1 行にまとめ、続けて次を日本語で簡潔に書く。Haiku の報告の全文やログは貼らない（保存先にある）。

```markdown
## 確認の結果
（成功 / 失敗・指摘あり / 実行できず と、コマンドごとの件数）

## 失敗・指摘と対応
| 対象 | 場所 | 原因 | 対応 |
| --- | --- | --- | --- |
| ... | `path:line` | コードの不具合 / テストが古い / 依存の脆弱性 / 環境 | Claude が修正して再実行で成功 / 未対応（理由） |

## 実行できなかったもの
（理由と、何があれば実行できるか。なければ省く）
```
