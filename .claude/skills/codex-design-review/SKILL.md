# Codex による設計レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が考えた設計を、別のモデル（Codex CLI の GPT-6.1 Sol）に独立してレビューさせ、その指摘を Claude が吟味する。Codex の呼び出しと保存はスクリプトに任せ、Claude は「設計書をまとめる」「指摘を判断する」だけを行う。結果は `artifacts/codex-design-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Claude が設計や実装計画をまとめ、ユーザーに提示する（または実装を始める）前に、次の基準で判断する。**迷ったら使う。**

**使う**（次のどれかに当たる）

- 3 ファイル以上に手を入れる設計、新しい機能・画面・API・モジュールを作る設計
- 複数の案を比べて 1 つを選んだ設計（選ばなかった案との比較を独立に確かめる）
- 規模にかかわらず、次に触れる設計
  - DB スキーマ、公開 API・インターフェース、設定ファイルの形式、データ移行
  - 認証・権限・課金・個人情報・秘密情報
  - 並行処理、キャッシュ、分散、再試行、データの整合性
  - 後から戻しにくいもの（外部公開、互換性を壊す変更、データの削除・変換）
- 新しいライブラリやアーキテクチャ上の仕組みを持ち込む
- haiku-impl で Haiku に任せる前の、分割や指示書の前提になる設計

**使わない**

- 1〜2 ファイルに収まる局所的な変更、原因と直し方が明らかなバグ修正、文言・設定値だけの変更
- ユーザーが「レビューは不要」「急ぎ」と言っている
- 同じ設計をこの会話ですでにレビュー済みで、その後の変更が小さい（大きく変えたら、もう一度レビューする）

**自分の判断で使うときの違い**

- 設計が codex-risk-design-review の「聞く」条件（データ移行・認可・課金・外部への送信など、壊れると影響が大きく戻しにくいもの）に当たるときは、先に codex-risk-design-review の聞き方で Astra を使うかをユーザーに聞き、その答えに従う（Astra を選ばれたらこのスキルは使わない）。
- 始める前に「提示する前に Codex に設計をレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。Fast モードはユーザーの指定がない限り使わない。
- まだユーザーに見せていない Claude 自身の設計案なので、5. で「採用」とした指摘は設計に反映してから提示してよい。その場合も、5. の表で何を採用し何を変えたかを示す。
- Codex がエラーで動かなかったら、そのことを 1 行伝えて、レビューなしで設計を提示する。

## 観点ごとに分けて並列でレビューするとき

**基本は Sol 1 本**で全観点を見る。並列にすると観点ごとに深く見られ、所要時間は一番遅い観点とほぼ同じで済むが、Codex の使用量も、Claude が読んで判断する指摘も観点の数だけ増える。そのため、次のどれかに**はっきり当たるときだけ**、確認を待たずに観点ごとに分けて Sol を並列に動かす。当たるか迷ったら 1 本にする。

1. ユーザーに「観点ごとに分けて」「並列でレビューして」と頼まれた
2. 設計が大きい: 新しいモジュールを 2 つ以上作るか、10 ファイル以上に手を入れる見込み
3. 次の領域のうち 2 つ以上に触れる: DB スキーマ・データ移行 / 認証・権限 / 課金・決済 / 個人情報・秘密情報 / 並行処理・整合性 / 外部への送信・公開 API・保存形式

「重要そう」「なんとなく不安」だけでは並列にしない。

分けるときは、設計に関係する観点だけを 2〜3 本選ぶ（例: 外部からの入力も権限も扱わないなら `security` は外す）。4 本すべてにするのは、ユーザーに頼まれたときだけにする。

| 観点 | 見るもの |
| --- | --- |
| `requirements` | 要件の抜け、前提の誤り（既存コードとの食い違い） |
| `reliability` | 境界ケース・失敗時の動き・並行実行・データ移行、性能・運用 |
| `security` | 認証・認可・権限、入力の検証、秘密情報・個人情報 |
| `simplicity` | もっと単純な代替案、過剰な抽象化、テストのしやすさ |

自分の判断で分けるときは、「提示する前に Codex に観点ごとに並列で設計をレビューさせます（requirements / reliability、effort=<レベル>）」と 1 行伝える。

## 手順

### 1. 引数を読む

- `--fast` または `fast` があれば Fast モードにする（速いぶん Codex の使用量が増える）。それ以外の依頼文に「速く」「fast で」とあっても同じ。
- `--focus <観点>,...` があれば、そのまま 4. に渡す。「観点ごとに分けて」「並列で」とあれば、「観点ごとに分けて並列でレビューするとき」の表から関係する観点を選んで渡す。
- ファイルパスがあれば、それをレビュー対象の設計書とする。
- パスがなければ、この会話で Claude が考えた直近の設計案を対象にする。設計案が会話にないときは、何をレビューするかを尋ねて終わる。

### 2. 実行フォルダを作る

設計の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 設計書を書く

出力された「設計書」のパスに、Write ツールで Markdown を書く。ファイルを渡された場合も、内容をそのまま書き写したうえで、下の不足分を補う。

Codex はこの会話を見られないので、設計書だけで判断できるように次を含める。

- **目的と背景**: 何を解決するか、なぜ今か
- **要件・制約**: 機能要件、非機能要件、変えてはいけないもの
- **設計**: 構成、データの流れ、主要なインターフェース、状態の持ち方（必要なら Mermaid 図）
- **検討した代替案**と選ばなかった理由
- **関連する既存コード**: 作業フォルダからの相対パス（Codex が読んで確かめる）
- **気になっている点**: Claude 自身が自信のない判断

ユーザーとの会話で決まったことは「決定事項」として書き、Codex が蒸し返さないようにする。秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. Codex にレビューさせる

Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと 10 分以上かかる）。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} [--fast] [--focus <観点>,...] <実行フォルダ>
```

- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- 観点ごとに分けるときは `--focus requirements,reliability` のように観点をカンマ区切りで渡す。1 回の呼び出しの中で観点の数だけ Codex が並列に動き、結果は観点ごとに `review-<観点>.md` に保存される。一部の観点だけ失敗したら、成功した観点の結果で判断し、失敗した観点を報告で伝える。
- 設計が今のフォルダ以外のリポジトリについてのものなら、`--cd <そのリポジトリのパス>` をつける。
- Codex は読み取り専用のサンドボックスと 1M コンテキストで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。
- エラーなら内容を伝えて終わる。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。

### 5. 報告する

スクリプトの出力の先頭（設定・所要時間・保存先・`codex resume` の行）をそのまま表示し、続けて次を日本語で簡潔に書く。Codex のレビュー全文は貼らない（保存先にある）。

```markdown
## Codex の総評
（1〜2 行で要約）

## 指摘への判断
| 重要度 | 指摘 | 判断 | 理由 |
| --- | --- | --- | --- |
| 高 | ... | 採用 / 一部採用 / 不採用 / 要確認 | ... |

## 設計の修正案
（採用した指摘をもとに、設計のどこをどう変えるか。箇条書きで）

## ユーザーに確認したいこと
（Codex の「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 観点ごとに分けたときは、観点をまたいで同じ指摘をまとめ、1 つの表にする（「指摘」の列の頭に `[security]` のように観点を書く）。「[担当外]」の指摘も同じように判断する。
- 指摘はうのみにしない。必要なら指摘されたファイルを Read / Grep で確かめ、根拠をもって判断する。Codex の指摘が誤っていれば「不採用」とし、理由を書く。
- 修正案は提案にとどめ、設計書やコードはユーザーの了承なしに書き換えない（自分の判断で使った場合の、提示前の設計案への反映は除く）。
- 修正後にもう一度レビューする場合は、新しい実行フォルダを作り、設計書に「前回レビューへの対応」の節を加えてから 2. からやり直す。
