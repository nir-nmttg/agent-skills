# Codex による設計レビュー

引数: $ARGUMENTS
Claude の推論レベル: ${CLAUDE_EFFORT}

Claude が考えた設計を、別のモデル（Codex CLI の GPT-6.1 Sol）に独立してレビューさせ、その指摘を Claude が吟味する。Codex の呼び出しと保存はスクリプトに任せ、Claude は「設計書をまとめる」「指摘を判断する」だけを行う。結果は `artifacts/codex-design-review/` に保存される。

## 自分の判断で使うとき

ユーザーに頼まれていなくても、積極的に使う。Claude が設計や実装計画をまとめ、ユーザーに提示する（または実装を始める）前に、次の基準で判断する。**迷ったら使う。**

**使う**: 作り方の判断を含む設計や実装計画は、規模にかかわらずすべて。たとえば次のもの。

- 新しい機能・画面・API・モジュールを作る、新しいライブラリやアーキテクチャ上の仕組みを持ち込む
- 複数の案を比べて 1 つを選ぶ（選ばなかった案との比較を独立に確かめる）
- DB スキーマ、公開 API・インターフェース、設定ファイルの形式、データ移行、認証・権限・課金・個人情報・秘密情報、並行処理、キャッシュ、分散、再試行、データの整合性、後から戻しにくいもの（外部公開、互換性を壊す変更、データの削除・変換）に触れる
- 外部のツール・ライブラリ・プラットフォーム・API の挙動を前提にする（公式の資料や実際の動作で確かめていない前提を含む）
- 既存の設計・規約・命名から外れる
- haiku-impl で Haiku に任せる前の、分割や指示書の前提を決める

**使わない**（設計の欠陥が起こりえない、次の場合だけ）

- 設計の判断を含まない変更: 原因と直し方が一通りに決まる修正、意味や動作を変えない修正（typo・整形・コメント）
- ユーザーが「レビューは不要」と言っている
- 同じ設計をこの会話ですでにレビュー済み（再レビューは、直した分だけで判断する。重要度「高」の指摘を直したとき、または直す中で指摘の範囲を超えて設計を足したり、新たにリスク領域に触れたりしたときにもう一度使う。同じ設計への再レビューは 2 回までにし、残る指摘はユーザーに伝える）

**自分の判断で使うときの違い**

- 見つけるのは設計の欠陥（前提の誤り・要件の抜け・壊れやすい構造）。壊れ方は Astra（codex-risk-design-review）が見るので、両方の条件に当たれば両方を使う。
- 設計が codex-risk-design-review の「聞く」条件（データ移行・認可・課金・外部への送信など、壊れると影響が大きく戻しにくいもの）に当たるとき、または当たるか迷うときは、先に codex-risk-design-review の聞き方で Astra を加えるかをユーザーに聞く（そのスキルの「聞かない」に当たるとき、たとえばユーザーが「急ぎ」と言っているときは聞かず、Sol だけで進める）。加えると選ばれたら、codex-risk-design-review の手順で、このスキルと並べて実行する（設計書・指摘のまとめ方・報告の形式はそちらに従う）。
- 始める前に「提示する前に Codex に設計をレビューさせます（effort=<レベル>）」と 1 行だけ伝え、確認は待たずに進める。
- まだユーザーに見せていない Claude 自身の設計案なので、5. で「採用」とした指摘は設計に反映してから提示してよい。その場合も、5. の表で何を採用し何を変えたかを示す。
- Codex がエラーで動かなかったら、そのことを 1 行伝えて、レビューなしで設計を提示する。

## 総合と観点ごとの重点を並列でレビューするとき

並列にすると、全観点を見る総合の 1 本に加えて、指定した観点を重点的に深く見る Sol が並列に動く（`--focus`）。所要時間は一番遅い 1 本とほぼ同じで、1 本では広すぎて見落とす欠陥を拾える。次のどれかに当たるときは、確認を待たずに並列にする。**1〜5 に当たるか迷ったら並列にする**（どれにも当たらない漠然とした不安では並列にしない）。

1. ユーザーに「観点ごとに分けて」「並列でレビューして」と頼まれた
2. 設計が大きい: 新しいモジュールを 2 つ以上作るか、10 ファイル以上に手を入れる見込み
3. 次の領域のうち 2 つ以上に触れる: DB スキーマ・データ移行 / 認証・権限 / 課金・決済 / 個人情報・秘密情報 / 並行処理・整合性 / 外部への送信・公開 API・保存形式
4. haiku-impl で 2 本以上の小タスクに分けて並行で実装させる前提の設計（分け方やつなぎ目の誤りが、実装の本数だけ広がる）
5. 外部の挙動の前提が設計を大きく左右する（前提が誤っていたら作り直しになる）

重点の観点は、並列にした理由に対応するものを 1〜3 本選ぶ（例: 2. なら `requirements`・`simplicity`、3. ならその領域に合わせて `security`・`reliability`、4. なら `requirements`、5. なら `requirements`・`reliability`）。それ以外の観点は、スクリプトが自動で加える総合の 1 本が見る。4 本すべてを重点にするのは、ユーザーに頼まれたときだけにする。

| 観点 | 見るもの |
| --- | --- |
| `requirements` | 要件の抜け、前提の誤り（既存コードとの食い違い） |
| `reliability` | 境界ケース・失敗時の動き・並行実行・データ移行、性能・運用 |
| `security` | 認証・認可・権限、入力の検証、秘密情報・個人情報 |
| `simplicity` | もっと単純な代替案、過剰な抽象化、テストのしやすさ |

自分の判断で並列にするときは、「提示する前に Codex に総合と観点ごとの重点で並列に設計をレビューさせます（requirements / reliability、effort=<レベル>）」と 1 行伝える。

## 手順

### 1. 引数を読む

- `--focus <観点>,...` があれば、そのまま 4. に渡す。「観点ごとに分けて」「並列で」とあれば、「総合と観点ごとの重点を並列でレビューするとき」の表から関係する観点を選んで渡す。
- ファイルパスがあれば、それをレビュー対象の設計書とする。
- パスがなければ、この会話で Claude が考えた直近の設計案を対象にする。設計案が会話にないときは、何をレビューするかを尋ねて終わる。

### 2. 実行フォルダを作る

設計の内容を表す短い英数字の名前（例: `auth-token-refresh`）を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/new-run.sh" <slug>
```

### 3. 設計書を書く

出力された「設計書」のパスに、Write ツールで Markdown を書く。ファイルを渡された場合も、内容をそのまま書き写したうえで、下の不足分を補う。

Codex はこの会話を見られないので、設計書だけで判断できるように次を含める。

- **目的と背景**: 何を解決するか、なぜ今か
- **要件・制約**: 機能要件、非機能要件、変えてはいけないもの
- **設計**: 構成、データの流れ、主要なインターフェース、状態の持ち方（必要なら Mermaid 図）
- **検討した代替案**と選ばなかった理由
- **関連する既存コード**: 作業フォルダからの相対パス（Codex が読んで確かめる）
- **外部の挙動の前提**: 設計が外部のツール・ライブラリ・API の挙動に頼るなら、確かめた版、公式の資料の該当箇所（URL と短い引用）、試した結果を書く。確かめていない前提は「未確認」と書き、実装に入る前に確かめる（Codex は外部にアクセスできないので、設計書にない根拠は確かめられない）
- **気になっている点**: Claude 自身が自信のない判断

ユーザーとの会話で決まったことは「決定事項」として書き、Codex が蒸し返さないようにする。秘密情報（トークン、パスワード、個人情報）は書かない。

### 4. Codex にレビューさせる

Bash ツールを **`run_in_background: true`** で実行する（推論レベルが高いと 10 分以上かかる）。終わると通知が来るので、それまで待つ。ポーリングはしない。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/review.sh" --effort ${CLAUDE_EFFORT} [--focus <観点>,...] <実行フォルダ>
```

- `--effort` には上の「Claude の推論レベル」をそのまま渡す。空や `auto` のときは省略してよい（スクリプトが high にする）。
- 並列にするときは `--focus requirements,reliability` のように重点の観点をカンマ区切りで渡す。1 回の呼び出しの中で、総合の 1 本と観点の数だけの Codex が並列に動き、結果は `review-general.md`（総合）と観点ごとの `review-<観点>.md` に保存される。一部だけ失敗したら、成功した分の結果で判断し、失敗した分を報告で伝える（総合が失敗したら、1 本でもう一度実行する）。
- 設計が今のフォルダ以外のリポジトリについてのものなら、`--cd <そのリポジトリのパス>` をつける。
- Codex は読み取り専用のサンドボックスと 1M コンテキストで動き、個人設定（MCP サーバーやプラグイン）は読み込まない。
- エラーなら内容を伝えて終わる。`codex` が見つからない・ログインしていないときは、`brew install --cask codex` と `codex login` を案内する。

### 5. 報告する

スクリプトの出力の先頭（設定・所要時間・保存先・`codex resume` の行）をそのまま表示し、続けて次を日本語で簡潔に書く。Codex のレビュー全文は貼らない（保存先にある）。

```markdown
## Codex の総評
（1〜2 行で要約）

## 指摘への判断
| 重要度 | 指摘 | 判断 | 理由 |
| --- | --- | --- | --- |
| 高 | ... | 採用 / 一部採用 / 不採用 / 要確認 | ... |

## 設計の修正案
（採用した指摘をもとに、設計のどこをどう変えるか。箇条書きで）

## ユーザーに確認したいこと
（Codex の「確認したい点」や「要確認」のうち、ユーザーにしか決められないもの。なければ省く）
```

- 並列にしたときは、総合と観点をまたいで同じ指摘をまとめ、1 つの表にする（「指摘」の列の頭に `[総合]`・`[security]` のように担当を書く）。「[担当外]」の指摘も同じように判断する。codex-risk-design-review と並べたときも、Astra の指摘を `[Astra]` として同じ表にまとめる。
- 指摘はうのみにしない。必要なら指摘されたファイルを Read / Grep で確かめ、根拠をもって判断する。Codex の指摘が誤っていれば「不採用」とし、理由を書く。
- 修正案は提案にとどめ、設計書やコードはユーザーの了承なしに書き換えない（自分の判断で使った場合の、提示前の設計案への反映は除く）。
- 修正後にもう一度レビューする場合は、新しい実行フォルダを作り、設計書に「前回レビューへの対応」の節を加えてから 2. からやり直す。
