# Haiku 5.5 にテストを実行させる

引数: $ARGUMENTS

テストの実行と失敗の切り分けを、Haiku 5.5（推論レベル max）のサブエージェント `haiku-tester` に任せ、Claude は短い報告だけを読む。テストの出力（数百〜数千行のログやスタックトレース）を Claude が読まずに済むので、コンテキストを節約できる。モデル・推論レベル・使えるツール（Read / Grep / Glob / Bash）はエージェントの定義で固定している。ログと、テストの実行で変わったファイルの差分は `artifacts/haiku-test/` に保存される。

Haiku はサンドボックスなしで、メインのセッションと同じ権限で動く。DB・Docker・localhost のサービスに接続するテストもそのまま実行できる。

## いつ使うか

ユーザーに頼まれたときに加えて、頼まれていなくても積極的に使う。**Claude がテスト・型チェック・リンター・ビルドを実行するときは、原則このスキルで Haiku に任せる**。Haiku は Claude の使用量になるが、長い出力を Claude のコンテキストに入れずに済むので、少しでも出力が出るものは任せる。

**必ず任せる**

- 実装や修正を終えて、正しく動くかを確かめるとき（haiku-impl で反映したあとを含む）
- codex-impl-review・codex-risk-impl-review・opus-final-review の前（変更に関係するテストと型チェック・リンター）と、レビューの指摘を直したあと
- 完了の報告、コミット、PR の作成の前に全体を確かめるとき
- テストスイート全体、複数のコマンド（テスト + 型チェック + リンターなど）、E2E、ビルドを実行するとき
- 失敗の原因を切り分けたいとき、失敗が多いとき
- このリポジトリのテストの実行方法がわからないとき（Haiku が調べる）
- ユーザーが「テストして」「動くか確認して」「CI 通る？」などと言ったとき

**Claude が直接実行する**（これ以外は任せる）

- 出力が数行で済む 1 件〜数件のテストを、編集のたびに数秒で結果を見たい細かい繰り返しの最中（区切りがついたら、全体の確認は任せる）
- ユーザーが「自分で実行して」「Haiku は使わないで」と言っている
- 本番環境や外部サービスに書き込むテスト、秘密情報を手で渡す必要があるテスト

迷ったら任せる。

**自分の判断で使うときの違い**

- 始める前に「テストの実行は Haiku 5.5 のサブエージェントに任せます」と 1 行だけ伝え、確認は待たずに進める。
- `haiku-tester` が見つからない・エラーで結果が返らなかったときは、そのことを 1 行伝えて Claude が自分で実行する。

## 手順

### 1. 依頼をまとめる

- 実行するコマンドがわかっていれば、それを依頼に書く（例: `npm test と npx tsc --noEmit を実行`）。わからなければ省略してよい。Haiku がリポジトリから実行方法を調べる。
- 範囲を絞るなら書く（例: `src/billing 配下に関係するテストだけ`）。Claude が変えたファイルがわかっていれば、それも書くと切り分けが速くなる。
- 対象が今のフォルダ以外のリポジトリなら、2. で `--cd <そのリポジトリのパス>` をつける。
- haiku-impl の Haiku が DB を使うテストを実行している間は、同じ DB を使うテストを任せない（取り合って結果が食い違う）。
- 秘密情報（トークン、パスワード、個人情報）は依頼に書かない。

### 2. 実行フォルダを作る

ログの保存先を作り、テストの前の状態を記録する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/changes.sh" new [--cd <dir>]
```

### 3. Haiku に実行させる

Agent ツールで呼ぶ。

- `subagent_type`: `haiku-tester`
- `model` と `effort`: **渡さない**（定義の `claude-haiku-5-5` と `max` を使う。`model` に別名を渡すと固定が外れる）
- `prompt`: 次の形で書く

  ```text
  作業場所: <changes.sh が出した作業場所>
  ログの保存先: <changes.sh が出したログの保存先>
  依頼: <1. でまとめた内容。なければ「テスト・型チェック・リンターを一通り実行」>
  ```

- バックグラウンドで動き、終わると通知が来るので、それまで待つ。ポーリングはしない。
- **実行中は Claude もユーザーも作業フォルダのファイルを変更しない**（結果が食い違ううえ、Haiku が変更したと誤って警告される）。待つ間は、ファイルを変えない作業（コードを読む、次の作業を考える）だけを進める。

### 4. ファイルが変わっていないか確かめる

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/changes.sh" check <実行フォルダ>
```

- 「変わったファイル」が出たら差分を Read で確かめ、Haiku による不要な変更なら取り除く（テストの実行で自然にできる生成物なら残してよい）。ユーザーのもとからの変更には触れない。

### 5. 報告を読んで判断する

- Haiku の報告だけを読む。原因の見立てに挙がった `path:line` は、直すのに必要な範囲で Read する。
- Haiku の見立てはうのみにしない。「テストが古い・誤り」とされたものは、テストを直すべきかコードを直すべきかを Claude が判断する（仕様の変更を伴うならユーザーに確認する）。
- 報告だけでは判断できないときに限り、ログ（`<実行フォルダ>/cmd-<番号>.log`）を Grep で必要な箇所だけ読む。ログ全体は Read しない。

### 6. 直して再実行する

Claude が直したあとの再実行は、同じ Haiku に SendMessage で頼むと、前回の文脈を引き継いで失敗したテストだけを確かめさせられる。頼む前に `changes.sh snap <実行フォルダ>` で状態を記録し直し、終わったら 4. と同じく `check` する。

```text
失敗していたテストを直しました。前回失敗したテストと実行できなかったテストを、同じログの保存先に続きの番号で保存しながら再実行してください。
```

失敗したテストが 1〜2 件で出力も短いなら、Claude が直接そのテストだけを実行してもよい。最後に全体を確かめるときは、もう一度 Haiku に任せる。

## 報告する

所要時間とトークン（完了の通知）を 1 行にまとめ、続けて次を日本語で簡潔に書く。Haiku の報告の全文やログは貼らない（保存先にある）。

```markdown
## テスト結果
（成功 / 失敗あり / 実行できず と、コマンドごとの件数）

## 失敗と対応
| テスト | 場所 | 原因 | 対応 |
| --- | --- | --- | --- |
| ... | `path:line` | コードの不具合 / テストが古い / 環境 | Claude が修正して再実行で成功 / 未対応（理由） |

## 実行できなかったもの
（理由と、何があれば実行できるか。なければ省く）
```
