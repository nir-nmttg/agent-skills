# 整備スキルを組み合わせてプロジェクト全体を整える

引数: $ARGUMENTS

トークンや時間に余裕があるときに、気になっている箇所を個別に挙げなくてもプロジェクト全体を一巡して整える。改善の効果を基準に実装・検証し、変更不要の工程はそのまま終える。変更件数やトークン消費量を目標にしない。

整備は振る舞いを変えずに構造を変える作業で、テストが通っても処理順序・例外の扱い・テストの検出力が変わりうる。そのため工程ごとに、確認を haiku-check に、差分のレビューを implementation-cross-review（Astra と Fable）に任せる。Haiku への実装の委任（haiku-implementation）は、方針が決まった広い機械的な変更にだけ使う。

このスキルを呼んだことを、作業ブランチへの工程ごとのコミットの依頼とみなす。push・PR・元のブランチへのマージはしない（報告のあとでユーザーに確認する）。

## 1. 引数を読んで始める

- `--steps 1,3` のように工程番号があれば、その工程だけを行う（ほかの工程は「未着手」のまま報告する）。
- 対象のパス・範囲、優先領域、時間やトークンの上限が書かれていれば計画に反映し、検証・修復・報告の余力を残す。指定がなければプロジェクト全体の自前のコード・テスト・利用／開発／運用文書を対象に全工程を一巡する。生成物・依存パッケージ・外部から取り込んだコードは除外する。残量を推測して作業量を決めず、制約内で終えられない範囲は未完了として明記する。
- 対象が今のフォルダ以外のリポジトリなら、下の start.sh に `--cd <そのパス>` を付ける。

**新しく始めるとき**: 整備の内容を表す短い英数字の名前を決めて実行する。

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/start.sh" [--cd <dir>] <slug>
```

- 作業ツリーが整っていれば、実行フォルダに進捗ファイル `progress.md` を作り、今の HEAD から作業ブランチ `codebase-cleanup/<日時>` を切る。開始時の SHA は全体の差分と戻し方の基準になる。
- `progress.md` の「依頼の範囲」に、対象のパス・範囲、行う工程（`--steps` がなければ全工程）、時間やトークンの上限を書く。
- git リポジトリでないと止まる。工程ごとのコミットとクロスレビューが使えないので、このスキルは使えないと伝えて終える（git リポジトリでないフォルダは、ユーザーが 6 本のスキルを個別に指定すれば整備できると案内する）。
- 未コミットの変更（未追跡を含む）があると止まる。表示された変更を示し、コミット・退避するか、デスクトップアプリなら新しい worktree のセッションで始めるかをユーザーに確認する（worktree では依存や `.env` がなく、チェックが実行不能になることがある）。
- ブランチを作れないなどほかの理由で止まったら、エラーの要点を伝えて終える。git の hook の失敗で作業ブランチに切り替わったまま止まったときは、そのことと作業ブランチ名・実行フォルダを伝えて終える。

**`--resume <実行フォルダ>` で再開するとき**: その `progress.md` と `exploration.md` を読み、「依頼の範囲」を引き継ぐ（行わない工程は再開しても行わない）。今のブランチが記録した作業ブランチであることを確かめる。違えば止めて確認する。「作業中」「レビュー中」の工程があれば、`git status` と工程開始時の SHA からの差分で書きかけの変更を確かめ、続けるか戻すかを決めてから進める。完了した工程はやり直さない。

**前提の確認**

- 各工程の判断基準は、`${CLAUDE_SKILL_DIR}/../<スキル名>/SKILL.md` を工程に入る前に Read で読み、この呼び出しの中で適用する（各スキルの「ユーザーに確認する」ものは、追加の承認待ちを挟まず保留に書いて報告で聞く）。読んだら frontmatter の `name` がスキル名と一致することを確かめる。読めない・一致しない工程は、手順を推測して代替しない。不足と影響を記録し、独立して実行できる工程は進める。
- メインのセッションが auto モードでなければ、工程ごとに Haiku の操作の確認が続くので haiku-implementation は使わず、Claude が書く（haiku-check と implementation-cross-review は使う）。

## 2. 共通の探索と準備

- リポジトリの指示、README、設計文書、ディレクトリ・パッケージ構成、実行設定と CI を Claude が自分で読み、設計の根拠と検証方法を把握する（Explore などのサブエージェントには任せない。要約の誤りがレビューの要件にまで渡るため）。
- 各領域の入口、主要経路、設計上の制約、関連テスト、探索済み・未探索の範囲を `exploration.md` にまとめ、後続の工程へ引き継ぐ。設計の根拠には、Claude が読んだ文書・コードの場所を書く。各工程で全体探索を最初から繰り返さず、変更されたコードと新しく影響する依存先は読み直す。ファイル一覧の取得だけで探索完了とはしない。
- 変更前の関連チェック（リポジトリで必須のテスト・型チェック・lint・ビルド・文書検証）を haiku-check で実行し、成功・既存の失敗・実行不能を `progress.md` の「変更前のチェック（基準）」に書く。以後の haiku-check の依頼には `progress.md` のパスを渡し、既存の失敗と新しい失敗を区別させる。

## 3. 次の順番で整備する

| 順序 | スキル | この工程の役割 |
| --- | --- | --- |
| 1 | [design-alignment-refactor](../design-alignment-refactor/SKILL.md) | 現在の設計方針を根拠に逸脱を修正し、後続が守る責務の境界や依存方向を明確にする。 |
| 2 | [overengineering-refactor](../overengineering-refactor/SKILL.md) | 明確になった設計の範囲で、未使用コードや要件に対して過剰な抽象化・汎用化・防御的実装を取り除き、後続が不要な複雑さまで整理し直さないようにする。 |
| 3 | [code-structure-refactor](../code-structure-refactor/SKILL.md) | その方針を保ちながら、責務の混在・重複・過剰な分割を整理する。前工程で解消・削除した候補を別案へ作り直さない。 |
| 4 | [test-suite-refactor](../test-suite-refactor/SKILL.md) | 本体の構造が落ち着いてから、検出力を保ってテストの重複や実装の細部への依存を整理する。前工程の確認に必要なテストは先に削減しない。 |
| 5 | [code-order-refactor](../code-order-refactor/SKILL.md) | 本体・テストの抽出や統合を終えた状態で、ファイル内の宣言を読みやすい順に整える。 |
| 6 | [docs-align-with-code](../docs-align-with-code/SKILL.md) | 最終的な実装に利用・開発・運用の説明と導線を合わせる。設計方針を実装に合わせて書き換え、保留した逸脱を解消した扱いにしない。 |

最初に順序と採用理由を簡潔に伝えてから進める。各工程に共通の対象範囲を引き継ぎ、直近の差分だけで探索を終えない。

### 各工程の進め方

1. **始める**: `progress.md` のその工程を「作業中」にし、工程開始時の SHA（`git rev-parse HEAD`）を書く。
2. **候補を決める**: その工程の SKILL.md の判断基準で、効果のある候補を決める。公開 API・永続化形式・業務ルールなど判断が必要な契約変更は保留して「保留・未探索」に書き、独立した改善を進める。作り方の判断を含む候補（複数の構造から 1 つを選ぶ、リスク領域に触れる、Haiku に任せる前の分割を決める）は、design-cross-review の条件で設計レビューを使う。
3. **実装する**: 担当は haiku-implementation の基準より絞り、方針と変更箇所が決まっていてテストで確かめられる、広い機械的な変更（多数の呼び出し元の置き換え、ファイルをまたぐ抽出、宣言の大量移動）だけを Haiku に任せ、それ以外は Claude が書く。工程 5 を Haiku に任せたときは、移動以外の変更が混ざっていないことを Claude が差分で確かめる。構造変更に必要なテスト・文書・参照先の更新は、その変更と一緒に行う。
4. **確かめる**: haiku-check で影響範囲のテスト・型チェック・lint・ビルドを実行する。新たな失敗はまず自分の変更を修復し、解消できなければ該当する自分の変更だけを戻す。失敗した変更に依存する後続作業は保留する。同じ状態・条件で成功済みの検証結果は共有し、影響するコードや設定が変わったら再実行する。
5. **レビューする**: 変更があれば `progress.md` を「レビュー中」にし、コミットの前に implementation-cross-review を `--base <工程開始時の SHA>` で動かす。
   - このレビューは工程の終わりの 1 回にまとめ、haiku-implementation の仕上げのレビューを兼ねる（Haiku に任せた小タスクごとにはレビューしない）。
   - 担当の決め方と再レビューは、implementation-cross-review の「自分の判断で使うとき」の規則に従う（工程 6 が動作を決めない文書だけの変更なら Fable だけになる）。
   - 要件には、ユーザーの依頼、この工程の SKILL.md の判断基準、「既存の振る舞いを変えない」、`exploration.md` の設計の根拠を書く。工程 4 では「削除・統合したテストごとに、同じ不具合を同じ観測点で検出するテストが残っていること」を受け入れ条件に書き、Claude の対応づけ（どのテストが代わりに守るか）は要件に書かない。
   - 採用した指摘を直し、直した分を haiku-check で確かめる。
   - レビュアーがどれも結果を返さず、この工程に Haiku に書かせた変更があれば、コミットせずに止めてユーザーに確認する（haiku-implementation の規則）。
6. **コミットする**: この工程で変えたファイル（Haiku の反映分を含む）だけを `git add -- <ファイル>` で指定し（`git add -A` は使わない）、工程ごとに 1 コミットにする。メッセージは「<工程のスキル名>: <主な改善>」の形にする。コミットしたら `git status --porcelain --untracked-files=all` が空であることを確かめ、残りがあれば次の工程に混ぜずに扱いを決める。pre-commit hook が失敗した・ファイルを書き換えたときは `--no-verify` を使わずに止め、内容を確かめてから直すかユーザーに確認する。
7. **記録する**: `progress.md` にコミットの SHA、レビューの実行フォルダ、状態を書く。状態は次のどれかにする。
   - 完了: 変更をコミットし、レビューを受けた
   - 完了（未レビュー）: レビュアーがどれも結果を返さなかった（Haiku に書かせた変更を含まない工程）。報告に明記して続ける
   - 変更不要: 効果のある候補がなかった（レビューもコミットもしない）
   - 保留・未着手・中断: 理由を「メモ」に書く

予算などで途中で止めるときは、書きかけの変更をコミットするか戻すかを決めてから止まり、`progress.md` を更新して、再開の方法（`/codebase-cleanup-workflow --resume <実行フォルダ>`）を報告する。

## 4. 最終状態を検証して報告する

- haiku-check で、リポジトリで必須のテスト・型チェック・lint・ビルド・文書検証を全体に対して実行する。実行できなかった検証を成功扱いにしない。
- 開始時の SHA からの全体の差分を Claude が読み、前工程の改善を後工程で打ち消していないか、既に整った箇所に別案を持ち込んでいないかを確かめる。工程ごとにレビュー済みなので、全体の差分のクロスレビューはしない。変更を作るために全工程を繰り返さず、追加対応は見つかった具体的な問題に絞る。直したら haiku-check で確かめ、implementation-cross-review の条件で判断してから、手順 6 と同じく作業ブランチに 1 コミットし、`progress.md` のメモに SHA を書く。
- 報告の前に `git status --porcelain --untracked-files=all` が空であることを確かめる（未コミットの変更を残すと、元のブランチに戻ったときに付いていく）。
- japanese-report の形で、日本語で簡潔に報告する。
  - 探索範囲と、探索していない範囲
  - 工程ごとの状態（完了・完了（未レビュー）・変更不要・保留・未着手・中断）、主な改善と理由、コミット
  - 工程ごとのレビューの結果（採用・見送りの件数と、残した指摘）
  - 実行した検証と結果（既存の失敗・実行不能を新しい不具合と分ける）
  - 保留した契約変更と、ユーザーに決めてほしいこと
  - 作業ブランチ名、開始時の SHA、実行フォルダ。すべて戻すなら元のブランチに戻って作業ブランチを消せばよいこと
- 予算などで中断した場合は再開の方法を示し、全体完了とは報告しない。すべて変更不要でも、確認した範囲と根拠を伝える。
- 最後に、作業ブランチを push して PR にするか、元のブランチにマージするかをユーザーに確認する（確認なしには行わない）。
